**Question 4:**
Which statement about NACLs is TRUE?

A) NACLs are stateful and automatically allow return traffic  
B) NACLs are evaluated after Security Groups  
C) NACL rules are evaluated in order starting with the lowest numbered rule  
D) NACLs can reference other NACLs for traffic control  

<details>
<summary>Click to reveal answer</summary>

**Answer: C ✅**

**Explanation:**
- NACL rules have numbers (1-32766)
- Evaluated in order: lowest to highest
- First match wins
- Remaining rules not evaluated

Example:
- Rule 100: ALLOW 0.0.0.0/0
- Rule 200: DENY 192.0.2.0/24
- Result: 192.0.2.0/24 is ALLOWED (Rule 100 matches first)

Correct order:
- Rule 100: DENY 192.0.2.0/24
- Rule 200: ALLOW 0.0.0.0/0
- Result: 192.0.2.0/24 is DENIED ✅

Why others are wrong:
- A: NACLs are STATELESS (not stateful)
- B: NACLs evaluated BEFORE Security Groups
- D: NACLs can't reference each other (IP/CIDR only)

**Key Concept:** NACL rule order matters, lowest first!
</details>

**Question 17:**
A Network Firewall has stateless and stateful rule groups. In what order are they evaluated?

A) Stateful first, then stateless  
B) Stateless first, then stateful  
C) Based on priority numbers  
D) Evaluated simultaneously  

<details>
<summary>Click to reveal answer</summary>

**Answer: B ✅**

**Explanation:**
Network Firewall packet flow:
```
1. Stateless rules (fast, priority-based)
   ↓
   Actions: DROP, PASS, FORWARD to stateful
   ↓
2. Stateful rules (deep inspection)
   ↓
   Actions: PASS, DROP, REJECT, ALERT
```

Why this order:
- Stateless is FAST (simple packet filtering)
- Drop obviously bad traffic early
- Forward complex decisions to stateful
- Stateful is SLOWER (connection tracking, deep inspection)

Example flow:
```
Packet arrives
→ Stateless rule 1 (priority 1): DROP known bad IPs
→ Stateless rule 10: FORWARD port 80/443 to stateful
→ Stateful domain filter: Check if domain blocked
→ Stateful Suricata: Deep packet inspection for attacks
→ Decision: PASS or DROP
```

**Key Concept:** Stateless THEN stateful in Network Firewall!
</details>

**Question 29:**
A company needs to ensure all outbound HTTPS traffic from EC2 instances is inspected for data exfiltration. The solution should not require decrypting TLS traffic. What approach works?

A) AWS WAF on ALB  
B) Network Firewall with TLS SNI inspection  
C) VPC Flow Logs analysis  
D) Cannot inspect HTTPS without decryption  

<details>
<summary>Click to reveal answer</summary>

**Answer: B ✅**

**Explanation:**
TLS SNI (Server Name Indication):
- Sent during TLS handshake
- BEFORE encryption starts
- Contains destination domain name
- Can be inspected without decryption!

Network Firewall domain filtering:
```
Target Types: TLS_SNI
Targets: 
  - .dropbox.com
  - .box.com
  - .mega.nz (file sharing services)
Generated Rules Type: DENYLIST

Result:
Instance → exfil-data → dropbox.com
→ Network Firewall sees SNI: dropbox.com
→ Blocks connection (in DENYLIST)
→ Data exfiltration prevented ✅
```

What you CAN see:
- Which domain is being accessed
- Can block/allow based on domain

What you CANNOT see:
- Content of HTTPS traffic (encrypted)
- Specific files being transferred

For full inspection:
- Need TLS decryption (SSL inspection)
- Requires third-party firewall (Palo Alto, Fortinet)
- Network Firewall doesn't decrypt

**Key Concept:** TLS SNI inspection = domain visibility without decryption!
</details>
