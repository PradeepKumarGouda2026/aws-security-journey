**Correct answer:** B - The key policy doesn't allow the user

**Why you got it wrong:**
- You thought IAM AdministratorAccess grants all permissions

**The truth:**
```
KMS uses BOTH key policy AND IAM policy:

Key Policy (resource-based):
- Attached to the KMS key
- MUST allow access first

IAM Policy (identity-based):
- Attached to user/role
- Evaluated AFTER key policy
- Both must allow = access granted

Scenario:
User has AdministratorAccess (IAM) → Allows kms:*
But key policy says: "Only allow alice" → User is NOT alice
Result: Access Denied ❌

Fix: Add user to key policy OR enable IAM policies
```

**Remember:** Key policy is the FIRST gate. If it doesn't allow you, IAM policy doesn't matter!

- OPTIONAL for most standards

Level 4: Tamper-reactive
- Not offered by AWS

Compliance Standards Reality:

HIPAA: ❌ Does NOT require Level 3
- Requires "encryption at rest and in transit"
- KMS (Level 2) is COMPLIANT ✅
- CloudHSM is overkill (but allowed)

PCI-DSS: ❌ Does NOT require Level 3
- Requires "strong cryptography"
- KMS (Level 2) is COMPLIANT ✅
- Some orgs choose Level 3 (not required)

SOC 2: ❌ Does NOT require Level 3
- Requires "encryption"
- KMS (Level 2) is COMPLIANT ✅

GDPR: ❌ Does NOT require Level 3
- Requires "appropriate security"
- KMS (Level 2) is COMPLIANT ✅

When Level 3 IS required:
- Specific government contracts
- Specific industry requirements
- Company internal policy
- NOT generic compliance standards!

Exam Trick:
Question: "Contract REQUIRES FIPS Level 3" → CloudHSM
