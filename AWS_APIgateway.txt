## 1.1 Service Overview & Purpose

### What is AWS API Gateway?
AWS API Gateway is a fully managed service that enables you to **create, publish, maintain, monitor, and secure APIs** at any scale. It acts as the **front door** for applications to access backend services such as Lambda, EC2, ECS, or any HTTP endpoint.

Think of API Gateway as a **highly configurable security checkpoint** — every API call passes through it, giving you centralized control over authentication, authorization, throttling, logging, and transformation.

### Three API Types
```
API Gateway offers three types:

REST API:
├── Most feature-rich option
├── Full request/response transformation
├── All authentication methods supported
├── Usage plans and API keys
├── Caching support
└── Higher cost

HTTP API:
├── Newer, simpler, cheaper (~70% less than REST)
├── Lower latency
├── JWT authorizers (Cognito/OIDC natively)
├── No API keys or usage plans
├── No request/response transformation
└── Best for: Lambda proxy, JWT auth

WebSocket API:
├── Persistent two-way connections
├── Real-time applications (chat, gaming)
├── Connection management
└── Route selection based on message content
```

### Why It Matters for Security Exam
```
API Gateway is a central security control point:
├── Authentication (who can call the API)
├── Authorization (what they can do)
├── Throttling (rate limiting)
├── WAF integration (attack protection)
├── TLS enforcement (encryption in transit)
├── Resource policies (network-level control)
├── Logging (CloudWatch, X-Ray)
└── Private APIs (VPC-only access)
```

### Exam Weight & Importance
- Appears in **Domain 2: Identity & Access Management** and **Domain 3: Infrastructure Security**
- Expect **3–5 questions** directly involving API Gateway security
- Commonly tested: authorizer types, resource policies, private APIs, throttling, WAF integration

## 1.2 Core Architecture

### API Gateway Security Architecture
```
┌─────────────────────────────────────────────────────────────────┐
│                    API Gateway Security Layers                  │
│                                                                 │
│  Layer 1: Network                                               │
│  ├── Public endpoint (default)                                  │
│  ├── Private endpoint (VPC only)                                │
│  └── Edge-optimized (CloudFront)                                │
│                                                                  │
│  Layer 2: WAF (optional)                                        │
│  ├── SQL injection blocking                                     │
│  ├── Rate limiting                                              │
│  └── IP blocking                                                │
│                                                                  │
│  Layer 3: Resource Policy                                        │
│  ├── Allow/deny by IP                                           │
│  ├── Allow/deny by VPC                                          │
│  └── Allow/deny by account                                      │
│                                                                  │
│  Layer 4: Authentication                                        │
│  ├── IAM authorization (SigV4)                                  │
│  ├── Cognito User Pool Authorizer                               │
│  ├── Lambda Authorizer (custom)                                 │
│  └── API Keys (usage plans)                                     │
│                                                                  │
│  Layer 5: Backend                                               │
│  ├── Lambda function                                            │
│  ├── HTTP endpoint                                              │
│  └── AWS service                                                │
└─────────────────────────────────────────────────────────────────┘
```

### Request Flow with Security Checks
```
Client Request
      │
      ▼
WAF (if attached) → BLOCK if attack detected
      │
      ▼
Resource Policy → DENY if IP/VPC not allowed
      │
      ▼
Authorizer check:
├── IAM: verify SigV4 signature
├── Cognito: validate JWT token
├── Lambda: custom validation logic
└── API Key: verify key in usage plan
      │
      ▼
Throttling check → 429 if over limit
      │
      ▼
Backend integration → Lambda/HTTP/AWS
      │
      ▼
Response to client
```

## 1.3 Deep Dive — Sub-Topics Part A

### A. Authentication Methods (Full Detail)

#### Method 1: IAM Authorization
```
How it works:
├── Client signs request with AWS SigV4 signature
├── API Gateway validates signature against IAM
├── IAM policies control access to API methods
└── Best for: AWS services, server-to-server, CLI

IAM policy to allow API call:
{
  "Effect": "Allow",
  "Action": "execute-api:Invoke",
  "Resource": "arn:aws:execute-api:region:account:api-id/stage/METHOD/resource"
}

Resource ARN format:
arn:aws:execute-api:{region}:{account}:{api-id}/{stage}/{method}/{resource}

Examples:
├── arn:aws:execute-api:*:*:abc123/prod/GET/users
├── arn:aws:execute-api:*:*:abc123/prod/*/users/*
└── arn:aws:execute-api:*:*:abc123/*/*/*  (all methods)
```

> ⚠️ **Exam critical:** IAM authorization uses **SigV4 signing** — the client must have valid AWS credentials. Good for service-to-service but NOT for browser/mobile clients who cannot have IAM credentials.

#### Method 2: Cognito User Pool Authorizer
```
How it works:
├── Client obtains JWT from Cognito User Pool
├── Client sends JWT in Authorization header
├── API Gateway validates JWT against User Pool
├── Valid token → request proceeds
└── Invalid/expired token → 401 Unauthorized

Configuration:
├── Token source: Header (Authorization)
├── User Pool ARN: your Cognito User Pool
├── Token validation: ID token or Access token
└── Authorization caching: 0–3600 seconds

What API Gateway validates:
├── Token signature (using User Pool public keys)
├── Token expiry (exp claim)
├── Token issuer (iss = User Pool URL)
└── Token audience (aud = App Client ID)

What it does NOT validate:
└── Custom business logic — use Lambda authorizer for that
```

#### Method 3: Lambda Authorizer
```
Two types:

TOKEN authorizer:
├── Receives token from header/query param
├── Lambda validates token
├── Returns IAM policy (allow/deny)
└── Use for: custom tokens, third-party JWT, API keys

REQUEST authorizer:
├── Receives full request context
│     (headers, query params, path, stage vars)
├── Lambda validates any combination of inputs
├── Returns IAM policy
└── Use for: complex auth logic, multiple inputs

Lambda Authorizer response format:
{
  "principalId": "user-identifier",
  "policyDocument": {
    "Version": "2012-10-17",
    "Statement": [{
      "Action": "execute-api:Invoke",
      "Effect": "Allow",
      "Resource": "arn:aws:execute-api:..."
    }]
  },
  "context": {
    "userId": "123",
    "role": "admin"
  }
}
```

> ⚠️ **Exam critical:** Lambda Authorizer returns an **IAM policy** — not just allow/deny. The policy is cached and reused for subsequent calls. Context values are passed to backend Lambda.

#### Method 4: API Keys & Usage Plans
```
API Keys:
├── 40-character alphanumeric strings
├── Passed in x-api-key header
├── Used for: identifying callers, not authentication
├── NOT a security mechanism alone
└── Must be combined with Usage Plans

Usage Plans:
├── Define throttling limits per API key:
│     ├── Rate: requests per second
│     └── Burst: maximum concurrent requests
├── Define quota: max requests per day/week/month
├── Associate API keys with usage plans
└── Use for: monetization, rate limiting per client
```

> ⚠️ **Exam trap:** API Keys are for **identification and throttling** — NOT for security/authentication. Never use API keys as your only security mechanism.

### B. Resource Policies (Full Detail)

#### What is a Resource Policy?
A resource policy is a **JSON policy attached to the API** that controls which principals (AWS accounts, IP addresses, VPCs) can invoke the API.

```
Resource policy use cases:
├── Allow access from specific AWS accounts
├── Allow access from specific IP ranges
├── Allow access from specific VPC
├── Deny access from specific countries (with WAF)
└── Restrict private API access to specific VPC
```

#### Cross-Account API Access
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::ACCOUNT_B:root"
      },
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:region:ACCOUNT_A:api-id/*"
    }
  ]
}
```

#### IP-Based Restriction
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:*:*:api-id/*",
      "Condition": {
        "IpAddress": {
          "aws:SourceIp": [
            "203.0.113.0/24",
            "198.51.100.0/24"
          ]
        }
      }
    }
  ]
}
```

#### Private API VPC Restriction
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:*:*:api-id/*",
      "Condition": {
        "StringNotEquals": {
          "aws:SourceVpc": "vpc-12345678"
        }
      }
    },
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:*:*:api-id/*"
    }
  ]
}
```

> ⚠️ **Exam critical:** Private API resource policies need **both a DENY and ALLOW statement**. DENY for wrong VPC + ALLOW for all (VPC check handles restriction). Just having ALLOW with VPC condition is NOT sufficient.

## 1.3 Deep Dive — Sub-Topics Part B

### C. Throttling & Rate Limiting (Full Detail)

#### Throttling Levels
```
API Gateway throttling works at multiple levels:

Level 1: Account Level (default limits)
├── 10,000 requests per second (RPS) per region
├── 5,000 burst limit per region
└── Shared across ALL APIs in account/region

Level 2: Stage Level
├── Override account defaults per stage
├── Example: prod=10,000 RPS, dev=100 RPS
└── Set in Stage settings

Level 3: Method Level
├── Override per HTTP method per resource
├── Example: POST /login = 10 RPS
│           GET /products = 1000 RPS
└── Most granular throttling control

Level 4: Usage Plan Level
├── Per API key throttling
├── Rate: sustained requests per second
├── Burst: token bucket — short spikes allowed
└── Quota: total requests per time period
```

#### Token Bucket Algorithm
```
How burst throttling works:

Token Bucket:
├── Bucket fills at RATE tokens per second
├── Bucket capacity = BURST limit
├── Each request consumes one token
├── If bucket empty → 429 Too Many Requests
└── Burst allows short spikes above sustained rate

Example:
├── Rate: 1000 RPS
├── Burst: 5000
├── Scenario: 5000 requests arrive simultaneously
│     → First 5000 served (bucket full)
│     → Bucket refills at 1000/second
│     → Next second: another 1000 served
└── Without burst: first 1001+ requests throttled
```

> ⚠️ **Exam critical:** When throttled, API Gateway returns **HTTP 429 Too Many Requests**. This is different from 403 (forbidden) or 401 (unauthorized).

#### Throttling Response
```
Throttled request response:
├── Status code: 429
├── Body: {"message": "Too Many Requests"}
├── Headers: X-Amzn-RequestId, x-amzn-ErrorType
└── Retry-After header (optional)

Client should implement:
├── Exponential backoff
├── Jitter (randomize retry timing)
└── Circuit breaker pattern
```

### D. Private APIs & VPC Endpoints (Full Detail)

#### API Endpoint Types
```
Three endpoint types:

Edge-Optimized (default):
├── Deployed to CloudFront edge locations
├── Reduced latency for global clients
├── Certificate must be in us-east-1
├── WAF attached at CloudFront level
└── Best for: public-facing global APIs

Regional:
├── Deployed in specific region only
├── Lower latency for same-region clients
├── Certificate in same region as API
├── WAF attached directly to API
└── Best for: regional apps, cross-region replication

Private:
├── Accessible ONLY from within VPC
├── Requires VPC Interface Endpoint
├── Not accessible from internet
├── Resource policy controls VPC access
└── Best for: internal microservices
```

#### Private API Setup
```
Step 1: Create VPC Interface Endpoint
        Service: com.amazonaws.region.execute-api
        VPC: your VPC
        Subnets: private subnets
        Private DNS: enabled

Step 2: Create Private API in API Gateway
        Endpoint Type: PRIVATE

Step 3: Attach Resource Policy to API
        Allow only from specific VPC endpoint:
        {
          "Condition": {
            "StringEquals": {
              "aws:SourceVpce": "vpce-12345678"
            }
          }
        }

Step 4: DNS resolution
        With private DNS enabled on endpoint:
        execute-api.region.amazonaws.com
        → resolves to private IP inside VPC
```

> ⚠️ **Exam critical:** Private APIs require **both** a VPC Interface Endpoint AND a resource policy. Without the resource policy, the API is still inaccessible. Without the VPC endpoint, there's no private path to reach the API.

#### VPC Endpoint Policy
```json
{
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": [
        "arn:aws:execute-api:region:account:api-id/*"
      ]
    }
  ]
}
```

> ⚠️ VPC Endpoint policies and API Resource policies work together — **both** must allow the call.

### E. Logging & Monitoring (Full Detail)

#### CloudWatch Logs Integration
```
Two types of API Gateway logs:

Execution Logs:
├── Detailed request/response logging
├── Includes: request ID, IP, method, resource
├── Includes: authorizer response
├── Includes: integration request/response
├── Use for: debugging, troubleshooting
└── Cost: CloudWatch Logs charges apply

Access Logs:
├── Custom format (JSON, CLF, XML)
├── Logged to specific CloudWatch Log Group
├── Configurable fields:
│     ├── $context.requestId
│     ├── $context.identity.sourceIp
│     ├── $context.httpMethod
│     ├── $context.resourcePath
│     ├── $context.status
│     ├── $context.responseLength
│     ├── $context.authorizer.principalId
│     └── $context.error.message
└── Use for: security auditing, analytics
```

#### Access Log Format Example
```json
{
  "requestId": "$context.requestId",
  "ip": "$context.identity.sourceIp",
  "caller": "$context.identity.caller",
  "user": "$context.identity.user",
  "requestTime": "$context.requestTime",
  "httpMethod": "$context.httpMethod",
  "resourcePath": "$context.resourcePath",
  "status": "$context.status",
  "protocol": "$context.protocol",
  "responseLength": "$context.responseLength",
  "authorizerError": "$context.authorizer.error",
  "principalId": "$context.authorizer.principalId"
}
```

#### CloudWatch Metrics
```
Key API Gateway metrics:

Count:          Total API requests
Latency:        Full round-trip time (ms)
IntegrationLatency: Backend response time (ms)
4XXError:       Client errors (auth, validation)
5XXError:       Server errors (backend failures)
CacheHitCount:  Responses from cache
CacheMissCount: Responses from backend

Security-relevant metrics:
├── 4XXError spike → possible attack/misconfiguration
├── 5XXError spike → backend overwhelmed (DDoS?)
└── Latency spike → possible slow loris attack
```

#### AWS X-Ray Integration
```
X-Ray tracing for API Gateway:
├── Enable active tracing on stage
├── Traces full request path:
│     Client → API GW → Lambda → DynamoDB
├── Identifies latency bottlenecks
├── Shows error rates per service
└── Service map visualization

X-Ray sampling rules:
├── Default: 5% of requests sampled
├── Custom rules: sample by path/method/rate
└── 100% sampling for debugging (high cost)
```

### F. Additional Security Features

#### Mutual TLS (mTLS) for API Gateway
```
mTLS configuration:
├── Upload truststore to S3
│     (PEM file with CA certificates)
├── Enable mTLS on custom domain
├── Clients must present valid certificate
├── API Gateway validates client cert
│     against truststore
└── Use for: B2B APIs, high-security scenarios

Truststore S3 URI format:
s3://bucket-name/truststore.pem

Client certificate requirements:
├── Signed by CA in truststore
├── Not expired
├── Not revoked
└── Certificate chain valid
```

#### Request Validation
```
API Gateway can validate requests before
they reach your backend:

Validation options:
├── Validate request body (against JSON schema)
├── Validate required headers
├── Validate required query parameters
└── Reject invalid requests with 400

Benefits:
├── Offloads validation from backend Lambda
├── Saves Lambda invocation costs
├── Returns clear error to client
└── Prevents malformed data reaching backend

Model example (JSON Schema):
{
  "type": "object",
  "properties": {
    "email": {
      "type": "string",
      "format": "email"
    },
    "age": {
      "type": "integer",
      "minimum": 18
    }
  },
  "required": ["email", "age"]
}
```

#### CORS Configuration
```
Cross-Origin Resource Sharing (CORS):

Why it matters for security:
├── Browser enforces same-origin policy
├── CORS headers tell browser which
│     origins are allowed
├── Misconfigured CORS = security risk

Secure CORS configuration:
├── Access-Control-Allow-Origin:
│     specific domain (not *)
├── Access-Control-Allow-Methods:
│     only needed methods
├── Access-Control-Allow-Headers:
│     only needed headers
└── Access-Control-Max-Age:
      cache preflight response

Dangerous CORS misconfiguration:
├── Access-Control-Allow-Origin: *
│     + Access-Control-Allow-Credentials: true
└── Allows any site to make credentialed requests
```

## 1.4 Comparison Tables

### Authorizer Comparison

| Feature | IAM Auth | Cognito Authorizer | Lambda Authorizer |
|---|---|---|---|
| **Token type** | SigV4 | JWT | Any (token/request) |
| **Best for** | AWS services | App users | Custom logic |

### REST API vs HTTP API Security

| Feature | REST API | HTTP API |
|---|---|---|
| **Lambda Authorizer** | ✅ TOKEN + REQUEST | ✅ REQUEST only |
| **Cognito Authorizer** | ✅ Yes | ✅ JWT Authorizer |
| **IAM Authorization** | ✅ Yes | ✅ Yes |
| **API Keys** | ✅ Yes | ❌ No |
| **Resource Policy** | ✅ Yes | ❌ No |
| **WAF** | ✅ Yes | ❌ No |

> ⚠️ **Exam critical:** HTTP APIs do NOT support resource policies or WAF. If a scenario requires IP-based restriction or WAF on an HTTP API → use REST API or put CloudFront + WAF in front.

## 1.5 Security & Compliance Angles

### Common Misconfigurations

| Misconfiguration | Risk | Fix |
|---|---|---|
| API Key as only auth | Anyone with key = full access | Add IAM or Lambda Authorizer |
| Authorizer cache too long | Revoked tokens still work | Reduce TTL or disable cache |
| No request validation | Malformed data hits backend | Enable request validation with model |
| CORS Allow-Origin: * | Cross-site request forgery risk | Specify exact allowed origins |
| No throttling configured | DoS via API flooding | Set rate + burst limits per stage/method |
| Execution logs disabled | Cannot debug or audit | Enable CloudWatch logging |
| Private API without resource policy | VPC endpoint alone insufficient | Always add resource policy |
| mTLS truststore in public S3 | Truststore exposed | Use private S3 bucket |
| No WAF on public API | OWASP attacks succeed | Attach WAF Web ACL |

## 1.6 Integration Patterns

### Pattern 1: Public API with Cognito
```
Mobile App
    │ JWT token in Authorization header
    ▼
API Gateway (REST)
    │ Cognito User Pool Authorizer validates JWT
    ▼
Lambda Function
    │ Reads user context from token
    ▼
DynamoDB (user-specific data)
```

### Pattern 2: Internal API (Private)
```
ECS Service (in VPC)
    │ HTTP call via VPC Endpoint
    ▼
VPC Interface Endpoint (execute-api)
    │ Private network path
    ▼
API Gateway (Private REST API)
    │ Resource policy: allow only this VPC
    │ IAM auth: SigV4 signed request
    ▼
Lambda Function
```

### Pattern 3: B2B API with mTLS
```
Partner System
    │ Client certificate presented
    ▼
API Gateway (custom domain + mTLS)
    │ Validates cert against truststore in S3
    │ Lambda Authorizer for additional checks
    ▼
Backend Service
```

### Pattern 4: Public API with Full Security Stack
```
Internet
    │
    ▼
Route 53 → CloudFront
    │ WAF Web ACL (OWASP rules + rate limiting)
    │ ACM certificate (us-east-1)
    ▼
API Gateway (Edge-Optimized)
    │ Lambda Authorizer (custom token validation)
    │ Request validation (JSON schema)
    │ Throttling (per method)
    │ CloudWatch logging
    ▼
Lambda → DynamoDB
```

### Pattern 5: Microservices with IAM Auth
```
Service A (has IAM role)
    │ Signs request with SigV4
    ▼
API Gateway
    │ IAM Authorization
    │ Resource policy: allow only Service A role
    ▼
Service B (Lambda)
```

### Question 1
**A company has a REST API in API Gateway used by their mobile app. Users authenticate via Cognito User Pool. After a user is banned, they can still call the API for up to 5 minutes. What is the cause and fix?**

A) Cognito takes 5 minutes to propagate user bans across regions
B) API Gateway Cognito Authorizer has a 300-second authorization cache TTL
C) The JWT token is valid for 5 minutes after user is banned
D) Lambda backend caches user status for 5 minutes

**Answer: B**

**Explanation:**
- API Gateway Cognito Authorizer caches authorization results by token
- Default cache TTL is 300 seconds (5 minutes)
- During cache period, banned user's old valid token still returns cached ALLOW
- Fix: reduce authorizer cache TTL to 0 (disables caching — higher latency)
- Better fix: combine with short token validity + GlobalSignOut on ban
- JWT token may still be valid (up to 24hr) but authorizer cache is the immediate cause
- Lambda backend caching is separate — not the primary cause here

---

### Question 2
**A security team needs to restrict a public REST API so that only requests from their corporate IP range (203.0.113.0/24) are allowed. All other requests must be denied. Which is the CORRECT implementation?**

A) Security Group on API Gateway allowing only corporate IP
B) WAF IP set allowing corporate IP attached to API Gateway
C) API Gateway Resource Policy with IP condition Allow for corporate IP and implicit deny for others
D) NACLs blocking all non-corporate IPs at subnet level

**Answer: C**

**Explanation:**
- API Gateway Resource Policy with IP condition is the native solution
- Allow statement with `aws:SourceIp` condition for 203.0.113.0/24
- All other IPs implicitly denied (no matching allow statement)
- API Gateway does not have Security Groups — it's a managed service
- WAF IP set works but is an additional layer — Resource Policy is simpler and native
- NACLs cannot be applied to API Gateway — it's not in a VPC subnet
- Resource Policy is the exam-correct answer for IP-based API restriction

---

### Question 3
**An API Gateway Lambda Authorizer is configured with a 300-second cache TTL. The authorizer uses the Authorization header as the cache key. Two different users with different tokens call the same API method within 5 seconds. What happens?**

A) Both users share the same cached authorization result
B) Each user's token creates a separate cache entry — both get their own authorization result
C) Second user's request is rejected because cache is busy
D) Cache TTL resets to 600 seconds after second request

**Answer: B**

**Explanation:**
- Lambda Authorizer cache key is the **token value** by default
- Each unique token = separate cache entry
- User A's token cached separately from User B's token
- Both users get correct authorization results from their own cache entries
- Cache collision only occurs if two users somehow have the same token (impossible with JWTs)
- Cache TTL doesn't reset on subsequent requests — it's per-entry from first invocation
- This is the correct behavior — caching is per-token, not per-resource

### Question 4
**A company wants to expose their internal microservice API to a partner company in a different AWS account. The API should not be accessible from the internet. Which solution achieves this?**

A) Public REST API with IAM authorization restricted to partner account
B) Private REST API + VPC endpoint + resource policy allowing partner account
C) HTTP API with JWT authorizer and partner account IP allowlist
D) REST API with API key shared with partner company

**Answer: B**

**Explanation:**
- Private REST API ensures no internet access — only reachable via VPC endpoint
- Partner connects via VPC peering or AWS Transit Gateway to reach the VPC endpoint
- Resource policy explicitly allows partner account's principal
- Public REST API with IAM still exposed to internet — violates "not accessible from internet"
- HTTP API does not support resource policies — cannot restrict to specific account
- API keys are not secure for cross-account access — can be intercepted
- Private API + VPC endpoint + resource policy is the complete, correct solution

### Question 8
**An API Gateway stage has throttling set to 1000 RPS with a burst of 2000. During a flash sale, traffic spikes to 3000 RPS for 10 seconds then returns to 500 RPS. What happens during the spike?**

A) All 3000 RPS are blocked — burst only allows up to 2000 simultaneous connections
B) First 2000 requests served from burst bucket, remaining 1000 throttled with 429, then rate recovers at 1000/second
C) All 3000 RPS blocked until traffic returns to under 1000 RPS
D) API Gateway automatically scales to handle 3000 RPS with no throttling

**Answer: B**

**Explanation:**
- Burst bucket starts full at 2000 tokens
- First 2000 requests consume burst bucket instantly
- Remaining 1000 requests in that second → throttled (429)
- Bucket refills at 1000 tokens/second (the rate limit)
- Next second: 1000 new tokens available → 1000 requests served, rest throttled
- After spike ends at 500 RPS: 500 below rate limit → bucket refills over time
- API Gateway does NOT auto-scale beyond configured limits
- This is the token bucket algorithm in action — exam frequently tests this

### Question 10
**A security engineer notices that the API Gateway execution logs show full request bodies including credit card numbers. This violates PCI DSS. What should they configure to prevent sensitive data appearing in logs?**

### Question 11
**A company uses HTTP API in API Gateway with a JWT authorizer pointing to their Cognito User Pool. They want to add IP-based restrictions so only corporate IPs can call the API. What is the BEST approach?**

### Question 12
**An API Gateway REST API has both a Cognito Authorizer AND a resource policy. A request arrives with a valid Cognito JWT token but from an IP blocked by the resource policy. What happens?**

B) Request blocked — resource policy evaluated first, denies before authorizer check
C) Request allowed — valid JWT overrides resource policy restrictions
D) Both checks run independently — result depends on which returns first

**Answer: B**

- 1) Resource policy (network-level check) → evaluated FIRST
- 2) Authorizer (authentication check) → evaluated SECOND
- Resource policy DENY stops the request before Cognito authorizer is even invoked
- This is efficient — no Lambda invocation or Cognito check wasted on blocked IPs
- Valid JWT cannot override resource policy restrictions
- Checks are sequential not parallel — order matters
- This is the correct API Gateway request evaluation order — frequently tested

B) IAM role on Lambda restricting invocation to API Gateway
C) VPC endpoint policy restricting Lambda invocations
D) API Gateway resource policy restricting Lambda access

**Answer: A**

### Question 18
**A developer configures CORS on a REST API with `Access-Control-Allow-Origin: *` and enables API Gateway to pass credentials (`Access-Control-Allow-Credentials: true`). A security auditor flags this as critical. Why?**

A) Wildcard origin with credentials is blocked by browsers — configuration has no effect
B) This combination allows any website to make credentialed cross-origin requests to the API — CSRF risk
C) Wildcard origin requires WAF to be enabled — missing security layer
D) This configuration causes API Gateway to ignore all authentication

**Answer: B**

**Explanation:**
- `Allow-Origin: *` + `Allow-Credentials: true` is a dangerous combination
- Browsers normally block `*` with credentials — but some configurations bypass this
- More importantly: this signals intent to allow any origin with credentials
- A malicious website can make credentialed requests (cookies, auth headers) to your API
- This enables Cross-Site Request Forgery (CSRF) attacks
- Fix: specify exact allowed origins instead of wildcard
- `Access-Control-Allow-Origin: https://app.company.com`
- Browsers actually DO block `*` + credentials — but misconfigured apps may not check
- Security auditor is correct to flag — principle of least privilege applies to CORS

### Question 20
**A company uses API Gateway with a Lambda authorizer. The security team discovers that if the Lambda authorizer throws an unhandled exception, API Gateway returns 200 OK and lets the request through. What configuration is causing this behavior?**

A) Lambda authorizer is configured with "effect: Allow" as default behavior on error
B) The authorizer is configured with "On error" setting as ALLOW instead of DENY (default)
C) Lambda timeout causes API Gateway to fail open — should increase Lambda timeout
D) Unhandled exceptions always return 200 — use try/catch in Lambda

**Answer: B**

**Explanation:**
- Lambda Authorizer has an "On error" configuration setting
- Default behavior: on error → return 401 Unauthorized (fail closed — secure)
- Misconfigured behavior: on error → ALLOW (fail open — insecure)
- Fail open means any error in authorizer logic = all requests allowed = security bypass
- Always configure authorizers to fail CLOSED (deny on error)
- Lambda timeout also causes error — increasing timeout helps but fail-closed config is essential
- try/catch in Lambda is good practice but doesn't fix the API GW configuration
- This is a critical security misconfiguration — exam tests "fail open vs fail closed"

## 2.2 Common Exam Traps & Distractors

### Trap 1: HTTP API Supports Resource Policies
> ❌ **Wrong:** "Add resource policy to HTTP API for IP restriction"
> ✅ **Right:** HTTP APIs do NOT support resource policies — use CloudFront + WAF

### Trap 2: API Keys Provide Security
> ❌ **Wrong:** "API key protects API from unauthorized access"
> ✅ **Right:** API keys are for identification/throttling ONLY — not security

### Trap 3: Cognito Authorizer Evaluated Before Resource Policy
> ❌ **Wrong:** "Valid JWT overrides resource policy denial"
> ✅ **Right:** Resource policy evaluated FIRST — denies before authorizer runs

### Trap 4: Lambda Authorizer Blocks on Exception by Default
> ❌ **Wrong:** "Lambda authorizer exception automatically blocks request"
> ✅ **Right:** Depends on configuration — default is 401 but can be misconfigured to ALLOW

### Trap 5: mTLS Supported on Edge-Optimized Endpoints
> ❌ **Wrong:** "Configure mTLS on edge-optimized API Gateway endpoint"
> ✅ **Right:** mTLS only on **Regional and Private** endpoints — not edge-optimized

### Trap 6: Private API Only Needs VPC Endpoint
> ❌ **Wrong:** "Create VPC endpoint — private API is accessible"
> ✅ **Right:** Private API needs VPC endpoint AND resource policy — both required

### Trap 7: Lambda Authorizer Returns Allow/Deny Only
> ❌ **Wrong:** "Lambda authorizer returns simple allow or deny boolean"
> ✅ **Right:** Returns full **IAM policy document** + optional context object

### Trap 8: 429 Means Authentication Failed
> ❌ **Wrong:** "429 response from API Gateway = invalid credentials"
> ✅ **Right:** 429 = **Too Many Requests** (throttled). 401 = unauthorized, 403 = forbidden

### Trap 9: Request Validation Invokes Lambda
> ❌ **Wrong:** "Request validation Lambda checks body before backend Lambda"
> ✅ **Right:** Request validation is native API Gateway — backend Lambda NOT invoked on invalid request

### Trap 10: IAM Auth Works Without Resource Policy Cross-Account
> ❌ **Wrong:** "IAM policy in Account B is enough to call Account A's API"
> ✅ **Right:** Cross-account IAM auth needs IAM policy (Account B) AND resource policy (Account A)

## 2.4 Elimination Strategies

### Strategy 1: HTTP API Limitations
**HTTP API + resource policy/WAF/API keys/request validation** → all unsupported → use REST API or add CloudFront

### Strategy 2: Evaluation Order
**Valid JWT but blocked IP** → resource policy evaluated FIRST → request blocked before authorizer

### Strategy 3: Cross-Account = Both Sides
**Cross-account API call** → always need IAM policy (caller) AND resource policy (API) — both required

### Strategy 4: Private API = Two Requirements
**Private API not reachable** → check BOTH VPC endpoint AND resource policy — one alone is insufficient

### Strategy 5: 429 vs 401 vs 403
**Too many requests** → 429. **Bad/missing token** → 401. **Denied by policy** → 403

### Strategy 6: mTLS Endpoint Type
**mTLS requirement** → eliminate edge-optimized → Regional or Private only

### Strategy 7: Fail Closed Security
**Authorizer error behavior** → always fail CLOSED (401) — fail open = critical vulnerability

### Strategy 8: API Keys = Throttling Not Security
**API key as security control** → eliminate → API keys are identification only, not authentication

### Strategy 9: Context Object for Data Passing
**Pass user data from authorizer to backend** → context object in authorizer response

### Strategy 10: Request Validation = No Lambda Invocation
**Invalid request + request validation** → API Gateway returns 400, backend Lambda NOT invoked
