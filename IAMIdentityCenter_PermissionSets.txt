## 1. IAM Identity Center Architecture

### What is IAM Identity Center?
Previously called **AWS SSO**, IAM Identity Center is AWS's **centralized access management service** that lets you manage SSO access to **multiple AWS accounts and applications** from one place.

### Why it matters for the exam?
- Replaces the old pattern of creating **IAM users in every account**
- Works natively with **AWS Organizations**
- Heavily tested in **identity federation** and **multi-account access** scenarios

### High-Level Architecture
```
Identity Source                    IAM Identity Center              AWS Targets
─────────────────                  ───────────────────              ───────────
Active Directory    ──SCIM/SAML──▶  User/Group Sync   ──assigns──▶  AWS Account A
External IdP        ──SAML 2.0───▶  Permission Sets   ──assigns──▶  AWS Account B
Built-in Directory  ────────────▶  Account Assignment ──assigns──▶  AWS Account C
                                                       ──assigns──▶  SaaS Apps
```

### Core Components

| Component | Description |
|---|---|
| **Identity Source** | Where users/groups come from (AD, IdP, or built-in) |
| **Permission Set** | Template defining what access a user gets in an account |
| **Account Assignment** | Links a user/group + permission set + AWS account |
| **AWS Access Portal** | The SSO login URL users access (`https://xxxx.awsapps.com/start`) |
| **SCIM** | Protocol for automatic user provisioning/deprovisioning |

## 2. Identity Sources (Deep Dive)

### Option 1: Built-in Identity Directory
- IAM Identity Center manages users/groups **natively**
- Good for **smaller organizations** or quick setup
- Users created and managed directly in IAM Identity Center console
- **No SCIM needed** — users exist natively
- MFA supported natively

### Option 2: Active Directory (Most Common Enterprise Pattern)
Two sub-options:

**A) AWS Managed Microsoft AD (via AWS Directory Service)**
```
On-premises AD ──AD Trust──▶ AWS Managed Microsoft AD ──▶ IAM Identity Center
```
- Two-way trust between on-prem and AWS Managed AD
- Users authenticate against on-prem AD
- Groups synced to IAM Identity Center

**B) AD Connector**
```
On-premises AD ◀──proxy──── AD Connector ──▶ IAM Identity Center
```
- AD Connector acts as a **proxy** — no data stored in AWS
- Authentication passes through to on-premises AD
- Lower cost but adds latency

### Option 3: External Identity Provider (SAML 2.0)
- Works with **Okta, Azure AD, Ping Identity, OneLogin** etc.
- SAML 2.0 for authentication
- SCIM for automatic **user provisioning**
- IAM Identity Center acts as **Service Provider (SP)**
- External IdP acts as **Identity Provider (IdP)**

```
User ──login──▶ Okta (IdP) ──SAML Assertion──▶ IAM Identity Center (SP) ──▶ AWS Console
```

### Identity Source Comparison

| Feature | Built-in | AWS Managed AD | External IdP |
|---|---|---|---|
| **User management** | IAM Identity Center | Active Directory | External IdP |
| **MFA** | Native | AD MFA | IdP MFA |
| **SCIM provisioning** | Not needed | Not needed | ✅ Recommended |
| **Best for** | Small orgs | Enterprise AD | Okta/Azure AD shops |
| **On-prem integration** | ❌ | ✅ | ✅ |

> ⚠️ Exam tip: If the question mentions **Okta or Azure AD** → External IdP + SAML 2.0 + SCIM. If it mentions **corporate Active Directory** → AWS Managed AD or AD Connector.

## 3. Permission Sets (Deep Dive)

### What is a Permission Set?
A **Permission Set** is a **template** that defines the level of access users/groups get when they log into a specific AWS account via IAM Identity Center.

Think of it as: **"What can this user do once they land in Account X?"**

### How Permission Sets Work
```
Permission Set: "SecurityAuditor"
        │
        ├── Managed Policies: SecurityAudit (AWS managed)
        ├── Inline Policy: Custom deny sensitive actions
        ├── Session Duration: 4 hours
        └── Relay State: Opens directly to Security Hub
```

When assigned → IAM Identity Center **creates a Role** in the target account automatically.

### Permission Set Components

| Component | Description |
|---|---|
| **AWS Managed Policies** | Attach standard policies like ReadOnlyAccess, AdministratorAccess |
| **Customer Managed Policies** | Attach your own custom IAM policies |
| **Inline Policy** | Embed a policy directly in the permission set |
| **Permissions Boundary** | Limit maximum permissions the role can have |
| **Session Duration** | How long the SSO session lasts (1hr–12hrs) |
| **Relay State** | URL the user lands on after login (e.g., GuardDuty console) |

### Common Permission Sets Pattern (Enterprise)

```
Permission Sets:
├── AdministratorAccess    → For cloud admins (break-glass)
├── PowerUserAccess        → For developers
├── SecurityAuditAccess    → For security team (ReadOnly + Security services)
├── BillingAccess          → For finance team
├── ReadOnlyAccess         → For auditors
└── NetworkAdminAccess     → For network team
```

### Permission Set → IAM Role Mapping
When you assign a Permission Set to an account, IAM Identity Center:
1. Creates an IAM Role in that account automatically
2. Role name format: `AWSReservedSSO_<PermissionSetName>_<RandomSuffix>`
3. Trust policy allows IAM Identity Center to assume it
4. **You don't manage this role manually** — Identity Center owns it

> ⚠️ Exam tip: If a Permission Set is updated, you must **re-provision** it to all accounts for changes to take effect.

## 4. ABAC with IAM Identity Center

### What is ABAC?
**Attribute-Based Access Control** — grant permissions based on **tags/attributes** rather than explicit role assignments.

### How it works with IAM Identity Center
IAM Identity Center can pass **user attributes** as **session tags** when a user assumes a role.

```
User in Identity Center:
  Attribute: Department = "Finance"
  Attribute: CostCenter = "CC-001"
        │
        ▼
Session Tags passed to AWS role:
  aws:PrincipalTag/Department = Finance
  aws:PrincipalTag/CostCenter = CC-001
        │
        ▼
IAM Policy uses tags to control access:
  Allow s3:GetObject if
  s3:ResourceTag/Department = aws:PrincipalTag/Department
```

### ABAC IAM Policy Example
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ABACFinanceS3Access",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::company-data/*",
      "Condition": {
        "StringEquals": {
          "s3:ExistingObjectTag/Department": "${aws:PrincipalTag/Department}"
        }
      }
    }
  ]
}
```

### ABAC Benefits
- **Scalable** — no need to create new roles for every team/project
- **Dynamic** — access follows the user's attributes automatically
- **Reduced role sprawl** — fewer permission sets needed

> ⚠️ Exam tip: ABAC requires **"All Features"** enabled in AWS Organizations AND attributes configured in IAM Identity Center.

## 5. Multi-Account Access Patterns

### Pattern 1: Flat Assignment
Direct assignment of users/groups to accounts:
```
Group: SecurityTeam
    ├── Account A → Permission Set: SecurityAudit
    ├── Account B → Permission Set: SecurityAudit
    └── Account C → Permission Set: SecurityAudit
```
Simple but doesn't scale well.

---

### Pattern 2: OU-Based Assignment (Recommended)
Assign at OU level — automatically applies to all accounts in OU:
```
Group: Developers → OU: Production → Permission Set: PowerUser
```
When new accounts are added to the OU, access is **automatically provisioned**.

---

### Pattern 3: Delegated Administration
- By default, only the **management account** manages IAM Identity Center
- You can **delegate** administration to a member account (e.g., a dedicated Security account)
- Best practice: use a **dedicated Security Tooling account** as delegated admin

```
Management Account
        │
        └── Delegates IAM Identity Center admin to ──▶ Security Account
                                                              │
                                                    Manages SSO for all
                                                    member accounts
```

---

### Pattern 4: Cross-Account Role Chaining with SSO
```
User logs in via SSO
        │
        ▼
Assumes Role in Security Account (via Permission Set)
        │
        ▼
From Security Account, assumes cross-account role in Prod Account
        │
        ▼
Performs privileged action in Prod
```
Used for **break-glass** or elevated access scenarios.

## 6. IAM Identity Center vs IAM Federation (Exam Comparison)

| Feature | IAM Identity Center | IAM Federation (Direct) |
|---|---|---|
| **Multi-account** | ✅ Native | ❌ Complex setup per account |
| **Centralized management** | ✅ Yes | ❌ Per account |
| **Permission Sets** | ✅ Yes | ❌ Manual roles |
| **SCIM provisioning** | ✅ Yes | ❌ No |
| **Best for** | Organizations with multiple accounts | Single account federation |
| **AWS recommended** | ✅ Yes (preferred) | ❌ Legacy approach |

> ⚠️ Exam tip: Any scenario involving **multiple AWS accounts + SSO** → IAM Identity Center is almost always the right answer over direct IAM federation.

```bash
# Step 2: Check IAM Identity Center instances

echo "[2] Listing IAM Identity Center instances..."
aws sso-admin list-instances \
  --query 'Instances[*].{InstanceArn:InstanceArn, IdentityStoreId:IdentityStoreId}' \
  --output table

  --query 'Instances[0].InstanceArn' \

# Step 3: List existing Permission Sets
echo ""
echo "[3] Listing Permission Sets..."

  --query 'PermissionSets' \
  --output table 2>/dev/null || echo "No permission sets found or insufficient permissions"

# Step 4: List users in Identity Store
echo ""
echo "[4] Listing users in Identity Store..."
aws identitystore list-users \
  --identity-store-id $IDENTITY_STORE_ID \
  --query 'Users[*].{UserId:UserId, UserName:UserName, DisplayName:DisplayName}' \
  --output table 2>/dev/null || echo "No users found or insufficient permissions"

echo ""
echo "[5] Listing groups in Identity Store..."
aws identitystore list-groups \
  --identity-store-id $IDENTITY_STORE_ID \
  --query 'Groups[*].{GroupId:GroupId, DisplayName:DisplayName}' \
  --output table 2>/dev/null || echo "No groups found or insufficient permissions"

# Step 6: List account assignments
echo ""
echo "[6] Checking account assignments..."
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

aws sso-admin list-account-assignments \
  --instance-arn $INSTANCE_ARN \
  --account-id $ACCOUNT_ID \
  --permission-set-arn $(aws sso-admin list-permission-sets \
    --instance-arn $INSTANCE_ARN \
    --query 'PermissionSets[0]' \
    --output text 2>/dev/null) \
  --output table 2>/dev/null || echo "No assignments found or insufficient permissions"

# Step 7: Summary
echo ""
echo "============================================"
echo "Lab 97 Summary"
echo "--------------------------------------------"
echo "IAM Identity Center Key Concepts:"
echo "  - Instance ARN: Unique identifier for your SSO instance"
echo "  - Identity Store: Holds users and groups"
echo "  - Permission Sets: Define access templates"
echo "  - Account Assignments: Link users+permsets to accounts"
echo "============================================"
```

## 🧠 Exam-Focus Q&A

**Q1: A company uses Okta as their IdP. They want SSO access to 10 AWS accounts. What's the best approach?**
> ✅ IAM Identity Center with External IdP (SAML 2.0) + SCIM provisioning. Create Permission Sets and assign groups to accounts.

**Q2: A Permission Set was updated but changes aren't reflecting in member accounts. Why?**
> ✅ Permission Sets must be **re-provisioned** after updates. Go to IAM Identity Center → Permission Sets → Re-provision.

**Q3: What protocol does IAM Identity Center use for automatic user provisioning from an external IdP?**
> ✅ **SCIM (System for Cross-domain Identity Management)**

**Q4: A company wants to give finance team access only to finance-tagged S3 buckets without creating separate roles per team. What solution scales best?**
> ✅ **ABAC** — configure user attributes in IAM Identity Center, pass as session tags, use tag-based conditions in IAM policies.

**Q5: Where are the IAM roles created when a Permission Set is assigned to an account?**
> ✅ IAM Identity Center automatically creates roles **in the target member account** with the format `AWSReservedSSO_<PermissionSetName>_<suffix>`

## 1.1 Service Overview & Purpose

### What is IAM Identity Center?
AWS IAM Identity Center (formerly AWS Single Sign-On / AWS SSO) is AWS's **centralized workforce identity and access management service**. It provides a **single place** to manage user identities and their access across **multiple AWS accounts, AWS applications, and third-party SaaS applications**.

Instead of creating IAM users in every AWS account (which was the old, painful pattern), IAM Identity Center lets you:
- Maintain users/groups in **one place**
- Define **what access** they get via Permission Sets
- Assign that access across **hundreds of accounts** from a single console
- Let users log in **once** and access everything they're entitled to

### Why Does It Exist? (Problem It Solves)
Before IAM Identity Center, enterprises with multiple AWS accounts faced:

```
Problem: 50 AWS accounts, 200 employees
Old approach:
  ├── Create 200 IAM users in Account 1
  ├── Create 200 IAM users in Account 2
  ├── Create 200 IAM users in Account 3
  ├── ... repeat 50 times
  ├── Manage password resets in every account
  ├── Manage MFA in every account
  ├── Audit access in every account separately
  └── When someone leaves → deactivate in 50 accounts
```

This was:
- **Unscalable** — O(users × accounts) complexity
- **Insecure** — easy to miss deprovisioning a leaver
- **Unauditable** — no central view of who has access to what
- **No SSO** — users needed separate credentials per account

IAM Identity Center solves ALL of this with a centralized model.

### When to Use IAM Identity Center vs Alternatives

| Scenario | Recommended Approach |
|---|---|
| Multiple AWS accounts, workforce users | ✅ IAM Identity Center |
| Single AWS account, small team | IAM users (acceptable) |
| Machine-to-machine access | IAM Roles (not Identity Center) |
| External customers logging into your app | Amazon Cognito (not Identity Center) |
| B2B federation for partners | IAM Identity Center or direct SAML |
| Existing Okta/Azure AD shop | IAM Identity Center + External IdP |
| On-premises AD, enterprise | IAM Identity Center + AWS Managed AD |

> ⚠️ **Critical exam distinction:** IAM Identity Center = **workforce identity** (your employees). Amazon Cognito = **customer identity** (your app's end users). This distinction appears in almost every exam scenario involving identity.

### Exam Weight & Importance
- Appears in **Domain 2: Identity & Access Management** (16% of exam)
- Frequently tested alongside AWS Organizations, cross-account roles, and federation
- Expect **3–5 questions** directly or indirectly involving IAM Identity Center
- Often the **correct answer** when a scenario involves multi-account SSO

### Data Flow — User Login to Console Access
```
Step 1: User visits https://xxxx.awsapps.com/start
Step 2: IAM Identity Center checks identity source
Step 3: User authenticates (password + MFA)
Step 4: IAM Identity Center checks account assignments
Step 5: User sees list of accounts + roles they can access
Step 6: User clicks account → IAM Identity Center issues
        temporary credentials via STS AssumeRoleWithSAML
Step 7: User lands in AWS Console for that account
Step 8: Session expires per Permission Set session duration
```

### Integration with AWS Organizations
IAM Identity Center is **deeply integrated** with AWS Organizations:
- Enabled at the **Organization level** (management account)
- Can assign access at the **OU level** — auto-applies to all accounts in OU
- New accounts added to OU **automatically inherit** access assignments
- Works with **delegated administration** — can delegate to a member account
- Supports **all AWS Organizations features** when "All Features" is enabled

## 1.3 Deep Dive — Every Sub-Topic

### A. Identity Sources (Full Detail)

#### Built-in Identity Directory
- IAM Identity Center **natively manages** users and groups
- Users stored in **IAM Identity Center's own identity store**
- Administrators create/manage users directly in the console or via API
- Supports **MFA natively**: TOTP apps, WebAuthn/FIDO2 security keys
- Supports **self-service MFA enrollment** for users
- Best for: small organizations, quick PoC, no existing IdP

**User attributes available:**
```
├── Username (login identifier)
├── Email address
├── First name / Last name
├── Display name
├── Custom attributes (up to 50)
└── Department, Title, etc.
```

---

#### AWS Managed Microsoft AD Integration

**Full flow:**
```
On-premises AD
      │
      │ (AD Trust — two-way)
      ▼
AWS Managed Microsoft AD
(in AWS Directory Service)
      │
      │ (native integration)
      ▼
IAM Identity Center
      │
      │ (syncs users/groups)
      ▼
Identity Store
```

**Key details:**
- Users authenticate against **on-premises AD credentials**
- Groups from AD are **synced** to IAM Identity Center
- No need for SCIM — sync is native
- Requires **AWS Directory Service** to be set up first
- Supports **Kerberos authentication**
- AD password policies apply
- Multi-region: Managed AD can be replicated across regions

**AD Connector alternative:**
```
On-premises AD
      ▲
      │ (proxy — no data stored in AWS)
AD Connector
      │
      ▼
IAM Identity Center
```
- AD Connector is a **directory gateway** — proxies all auth requests to on-prem AD
- **No user data stored in AWS** — good for data residency requirements
- Lower cost than Managed AD
- Higher latency (round-trip to on-premises for every auth)
- Does **not** support MFA natively (must use RADIUS on-prem)
- Does **not** support trust relationships

---

#### External IdP (SAML 2.0 + SCIM)

**Authentication flow (SAML 2.0):**
```
User ──▶ AWS Access Portal
              │
              │ Redirects to IdP
              ▼
         Okta / Azure AD
              │
              │ User authenticates (MFA here)
              │
              │ SAML Assertion returned
              ▼
         IAM Identity Center validates assertion
              │
              │ Issues temporary credentials
              ▼
         User accesses AWS Console
```

**Provisioning flow (SCIM):**
```
Okta / Azure AD
      │
      │ SCIM API calls (automatic)
      │ ├── Create user
      │ ├── Update user attributes
      │ ├── Deactivate user (when offboarded)
      │ └── Sync group memberships
      ▼
IAM Identity Center Identity Store
```

**SCIM details:**
- SCIM = System for Cross-domain Identity Management (RFC 7642/7643/7644)
- Automates user **lifecycle management**
- When a user is deactivated in Okta → **automatically deactivated** in IAM Identity Center within minutes
- Requires generating a **SCIM endpoint URL** and **access token** in IAM Identity Center
- Token has **no expiry** but should be rotated periodically

**Supported external IdPs (exam commonly mentions):**
- Microsoft Azure Active Directory (Entra ID)
- Okta
- Ping Identity / PingFederate
- OneLogin
- JumpCloud
- Any SAML 2.0 compliant IdP

> ⚠️ **Exam gotcha:** With external IdP, MFA is handled **by the IdP**, not by IAM Identity Center. Don't configure MFA in both places — it causes double MFA prompts.

> ⚠️ **Exam gotcha:** SCIM is for **provisioning** (user/group sync). SAML is for **authentication**. They serve different purposes and both are typically needed together.

### B. Permission Sets (Full Detail)

#### What Happens When You Create a Permission Set
```
1. You define a Permission Set in IAM Identity Center console
2. You assign it: Group X → Permission Set Y → Account Z
3. IAM Identity Center automatically:
   ├── Creates an IAM Role in Account Z
   │   Name: AWSReservedSSO_<PermissionSetName>_<RandomHex>
   │   Trust Policy: Trusts IAM Identity Center SAML endpoint
   └── Attaches your defined policies to that role
4. When user logs in → STS AssumeRoleWithSAML → gets temp credentials
```

#### Permission Set Components (Full)

**1. AWS Managed Policies**
- Standard AWS-managed policies like:
  - `AdministratorAccess`
  - `ReadOnlyAccess`
  - `SecurityAudit`
  - `PowerUserAccess`
  - `ViewOnlyAccess`
- Up to **10 AWS managed policies** per permission set

**2. Customer Managed Policies**
- Your own custom IAM policies stored in each member account
- IAM Identity Center references them **by name** (not ARN)
- The policy must exist **in every account** where the permission set is assigned
- Useful for organization-specific custom access patterns

**3. Inline Policy**
- JSON policy embedded directly in the permission set
- Max size: **10,240 characters**
- Good for small customizations or additions
- Cannot be reused across permission sets

**4. Permissions Boundary**
- Sets the **maximum permissions** the role can have
- Can be AWS managed or customer managed policy
- Works same as IAM permissions boundary
- Useful for restricting what developers can do even with broad permission sets

**5. Session Duration**
- Minimum: **1 hour**
- Maximum: **12 hours**
- Default: **1 hour**
- Controls how long the SSO session lasts before re-authentication required
- For privileged access: keep short (1hr)
- For read-only audit access: can be longer (4–8hr)

**6. Relay State**
- URL the user is redirected to **after successful login**
- Example: Direct security team straight to Security Hub:
  ```
  https://console.aws.amazon.com/securityhub/home
  ```
- Useful for role-specific landing pages

#### Permission Set Provisioning
```
Create/Update Permission Set
          │
          ▼
Must PROVISION to accounts
          │
    ┌─────┴─────┐
    │           │
    ▼           ▼
Account A    Account B
IAM Role     IAM Role
updated      updated
```

> ⚠️ **Critical exam point:** If you update a permission set (e.g., add a new policy), the change **does NOT automatically apply** to assigned accounts. You must explicitly **re-provision** the permission set. This is a common exam trap and real-world gotcha.

**Re-provisioning methods:**
- Console: Permission Sets → Select → Re-provision
- CLI:
```bash
aws sso-admin provision-permission-set \
  --instance-arn $INSTANCE_ARN \
  --permission-set-arn $PERMISSION_SET_ARN \
  --target-type ALL_PROVISIONED_ACCOUNTS
```

### C. ABAC with IAM Identity Center (Full Detail)

#### Concept
Instead of creating **separate permission sets per team**, ABAC uses **user attributes** to dynamically control access.

#### Configuration Steps
```
Step 1: Enable ABAC in IAM Identity Center
        Settings → Attributes for access control → Enable

Step 2: Define attribute mappings
        Map Identity Center attributes to session tag keys
        Example:
          ${path:enterprise.department} → Department
          ${path:enterprise.costCenter} → CostCenter

Step 3: Ensure attributes exist in identity source
        (AD attributes, IdP attributes, or built-in directory attributes)

Step 4: Write IAM policies using aws:PrincipalTag conditions
        in Permission Sets

Step 5: Tag AWS resources with matching tag keys
```

#### Full ABAC Policy Example
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAccessToTeamResources",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::company-data/*",
      "Condition": {
        "StringEquals": {
          "s3:ExistingObjectTag/Department": "${aws:PrincipalTag/Department}",
          "s3:ExistingObjectTag/CostCenter": "${aws:PrincipalTag/CostCenter}"
        }
      }
    },
    {
      "Sid": "AllowEC2ByTeamTag",
      "Effect": "Allow",
      "Action": [
        "ec2:StartInstances",
        "ec2:StopInstances"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "ec2:ResourceTag/Team": "${aws:PrincipalTag/Department}"
        }
      }
    }
  ]
}
```

#### ABAC Attribute Sources
| Identity Source | Attribute Source |
|---|---|
| Built-in Directory | Custom attributes defined in Identity Center |
| AWS Managed AD | AD user attributes (department, title, etc.) |
| External IdP | SAML assertion attributes mapped via SCIM |

#### ABAC Benefits vs RBAC Comparison
| Aspect | RBAC (Role-Based) | ABAC (Attribute-Based) |
|---|---|---|
| **Scalability** | Poor (role explosion) | Excellent |
| **Granularity** | Coarse | Fine-grained |
| **Maintenance** | High | Low (attributes drive access) |
| **New team onboarding** | New permission set needed | Just set attributes |
| **Complexity** | Low | Higher (policy design) |
| **Exam preference** | Legacy pattern | Modern, AWS recommended |

### D. Multi-Account Access Patterns (Full Detail)

#### Pattern 1: Direct Account Assignment
```
User/Group → Permission Set → Specific Account
```
- Explicit, granular control
- Doesn't scale beyond ~20 accounts
- Must manually assign each new account

#### Pattern 2: OU-Level Assignment
```
User/Group → Permission Set → OU
                                └── All accounts in OU inherit assignment
```
- Scales automatically
- New accounts added to OU get access provisioned automatically
- Best practice for large organizations
- Can combine OU-level + account-level for exceptions

#### Pattern 3: Delegated Administration
- By default: only **management account** can manage IAM Identity Center
- Delegated admin: assign a **member account** as IAM Identity Center administrator
- Best practice: use dedicated **Security Tooling account**

```bash
# Delegate IAM Identity Center administration
aws organizations register-delegated-administrator \
  --account-id 123456789012 \
  --service-principal sso.amazonaws.com
```

Benefits:
- Management account stays clean (no workloads)
- Security team manages access from their own account
- Follows AWS multi-account best practices

#### Pattern 4: Break-Glass Access Pattern
```
Normal access:     User → PowerUser Permission Set → Dev accounts
Break-glass:       User → AdministratorAccess Permission Set → Prod account
                         (requires approval, short session, heavily logged)
```
- Short session duration (1 hour)
- CloudTrail alerts on assumption
- SNS notification to security team
- Reviewed post-incident

#### Pattern 5: Cross-Account Role Chaining via SSO
```
User logs in via IAM Identity Center
        │
        ▼
Assumes Role in Security Account (via Permission Set)
        │
        │ aws sts assume-role (explicit)
        ▼
Cross-account role in Production Account
        │
        ▼
Performs privileged action
```
- Used for highly sensitive operations
- Double audit trail (SSO login + role assumption)
- Extra layer of control

## 1.5 Security & Compliance Angles

### IAM Permissions Required for IAM Identity Center

| Action | IAM Permission |
|---|---|
| View Identity Center config | `sso:DescribeRegisteredRegions` |
| Manage permission sets | `sso-admin:CreatePermissionSet` |
| Assign accounts | `sso-admin:CreateAccountAssignment` |
| List users | `identitystore:ListUsers` |
| Create users | `identitystore:CreateUser` |
| Manage instances | `sso-admin:ListInstances` |

### Encryption
- IAM Identity Center **encrypts all data at rest** using AWS-managed KMS keys
- Data in transit encrypted via TLS 1.2+
- **No option for customer-managed KMS** for Identity Center data itself
- Temporary credentials issued by STS follow standard STS encryption

### Logging & Monitoring

**CloudTrail integration:**
- All IAM Identity Center API calls logged in CloudTrail
- Events in `us-east-1` regardless of where action taken
- Key events to monitor:
  ```
  ├── sso-admin:CreateAccountAssignment   (new access granted)
  ├── sso-admin:DeleteAccountAssignment   (access removed)
  ├── sso-admin:CreatePermissionSet       (new permission set)
  ├── sso-admin:ProvisionPermissionSet    (permission set deployed)
  ├── sso:Authenticate                    (user login)
  └── sso:Logout                          (user logout)
  ```

**CloudWatch integration:**
- Set up CloudWatch alarms on CloudTrail events
- Alert on: failed logins, new account assignments, permission set changes

**AWS Access Analyzer:**
- Analyze roles created by IAM Identity Center for external access
- Detect overly permissive permission sets

### Common Misconfigurations

| Misconfiguration | Risk | Fix |
|---|---|---|
| Long session duration on admin permission sets | Credential exposure window | Set to 1 hour for privileged sets |
| No MFA enforced | Account takeover | Enable MFA in Identity Center or IdP |
| SCIM token never rotated | Token compromise | Rotate SCIM token regularly |
| Management account used as delegated admin | Violates separation of concerns | Use dedicated Security account |
| Customer managed policy missing in some accounts | Permission set fails silently | Ensure policy deployed to all accounts via IaC |
| No CloudTrail alerts on assignment changes | Undetected privilege escalation | Set up EventBridge rules on sso-admin events |

### Compliance Relevance
| Framework | IAM Identity Center Relevance |
|---|---|
| **CIS AWS Benchmark** | Centralized access management requirement |
| **ISO 27001** | Access control, user provisioning/deprovisioning |
| **SOC 2** | Logical access controls, audit trail |
| **PCI DSS** | Least privilege, MFA for admin access |
| **NIST 800-53** | AC-2 (Account Management), AC-17 (Remote Access) |

## 2.2 Common Exam Traps & Distractors

### Trap 1: Cognito vs IAM Identity Center
> ❌ **Wrong:** "Use Cognito for employee SSO to multiple AWS accounts"
> ✅ **Right:** Cognito = customer-facing apps. IAM Identity Center = workforce/employees

### Trap 2: Permission Set Update = Automatic Propagation
> ❌ **Wrong:** "Update the permission set and changes apply immediately"
> ✅ **Right:** Must explicitly re-provision after any permission set change

### Trap 3: SAML = Provisioning
> ❌ **Wrong:** "Configure SAML 2.0 to automatically sync users from Okta"
> ✅ **Right:** SAML = authentication only. SCIM = provisioning/deprovisioning

### Trap 4: SCPs Grant Access
> ❌ **Wrong:** "Use SCPs to grant read-only access to new accounts"
> ✅ **Right:** SCPs never grant — they only restrict. Use Permission Sets to grant.

### Trap 5: Management Account Exempt from SCPs but Not from Identity Center
> ⚠️ Management account IS exempt from SCPs
> ⚠️ Management account is NOT exempt from IAM Identity Center controls

### Trap 6: Manually Modifying AWSReservedSSO Roles
> ❌ **Wrong:** "Modify the AWSReservedSSO role directly to add permissions"
> ✅ **Right:** Always update the Permission Set — manual role changes are overwritten on re-provision

### Trap 7: AD Connector Stores Data in AWS
> ❌ **Wrong:** "AD Connector replicates directory data to AWS"
> ✅ **Right:** AD Connector is a proxy — zero data stored in AWS

### Trap 8: Double MFA with External IdP
> ⚠️ If external IdP is used, configure MFA at the IdP only
> ⚠️ Enabling MFA in both IAM Identity Center AND IdP causes double prompts

### Trap 9: ABAC Works Without Enabling It
> ❌ **Wrong:** "Just add PrincipalTag conditions to IAM policies"
> ✅ **Right:** Must explicitly **enable ABAC** in IAM Identity Center settings AND configure attribute mappings

### Trap 10: Customer Managed Policy Auto-Created
> ❌ **Wrong:** "IAM Identity Center creates missing customer managed policies in accounts"
> ✅ **Right:** Policy must pre-exist in every target account — provisioning fails if missing

### Strategy 1: Workforce vs Customer
If the scenario mentions **employees, staff, internal users** → eliminate Cognito immediately → lean toward IAM Identity Center

### Strategy 2: Multi-Account = Identity Center

### Strategy 3: Automatic Provisioning = SCIM

### Strategy 4: Scalability = OU Assignment or ABAC

### Strategy 5: Data Residency = AD Connector

### Strategy 6: Read SCPs Carefully

Any question about permission set changes not taking effect → re-provisioning is the answer

# SCIM — System for Cross-domain Identity Management

## Plain English
SCIM is a **standardized protocol** that automates the process of **creating, updating, and deleting user accounts** across different systems. Think of it as a "messenger" that keeps user databases in sync automatically.

## The Problem It Solves
```
Without SCIM:
New employee joins → IT manually creates account in:
  ├── Okta
  ├── AWS IAM Identity Center  ← manual step
  ├── Salesforce               ← manual step
  ├── Slack                    ← manual step
  └── GitHub                   ← manual step

Employee leaves → IT must manually delete from all 5 systems
  └── Miss one = security risk (ghost account)
```

```
With SCIM:
New employee joins → IT creates account in Okta ONLY
  └── SCIM automatically propagates to:
        ├── AWS IAM Identity Center ✅ auto
        ├── Salesforce              ✅ auto
        ├── Slack                   ✅ auto
        └── GitHub                  ✅ auto

Employee leaves → Deactivate in Okta ONLY
  └── SCIM automatically deactivates everywhere ✅
```

## How SCIM Works Technically
```
Okta (SCIM Client)          IAM Identity Center (SCIM Server)
      │                                │
      │  HTTP POST /Users              │
      │  {name, email, department}     │
      │ ──────────────────────────────▶│ Creates user
      │                                │
      │  HTTP PATCH /Users/{id}        │
      │  {department: "Finance"}       │
      │ ──────────────────────────────▶│ Updates attribute
      │                                │
      │  HTTP DELETE /Users/{id}       │
      │ ──────────────────────────────▶│ Deactivates user
```

- SCIM runs over **HTTPS**
- Uses **REST API** calls (POST, PATCH, DELETE)
- Requires a **SCIM endpoint URL** (provided by IAM Identity Center)
- Requires a **SCIM access token** (generated in IAM Identity Center, configured in Okta)
- Standard: **RFC 7642 / 7643 / 7644**

## SCIM vs SAML — Key Distinction
```
SAML  = Authentication (WHO are you? Prove it.)
SCIM  = Provisioning  (Create/update/delete your account)

They serve completely different purposes.
Both are typically needed together for a complete solution.
```

| Aspect | SAML | SCIM |
|---|---|---|
| **Purpose** | Authentication (login) | User provisioning (lifecycle) |
| **Triggered by** | User clicking login | Admin action in IdP |
| **Direction** | IdP → Service Provider | IdP → Service Provider |
| **Protocol** | XML-based assertions | REST API (JSON) |
| **When it runs** | Every login | When users are created/changed/deleted |

## Real World Example (Exam Context)
> "A company uses Okta. A new employee is added to Okta but cannot access AWS the next day."
> → **SCIM is not configured** — user was not provisioned into IAM Identity Center automatically

# IdP — Identity Provider

## Plain English
An IdP is a **system that stores and verifies user identities**. It is the **single source of truth** for who a user is and whether their credentials are valid.

Think of it like a **passport office** — it issues and validates identity documents that other systems trust.

## The Problem It Solves
```
Without IdP (old world):
  ├── AWS has its own username/password
  ├── Salesforce has its own username/password
  ├── GitHub has its own username/password
  └── User manages 10+ different passwords

Problems:
  ├── Password fatigue → weak passwords
  ├── No central place to revoke access
  └── IT nightmare to manage
```

```
With IdP (modern world):
  ├── User has ONE identity in Okta (IdP)
  ├── Okta verifies the user
  └── All other systems TRUST Okta's verification

Benefits:
  ├── Single password (SSO)
  ├── MFA in one place
  └── Revoke access centrally
```

## How IdP Works (SAML Flow)
```
Step 1: User visits AWS Console (Service Provider)
Step 2: AWS redirects to Okta (IdP) — "go prove who you are"
Step 3: User enters Okta credentials + MFA
Step 4: Okta validates credentials
Step 5: Okta sends SAML Assertion back to AWS
        (a signed XML token saying "this user is verified")
Step 6: AWS trusts Okta's assertion → grants access
Step 7: User is in AWS Console — never entered AWS password
```

## IdP vs SP (Service Provider)
```
IdP (Identity Provider):        SP (Service Provider):
├── Okta                        ├── AWS IAM Identity Center
├── Azure Active Directory      ├── Salesforce
├── Ping Identity               ├── GitHub
├── OneLogin                    ├── Slack
└── JumpCloud                   └── Any app that trusts the IdP
```

| Role | Responsibility |
|---|---|
| **IdP** | Stores identities, validates credentials, issues assertions |
| **SP** | Provides the service, trusts the IdP, grants access based on assertion |

## Types of IdPs (Exam Relevant)

### External IdP (Third Party)
- Okta, Azure AD (Entra ID), Ping Identity, OneLogin
- Organization manages users here
- Integrates with IAM Identity Center via SAML 2.0

### AWS as IdP
- IAM Identity Center has a **built-in directory** — it can act as its own IdP
- IAM also supports **OIDC** and **SAML** identity providers natively

### Active Directory as IdP
- AWS Managed Microsoft AD acts as IdP
- IAM Identity Center reads users/groups from it
- Kerberos used for actual authentication

## SAML Assertion (What IdP Actually Sends)
```xml
<!-- Simplified SAML Assertion from Okta to AWS -->
<SAMLAssertion>
  <Issuer>https://okta.company.com</Issuer>
  <Subject>
    <NameID>pradeep@company.com</NameID>
  </Subject>
  <Attributes>
    <Attribute name="Department">Security</Attribute>
    <Attribute name="Role">SecurityAudit</Attribute>
  </Attributes>
  <Signature><!-- cryptographic proof Okta signed this --></Signature>
</SAMLAssertion>
```

AWS trusts this because it has Okta's **public certificate** pre-configured — verifies the signature.
