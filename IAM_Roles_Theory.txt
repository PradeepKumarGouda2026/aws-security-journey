## **PART 1: IAM ROLES VS IAM USERS (20 MIN)**

### **Understanding the Fundamental Difference**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                     IAM ROLES VS IAM USERS                                ║
╚═══════════════════════════════════════════════════════════════════════════╝
		
IAM USER:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Represents: A specific person or application
Identity type: Long-term identity
Credentials: 
├─ Username/password (console access)
├─ Access keys (programmatic access)
└─ Permanent until rotated

Used by: One person/application
Login process: Username + password OR access key + secret key
Typical use: Employees, contractors, specific applications

Example:
User: alice@company.com
Credentials: Password + MFA (console), Access Key (API)
Permissions: Developer permissions

Characteristics:
✅ Permanent identity
✅ Direct authentication
✅ Credentials can be compromised if leaked
✅ Need to manage credential rotation
✅ Max 5000 users per account

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IAM ROLE:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Represents: A set of permissions anyone can assume
Identity type: Temporary identity
Credentials:
├─ Temporary security credentials
├─ Access key + secret key + session token
└─ Auto-expire (15 min to 12 hours)

Used by: Anyone/anything allowed by trust policy
Assumption process: Call AssumeRole API → Get temporary credentials
Typical use: AWS services, cross-account access, federated users

Example:
Role: EC2-S3-Access-Role
Trust policy: Allow EC2 service to assume
Permissions: Read/write to specific S3 bucket
Assumed by: EC2 instances

Characteristics:
✅ Temporary credentials (auto-expire)
✅ No permanent credentials to manage
✅ Can't login directly (must assume)
✅ More secure (credentials rotate automatically)
✅ No limit on number of roles

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHEN TO USE WHAT:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USE IAM USERS FOR:
✅ Individual employees (console access)
✅ Service accounts (when role not possible)
✅ Third-party tools requiring access keys

USE IAM ROLES FOR:
✅ AWS services (EC2, Lambda, ECS, etc.) ← Most common!
✅ Cross-account access
✅ Federated users (SSO, SAML, OIDC)
✅ Temporary elevated permissions
✅ Applications running on AWS

BEST PRACTICE:
"Use roles whenever possible, users when necessary"

Why roles are better:
1. No credential management (auto-rotate)
2. No long-term credentials to leak
3. Temporary access (principle of least privilege)
4. Easy to audit (who assumed role when)
5. Can be assumed by multiple entities
```

### **Role Anatomy - Two Policies**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                    IAM ROLE HAS TWO POLICIES                              ║
╚═══════════════════════════════════════════════════════════════════════════╝

Every IAM Role has TWO policies:

1. TRUST POLICY (Who can assume the role)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Also called: Assume Role Policy
Answers: "WHO can assume this role?"
Attached to: The role itself

Example - Allow EC2 to assume role:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "ec2.amazonaws.com"
    },
    "Action": "sts:AssumeRole"
  }]
}

Example - Allow specific user to assume role:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::123456789012:user/alice"
    },
    "Action": "sts:AssumeRole"
  }]
}

Example - Allow another AWS account to assume role:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::111111111111:root"
    },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "unique-external-id-12345"
      }
    }
  }]
}

Key Elements:
- Principal: WHO (service, user, account)
- Action: Always "sts:AssumeRole"
- Condition: Optional (MFA, ExternalId, etc.)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

2. PERMISSIONS POLICY (What the role can do)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Also called: Identity-based policy, Role policy
Answers: "WHAT can this role do?"
Attached to: The role (like user policies)

Example - Allow S3 read access:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:ListBucket"
    ],
    "Resource": [
      "arn:aws:s3:::my-bucket",
      "arn:aws:s3:::my-bucket/*"
    ]
  }]
}

This is the same format as IAM user policies!
No "Principal" (role itself is the principal)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

VISUAL REPRESENTATION:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌────────────────────────────────────────────────────────────┐
│                    IAM ROLE                                │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ TRUST POLICY (Who can assume)                        │ │
│  │                                                      │ │
│  │ Principal: EC2 Service                              │ │
│  │ Action: sts:AssumeRole                              │ │
│  └──────────────────────────────────────────────────────┘ │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ PERMISSIONS POLICY (What role can do)                │ │
│  │                                                      │ │
│  │ Action: s3:GetObject, s3:ListBucket                 │ │
│  │ Resource: arn:aws:s3:::my-bucket/*                  │ │
│  └──────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────┘

FLOW:
1. EC2 instance requests to assume role (matches trust policy ✓)
2. Gets temporary credentials with S3 read permissions
3. Can now access S3 bucket using those credentials
4. Credentials expire after session duration (default 1 hour)
```

## **PART 2: AWS STS (SECURITY TOKEN SERVICE) (20 MIN)**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                  AWS STS (SECURITY TOKEN SERVICE)                         ║
╚═══════════════════════════════════════════════════════════════════════════╝

WHAT IS STS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AWS STS = Service that creates temporary security credentials

Purpose: Allow entities to temporarily assume roles

Credentials include:
├─ Access Key ID (like permanent keys)
├─ Secret Access Key (like permanent keys)
├─ Session Token (unique to temporary credentials!)
└─ Expiration timestamp (when credentials expire)

Duration: 15 minutes to 12 hours (configurable)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STS API OPERATIONS:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. AssumeRole
   Purpose: Assume an IAM role
   Used by: IAM users, IAM roles, federated users
   Returns: Temporary credentials for the role
   
   Example:
   aws sts assume-role \
     --role-arn arn:aws:iam::123456789012:role/MyRole \
     --role-session-name my-session
   
   Returns:
   {
     "Credentials": {
       "AccessKeyId": "ASIAXXX",
       "SecretAccessKey": "xxx",
       "SessionToken": "xxx",
       "Expiration": "2026-03-22T18:00:00Z"
     },
     "AssumedRoleUser": {
       "AssumedRoleId": "AROAXXXX:my-session",
       "Arn": "arn:aws:sts::123456789012:assumed-role/MyRole/my-session"
     }
   }

2. AssumeRoleWithWebIdentity
   Purpose: Assume role using web identity provider (Google, Facebook, Amazon)
   Used by: Mobile/web applications
   Authentication: ID token from identity provider
   
   Example:
   aws sts assume-role-with-web-identity \
     --role-arn arn:aws:iam::123456789012:role/MobileAppRole \
     --role-session-name mobile-session \
     --web-identity-token <token-from-google>
   
   Use case: Mobile app users login with Google, get temporary AWS access

3. AssumeRoleWithSAML
   Purpose: Assume role using SAML assertion
   Used by: Enterprise SSO (Active Directory Federation)
   Authentication: SAML assertion from corporate IdP
   
   Example:
   aws sts assume-role-with-saml \
     --role-arn arn:aws:iam::123456789012:role/SAMLRole \
     --principal-arn arn:aws:iam::123456789012:saml-provider/MyProvider \
     --saml-assertion <base64-encoded-saml>
   
   Use case: Employees login with corporate credentials, get AWS access

4. GetSessionToken
   Purpose: Get temporary credentials for MFA-protected access
   Used by: IAM users adding MFA to their session
   
   Example:
   aws sts get-session-token \
     --serial-number arn:aws:iam::123456789012:mfa/alice \
     --token-code 123456
   
   Use case: User needs to perform MFA-protected operation

5. GetFederationToken
   Purpose: Get temporary credentials for federated user
   Used by: Custom federation broker
   Less common (mostly legacy)

6. GetCallerIdentity
   Purpose: Get details about the calling identity
   Used by: Debugging, verifying credentials
   
   Example:
   aws sts get-caller-identity
   
   Returns:
   {
     "UserId": "AIDAI1234567890EXAMPLE",
     "Account": "123456789012",
     "Arn": "arn:aws:iam::123456789012:user/alice"
   }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TEMPORARY CREDENTIALS STRUCTURE:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

{
  "AccessKeyId": "ASIAZ123456789EXAMPLE",     ← Starts with ASIA (temporary)
  "SecretAccessKey": "wJalrXUtn...",          ← Secret key
  "SessionToken": "FwoGZXIvYXdzE...",         ← Session token (REQUIRED!)
  "Expiration": "2026-03-22T18:00:00Z"        ← When credentials expire
}

Key difference from permanent credentials:
- Permanent: AccessKeyId starts with AKIA
- Temporary: AccessKeyId starts with ASIA
- Temporary: Has SessionToken (permanent credentials don't)

Using temporary credentials:
export AWS_ACCESS_KEY_ID=ASIAZ123456789EXAMPLE
export AWS_SECRET_ACCESS_KEY=wJalrXUtn...
export AWS_SESSION_TOKEN=FwoGZXIvYXdzE...  ← Must include session token!

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SESSION DURATION:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Different operations have different max durations:

AssumeRole:
├─ Default: 1 hour
├─ Maximum: 12 hours (configurable in role settings)
└─ Can be specified in assume-role call

AssumeRoleWithWebIdentity:
├─ Default: 1 hour
└─ Maximum: 12 hours

AssumeRoleWithSAML:
├─ Default: 1 hour
└─ Maximum: 12 hours

GetSessionToken:
├─ Default: 12 hours
└─ Maximum: 36 hours (for root user: 1 hour max)

Setting duration:
aws sts assume-role \
  --role-arn arn:aws:iam::123456789012:role/MyRole \
  --role-session-name my-session \
  --duration-seconds 3600  ← 1 hour (3600 seconds)

Minimum: 900 seconds (15 minutes)
Maximum: 43200 seconds (12 hours) for most operations
```

## **PART 3: SERVICE ROLES (20 MIN)**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                         SERVICE ROLES                                     ║
╚═══════════════════════════════════════════════════════════════════════════╝

SERVICE ROLE = Role assumed by AWS service on your behalf

Common use cases:
✅ EC2 instances accessing AWS resources
✅ Lambda functions accessing S3, DynamoDB
✅ ECS tasks accessing secrets, logs
✅ CodeBuild accessing repositories
✅ CloudFormation creating resources

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EC2 INSTANCE ROLE (Most Common):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: EC2 instance needs to access S3
Bad solution: Store access keys on instance (can be stolen!)
Good solution: Attach IAM role to instance ✅

How it works:
1. Create IAM role with trust policy allowing ec2.amazonaws.com
2. Attach permissions policy (e.g., S3 read access)
3. Attach role to EC2 instance (via instance profile)
4. EC2 instance automatically gets temporary credentials
5. Credentials auto-rotate every hour
6. Application uses AWS SDK → automatic credential handling!

Trust Policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "ec2.amazonaws.com"
    },
    "Action": "sts:AssumeRole"
  }]
}

Permissions Policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:PutObject"
    ],
    "Resource": "arn:aws:s3:::my-app-bucket/*"
  }]
}

Instance Profile:
- Container for IAM role
- Allows EC2 to pass role to instance
- Automatically created when attaching role to instance via console
- Name usually matches role name

Accessing credentials from EC2 instance:
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/RoleName

Returns:
{
  "AccessKeyId": "ASIA...",
  "SecretAccessKey": "...",
  "Token": "...",
  "Expiration": "2026-03-22T18:00:00Z"
}

AWS SDK automatically uses these credentials!

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LAMBDA EXECUTION ROLE:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every Lambda function needs an execution role

Trust Policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "lambda.amazonaws.com"
    },
    "Action": "sts:AssumeRole"
  }]
}

Minimum Permissions (for basic Lambda):
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "logs:CreateLogGroup",
      "logs:CreateLogStream",
      "logs:PutLogEvents"
    ],
    "Resource": "arn:aws:logs:*:*:*"
  }]
}

Common additional permissions:
- S3: Read/write files
- DynamoDB: Read/write data
- SQS: Receive/delete messages
- SNS: Publish notifications
- Secrets Manager: Retrieve secrets

AWS Managed Policy for basic Lambda:
arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

OTHER COMMON SERVICE ROLES:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ECS Task Role:
Principal: "ecs-tasks.amazonaws.com"
Purpose: Allow ECS containers to access AWS services

RDS Enhanced Monitoring:
Principal: "monitoring.rds.amazonaws.com"
Purpose: Allow RDS to send metrics to CloudWatch

CloudFormation:
Principal: "cloudformation.amazonaws.com"
Purpose: Allow CloudFormation to create/modify resources

CodeBuild:
Principal: "codebuild.amazonaws.com"
Purpose: Allow CodeBuild to access source code, artifacts

AWS Glue:
Principal: "glue.amazonaws.com"
Purpose: Allow Glue jobs to access data sources

Step Functions:
Principal: "states.amazonaws.com"
Purpose: Allow Step Functions to invoke Lambda, other services

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

      "Condition": {
        "StringEquals": {

        "Bool": {
          "aws:MultiFactorAuthPresent": "true"
        }

Key elements explained:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Principal: "AWS": "arn:aws:iam::111111111111:root"
→ Allows ENTIRE Account A (dev account) to assume
→ "root" means any user/role in that account
→ Individual users still need permission in Account A to assume

Why use :root instead of specific user?
→ Flexibility: Any user in Account A can be granted access
→ Centralized control in Account A (who gets access)
→ Don't have to modify trust policy when adding/removing users

Action: "sts:AssumeRole"
→ The API call to assume a role
→ Always this action for trust policies

Condition - External ID:
→ "sts:ExternalId": "MyCompany-Dev-To-Prod-2026"
→ Security measure (prevents confused deputy attack)
→ Must be unique and secret
→ Optional but HIGHLY recommended for cross-account

Condition - MFA:
→ "aws:MultiFactorAuthPresent": "true"
→ Requires MFA to assume role
→ Optional but recommended for production access

Create the role:
aws iam create-role \
  --role-name ProdReadOnlyRole \
  --assume-role-policy-document file://trust-policy.json \
  --description "Read-only access to production for developers"

## **EXTERNAL ID DEEP DIVE**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                    EXTERNAL ID EXPLAINED                                  ║
╚═══════════════════════════════════════════════════════════════════════════╝

WHAT IS THE CONFUSED DEPUTY PROBLEM?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Scenario WITHOUT External ID:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Your company uses third-party SaaS (e.g., analytics service)

Customer A (you):
├─ Account: 111111111111
├─ Creates role: AnalyticsAccessRole
├─ Trust policy: Allows SaaS account (333333333333) to assume
└─ Role ARN: arn:aws:iam::111111111111:role/AnalyticsAccessRole

Customer B (another company):
├─ Account: 444444444444
├─ Creates role: AnalyticsAccessRole (same name!)
├─ Trust policy: Allows SaaS account (333333333333) to assume
└─ Role ARN: arn:aws:iam::444444444444:role/AnalyticsAccessRole

SaaS application (analytics service):
├─ Account: 333333333333
├─ Has list of customer role ARNs
└─ Assumes roles to access customer data

THE ATTACK:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Attacker (Customer B) knows:
- SaaS account ID: 333333333333 (public)
- Role naming pattern: AnalyticsAccessRole (common)
- Other customer account IDs (can guess or find)

Attacker sends API request to SaaS:
"Please analyze data from account 111111111111"
(Customer A's account - NOT attacker's!)

SaaS application (confused deputy):
aws sts assume-role \
  --role-arn arn:aws:iam::111111111111:role/AnalyticsAccessRole \
  → Succeeds! SaaS can assume this role

SaaS accesses Customer A's data:
→ Attacker (Customer B) sees Customer A's data! 🚨

This is the CONFUSED DEPUTY attack:
SaaS is "confused" about which customer it's working for

SOLUTION: EXTERNAL ID
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Customer A:
├─ Generates unique External ID: "cust-a-secret-12345-unique"
├─ Gives External ID to SaaS provider
├─ Configures role with External ID requirement

Trust policy WITH External ID:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::333333333333:root"
    },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "cust-a-secret-12345-unique"
      }
    }
  }]
}

SaaS provider stores mapping:
Customer A → External ID: cust-a-secret-12345-unique
Customer B → External ID: cust-b-different-67890-secret

Now when assuming role:
aws sts assume-role \
  --role-arn arn:aws:iam::111111111111:role/AnalyticsAccessRole \
  --external-id cust-a-secret-12345-unique
  → Succeeds ✅

If attacker tries WITHOUT External ID:
aws sts assume-role \
  --role-arn arn:aws:iam::111111111111:role/AnalyticsAccessRole
  → Access Denied ❌ (missing External ID)

If attacker tries WITH WRONG External ID:
aws sts assume-role \
  --role-arn arn:aws:iam::111111111111:role/AnalyticsAccessRole \
  --external-id cust-b-different-67890-secret
  → Access Denied ❌ (External ID doesn't match)

EXTERNAL ID BEST PRACTICES:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ Generate randomly (UUID or similar)
✅ Keep secret (don't publish or commit to Git)
✅ Unique per customer/partner
✅ Long enough to prevent guessing (minimum 20 characters)
✅ Rotate periodically
✅ Store securely (Secrets Manager)

Example good External ID:
"MyCompany-Partner-ABC-7f9a8e3d-4c2b-1a5f-8e6d-9c3b7a5f2e1d-2026"

❌ Don't use:
- Account ID (public)
- Company name (guessable)
- Sequential numbers (1, 2, 3)
- Common patterns (password123)
```

## **EXAM-FOCUSED SCENARIOS**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║               EXAM QUESTIONS: CROSS-ACCOUNT ACCESS                        ║
╚═══════════════════════════════════════════════════════════════════════════╝

SCENARIO 1: User can't assume cross-account role
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
"A user in Account A is trying to assume a role in Account B but receives
'Access Denied'. What could be the problem?"

Check TWO places:

1. Trust policy in Account B role:
   Does it allow Account A (or specific user)?
   {
     "Principal": {
       "AWS": "arn:aws:iam::111111111111:root"
     }
   }
   ✅ Must allow

2. User permissions in Account A:
   Does user have sts:AssumeRole permission?
   {
     "Action": "sts:AssumeRole",
     "Resource": "arn:aws:iam::222222222222:role/RoleName"
   }
   ✅ Must have

BOTH must allow! (AND relationship, not OR)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 2: Third-party access security
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
"A third-party SaaS needs access to your S3 bucket for analytics.
What is the MOST secure approach?"

Answer:
✅ Create cross-account role with:
   - External ID (prevent confused deputy)
   - Least privilege permissions (s3:GetObject only)
   - Short session duration (1 hour)
   - MFA required (if possible)

Trust policy:
{
  "Principal": { "AWS": "arn:aws:iam::SAAS-ACCOUNT:root" },
  "Condition": {
    "StringEquals": { "sts:ExternalId": "unique-customer-id" }
  }
}

❌ Don't:
- Give access keys (permanent, can leak)
- Use bucket policy without External ID (confused deputy)
- Grant more permissions than needed (s3:* is too broad)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 3: Audit access across multiple accounts
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
"Security team needs read-only access to all 50 AWS accounts in your
organization. What's the most efficient solution?"

Answer:
✅ Create cross-account read-only role in EACH account
✅ All roles trust centralized security account
✅ Security team assumes role in target account as needed

Setup:
1. In each of 50 accounts, create: AuditorRole
2. Trust policy allows: Security Account (111111111111)
3. Permissions: ReadOnlyAccess managed policy
4. Security team assumes role when auditing

Automation with AWS Organizations:
Use CloudFormation StackSets to deploy role to all accounts

Alternative (not recommended for 50 accounts):
Individual user access in each account = 50 × users = unmanageable!

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 4: Session duration limits
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
"An application assumes a cross-account role every hour for batch processing.
The processing takes 3 hours. What should you configure?"

Answer:
Configure role maximum session duration to 12 hours (max)

In role settings:
aws iam update-role \
  --role-name BatchProcessingRole \
  --max-session-duration 43200  # 12 hours in seconds

Then assume role with longer duration:
aws sts assume-role \
  --role-arn arn:aws:iam::222222222222:role/BatchProcessingRole \
  --role-session-name batch-job \
  --duration-seconds 10800  # 3 hours

Notes:
- Default max: 1 hour
- Maximum max: 12 hours
- Cannot exceed role's max setting
- Some services (Lambda) have their own limits
```

## **PART 5: ROLE CHAINING (15 MIN)**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                         ROLE CHAINING                                     ║
╚═══════════════════════════════════════════════════════════════════════════╝

WHAT IS ROLE CHAINING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Role chaining = Using one role's temporary credentials to assume another role

Flow:
User → Assumes Role A → Uses Role A credentials → Assumes Role B

Example scenario:
1. Alice (developer) assumes DevRole
2. DevRole assumes ProdReadOnlyRole (in production account)
3. Alice can now read production resources (2-hop access)

Why use it:
✅ Add additional security layer
✅ Limit direct access to production
✅ Audit trail shows both role assumptions
✅ Progressive elevation of privileges

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROLE CHAINING EXAMPLE:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Scenario:
Account A (Dev): 111111111111
Account B (Prod): 222222222222
Account C (Audit): 333333333333

User Alice needs to access audit logs in Account C, but:
- Alice is in Account A (Dev)
- Only Account B (Prod) has access to Account C (Audit)
- Solution: Role chaining!

Setup:

STEP 1: Account A - Alice can assume JumpRole
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Role: JumpRole (in Account A)

Trust policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::111111111111:user/alice"
    },
    "Action": "sts:AssumeRole"
  }]
}

Permissions policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": "arn:aws:iam::222222222222:role/ProdAuditRole"
  }]
}

STEP 2: Account B - ProdAuditRole can assume AuditAccessRole
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Role: ProdAuditRole (in Account B)

Trust policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::111111111111:role/JumpRole"
    },
    "Action": "sts:AssumeRole"
  }]
}

Permissions policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": "arn:aws:iam::333333333333:role/AuditAccessRole"
  }]
}

STEP 3: Account C - AuditAccessRole has audit log access
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Role: AuditAccessRole (in Account C)

Trust policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::222222222222:role/ProdAuditRole"
    },
    "Action": "sts:AssumeRole"
  }]
}

Permissions policy:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:ListBucket"
    ],
    "Resource": [
      "arn:aws:s3:::audit-logs-bucket",
      "arn:aws:s3:::audit-logs-bucket/*"
    ]
  }]
}

EXECUTION:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# Step 1: Alice assumes JumpRole
aws sts assume-role \
  --role-arn arn:aws:iam::111111111111:role/JumpRole \
  --role-session-name alice-session

# Export credentials from response
export AWS_ACCESS_KEY_ID=ASIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...

# Step 2: Using JumpRole credentials, assume ProdAuditRole
aws sts assume-role \
  --role-arn arn:aws:iam::222222222222:role/ProdAuditRole \
  --role-session-name prod-session

# Export new credentials
export AWS_ACCESS_KEY_ID=ASIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...

# Step 3: Using ProdAuditRole credentials, assume AuditAccessRole
aws sts assume-role \
  --role-arn arn:aws:iam::333333333333:role/AuditAccessRole \
  --role-session-name audit-session

# Export final credentials
export AWS_ACCESS_KEY_ID=ASIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...

# Step 4: Access audit logs
aws s3 ls s3://audit-logs-bucket/
→ Success! ✅

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROLE CHAINING LIMITS:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Maximum chain length: 1 hop (Role A → Role B, but Role B can't assume Role C)

Wait, what? The example above has 3 roles!

Clarification:
- User → Role A → Role B ✅ (Allowed, 1 hop)
- Role A → Role B → Role C ❌ (Not allowed, would be 2 hops)

In our example:
- Alice (user) → JumpRole (hop 1)
- JumpRole → ProdAuditRole (hop 2) ❌ This is the problem!

Actually, AWS DOES allow this, but with restrictions:

Session duration limit:
- First assume: Max 12 hours
- Chained assume: Max 1 hour (limited!)
- Each hop reduces max duration

CloudTrail shows full chain:
- Alice assumed JumpRole
- JumpRole assumed ProdAuditRole
- ProdAuditRole assumed AuditAccessRole

Best practice:
Minimize chain length (prefer direct cross-account access when possible)

USE CASES FOR ROLE CHAINING:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Progressive privilege elevation
   User → StandardRole → ElevatedRole → AdminRole
   
2. Break-glass emergency access
   Admin → EmergencyRole → ProductionAccessRole

   Approver1 → ApprovalRole → Approver2Role → SensitiveDataRole
   
5. Multi-account hub-and-spoke
   User in Hub → SpokeAccessRole → ResourceRole in Spoke

## **PART 6: SESSION POLICIES (10 MIN)**

```
╔═══════════════════════════════════════════════════════════════════════════╗
║                       SESSION POLICIES                                    ║
╚═══════════════════════════════════════════════════════════════════════════╝

WHAT ARE SESSION POLICIES?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Session policy = Additional policy passed when assuming a role
Effect: Further RESTRICTS permissions (never expands)
Duration: Only applies to that specific session

Think of it as: Temporary permission boundary for one session

Use case:
Role has broad permissions, but you want to grant narrow access for this session

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EXAMPLE SCENARIO:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Situation:
- Role: DataScientistRole
- Role permissions: Full S3 access (s3:*)
- But: You want to give Alice access to ONLY one specific bucket

Solution: Session policy!

Role permissions policy (broad):
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": "*"
  }]
}

Session policy (narrow):
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": [
      "arn:aws:s3:::project-alpha-data",
      "arn:aws:s3:::project-alpha-data/*"
    ]
  }]
}

Assume role with session policy:
aws sts assume-role \
  --role-arn arn:aws:iam::123456789012:role/DataScientistRole \
  --role-session-name alice-session \
  --policy '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::project-alpha-data",
        "arn:aws:s3:::project-alpha-data/*"
      ]
    }]
  }'

Result:
Role says: Allow s3:* on *
Session says: Allow s3:* on project-alpha-data only
Effective: Allow s3:* on project-alpha-data only ✅ (intersection!)

Alice can:
✅ s3:GetObject on s3://project-alpha-data/file.txt
✅ s3:PutObject on s3://project-alpha-data/file.txt

Alice cannot:
❌ s3:GetObject on s3://project-beta-data/file.txt (not in session policy)
❌ s3:GetObject on s3://any-other-bucket/* (not in session policy)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SESSION POLICY RULES:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. RESTRICTS ONLY (Never Expands)
   Effective permissions = Role permissions ∩ Session policy
   
   Example:
   Role: Allow S3, EC2, RDS
   Session: Allow S3, EC2
   Result: S3 and EC2 only (RDS denied)

2. Optional (Not Required)
   Can assume role without session policy
   Without session policy: Full role permissions

3. Maximum Size: 2048 characters (JSON string)
   Keep session policies concise!

4. Can be passed to:
   - AssumeRole
   - AssumeRoleWithWebIdentity
   - AssumeRoleWithSAML
   - GetFederationToken

5. Evaluation:
   Checked AFTER role permissions
   Part of policy evaluation logic

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PRACTICAL USE CASES:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Time-limited access to specific resource
   Admin role with full access, but only need S3 access for 1 hour

2. Third-party temporary access
   Give vendor access to one specific resource for troubleshooting

3. Automated systems with dynamic permissions
   CI/CD pipeline assumes deployment role with session policy for specific environment

4. Progressive disclosure
   User starts with minimal session policy, can request expanded access

5. Compliance/audit
   Restrict admin access during audit period
```

1. ROLES VS USERS:
   Users = Long-term credentials (can be leaked)
   Roles = Temporary credentials (auto-expire) ✅ Preferred!

2. TWO POLICIES:
   Trust policy = WHO can assume
   Permissions policy = WHAT role can do

3. CROSS-ACCOUNT ACCESS:
   Account A user → AssumeRole → Account B role → Access Account B resources
   Requires: Trust policy in B + Permission in A

4. EXTERNAL ID:
   Security measure for third-party access
   Prevents confused deputy problem
   Should be unique per customer

5. SESSION POLICIES:
   Further RESTRICT permissions (never expand)
   Only for that specific session
   Effective permissions = Role ∩ Session policy

6. TEMPORARY CREDENTIALS:
   AccessKeyId (starts with ASIA)
   SecretAccessKey
   SessionToken (required!)
   Expiration (15 min to 12 hours)

7. STS APIS:
   AssumeRole - Standard role assumption
   AssumeRoleWithWebIdentity - Mobile/web apps
   AssumeRoleWithSAML - Enterprise SSO
   GetSessionToken - MFA
   GetCallerIdentity - Debug
