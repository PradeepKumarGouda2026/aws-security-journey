LAB 19: S3 BUCKET POLICIES vs IAM POLICIES
Understanding the Difference:
IAM Policy (Identity-based):
- Attached to users/roles
- Controls what THIS user can do
- "Alice can access S3"

Bucket Policy (Resource-based):
- Attached to S3 bucket
- Controls who can access THIS bucket
- "This bucket allows Alice"

Both must allow = Access granted

## **Lab 19.4: Add Bucket Policy (Deny Specific User)**
```
1. S3 Console → Your bucket → Permissions tab

2. Bucket policy → Edit

3. Paste this policy (replace YOUR-ACCOUNT-ID):
json{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOwnerFullControl",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::YOUR-ACCOUNT-ID:root"
      },
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::security-lab-bucket-YOURNAME-123",
        "arn:aws:s3:::security-lab-bucket-YOURNAME-123/*"
      ]
    },
    {
      "Sid": "DenyAliceAccess",
      "Effect": "Deny",
      "Principal": {
        "AWS": "arn:aws:iam::YOUR-ACCOUNT-ID:user/alice"
      },
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::security-lab-bucket-YOURNAME-123",
        "arn:aws:s3:::security-lab-bucket-YOURNAME-123/*"
      ]
    }
  ]
}
```
```
4. Save changes

✅ Bucket policy applied!
```

**What this does:**
- Allows account owner (root) full access
- Explicitly DENIES alice (even if she has IAM S3 permissions)
- Deny always wins!

# **LAB 20: BLOCK PUBLIC ACCESS**

## **Understanding Block Public Access (BPA):**
```
4 Settings (all should be ON for security):

1. Block public access to buckets and objects granted through NEW ACLs
2. Block public access to buckets and objects granted through ANY ACLs
3. Block public access to buckets and objects granted through NEW public bucket policies
4. Block public and cross-account access to buckets and objects through ANY public bucket policies

When ALL are ON:
- No public access possible
- Overrides bucket policies
- Account-level AND bucket-level settings
```

---

## **Lab 20.1: Test Block Public Access**
```
1. Go to your public bucket: public-read-test-YOURNAME-456

2. Permissions → Block public access (bucket settings)

3. Click Edit

4. ✅ Check ALL 4 boxes:
   - Block public access to buckets and objects granted through new access control lists (ACLs)
   - Block public access to buckets and objects granted through any access control lists (ACLs)
   - Block public access to buckets and objects granted through new public bucket or access point policies
   - Block public and cross-account access to buckets and objects through any public bucket or access point policies

5. Save changes

6. Type "confirm" → Confirm

   → Should show AccessDenied ❌

✅ Block Public Access working!
```

# **LAB 21: S3 ENCRYPTION**

## **Three Encryption Types:**
```
SSE-S3 (Server-Side Encryption with S3-managed keys):
- AWS manages keys
- AES-256 encryption
- FREE
- Default for new buckets

SSE-KMS (Server-Side Encryption with KMS):
- You control keys via KMS
- Audit trail in CloudTrail
- Can use custom KMS keys
- Costs: KMS API calls

SSE-C (Server-Side Encryption with Customer-provided keys):
- You manage keys outside AWS
- You provide key with each request
- AWS encrypts/decrypts
- No key storage in AWS
```

---

```
1. Go to: security-lab-bucket-YOURNAME-123

Lab 21.3: Test SSE-C (Customer-Provided Keys) via CLI
bash# CloudShell

# Generate a 256-bit encryption key
openssl rand -base64 32 > my-encryption-key.txt

# View the key
cat my-encryption-key.txt
# Output: abc123xyz... (32-byte base64 key)

# Create test file
echo "Sensitive data encrypted with my own key" > secret.txt

# Upload with SSE-C
aws s3 cp secret.txt \
  s3://security-lab-bucket-YOURNAME-123/secret-ssec.txt \
  --sse-c AES256 \
  --sse-c-key fileb://my-encryption-key.txt

# Upload successful ✅

# Try to download WITHOUT key (should fail)
aws s3 cp \
  s3://security-lab-bucket-YOURNAME-123/secret-ssec.txt \
  downloaded.txt

# Error: The object was stored using a form of Server Side Encryption ❌

# Download WITH key (should work)
aws s3 cp \
  s3://security-lab-bucket-YOURNAME-123/secret-ssec.txt \
  downloaded.txt \
  --sse-c AES256 \
  --sse-c-key fileb://my-encryption-key.txt

# Success! ✅
cat downloaded.txt
# Output: Sensitive data encrypted with my own key

✅ SSE-C working! You control the keys!
```

## **Lab 21.4: Enforce Encryption with Bucket Policy**
```
Bucket policy → Edit → Add this statement:
json{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedObjectUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::security-lab-bucket-YOURNAME-123/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": [
            "AES256",
            "aws:kms"
          ]
        }
      }
    }
  ]
}
What this does: Rejects any upload that doesn't specify encryption!
Test:
bash# Upload without encryption header
echo "test" > unencrypted.txt
aws s3 cp unencrypted.txt s3://security-lab-bucket-YOURNAME-123/

# Should fail: Access Denied ❌

# Upload with encryption
aws s3 cp unencrypted.txt \
  s3://security-lab-bucket-YOURNAME-123/ \
  --sse AES256

# Should work! ✅
```

# **LAB 22: S3 OBJECT LOCK & VERSIONING**

## **What is Object Lock?**
```
Write-Once-Read-Many (WORM) model:
- Objects cannot be deleted or overwritten
- Used for compliance (SEC, FINRA, HIPAA)
- Two modes:
  1. Governance mode: Some users can override
  2. Compliance mode: NO ONE can delete (not even root!)
```

# **LAB 24: PRESIGNED URLs**

## **What are Presigned URLs?**
```
Temporary URLs that grant access to private S3 objects:
- URL expires after X seconds/minutes/hours
- Anyone with URL can access (no AWS credentials needed)
- Use case: Share private file temporarily

Lab 24.1: Generate Presigned URL
bash# CloudShell

# Upload private file
echo "This is private data" > private-file.txt
aws s3 cp private-file.txt s3://security-lab-bucket-YOURNAME-123/

# Generate presigned URL (valid for 1 hour)
aws s3 presign \
  s3://security-lab-bucket-YOURNAME-123/private-file.txt \
  --expires-in 3600

# Output:
https://security-lab-bucket-YOURNAME-123.s3.amazonaws.com/private-file.txt?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=...&X-Amz-Expires=3600...

# Copy this URL
# Open in incognito browser
# File downloads! ✅ (even though bucket is private)

# Wait 1 hour → URL expires → Access Denied ❌

Lab 24.2: Presigned URL for Upload
bash# Generate presigned URL for UPLOAD (PUT)
aws s3 presign \
  s3://security-lab-bucket-YOURNAME-123/uploaded-file.txt \
  --expires-in 300

# Anyone with this URL can upload to this specific path
# (Valid for 5 minutes)

# Test upload:
curl -X PUT \
  --upload-file test.txt \
  "PRESIGNED_URL_HERE"

✅ File uploaded via presigned URL!
```

# **LAB 25: MFA DELETE**

## **What is MFA Delete?**
```
Requires MFA (multi-factor authentication) to:
- Permanently delete object versions
- Suspend versioning on bucket

Extra security layer for critical data!
```

---

## **Lab 25.1: Enable Versioning**
```
1. S3 Console → security-lab-bucket-YOURNAME-123

2. Properties → Bucket Versioning → Edit

3. Bucket Versioning: Enable

4. Save

✅ Versioning enabled

Lab 25.2: Enable MFA Delete (ROOT ACCOUNT ONLY)
⚠️ IMPORTANT: MFA Delete can ONLY be enabled by ROOT account via CLI!
bash# Sign in as ROOT user (not IAM user)
# AWS Console → Sign out → Sign in as Root user

# Open CloudShell as root

# Get MFA device serial number
aws iam list-mfa-devices

# Output shows:
{
  "MFADevices": [
    {
      "SerialNumber": "arn:aws:iam::YOUR-ACCOUNT-ID:mfa/root-account-mfa-device",
      ...
    }
  ]
}

# Enable MFA Delete
aws s3api put-bucket-versioning \
  --bucket security-lab-bucket-YOURNAME-123 \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::YOUR-ACCOUNT-ID:mfa/root-account-mfa-device 123456"
  # Replace 123456 with current MFA code from your Google Authenticator

✅ MFA Delete enabled!

Lab 25.3: Test MFA Delete
bash# Upload file
aws s3 cp test.txt s3://security-lab-bucket-YOURNAME-123/

# Upload again (creates new version)
aws s3 cp test.txt s3://security-lab-bucket-YOURNAME-123/

# Try to delete version WITHOUT MFA (should fail)
aws s3api delete-object \
  --bucket security-lab-bucket-YOURNAME-123 \
  --key test.txt \
  --version-id VERSION_ID_HERE

# Error: MFA authentication required ❌

# Delete WITH MFA
aws s3api delete-object \
  --bucket security-lab-bucket-YOURNAME-123 \
  --key test.txt \
  --version-id VERSION_ID_HERE \
  --mfa "MFA_SERIAL 123456"

✅ Deleted with MFA!
```

### Lab 20: Block Public Access - Two Levels

**Lab 20.1: Bucket-Level BPA**
- Scope: Single bucket (public-read-test-YOURNAME-456)
- Action: Enabled all 4 BPA settings
- Result: Blocked public access for THAT bucket
- Use case: Granular control per bucket

**Lab 20.2: Account-Level BPA**
- Scope: Entire AWS account
- Action: Enabled via CLI (UI not accessible)
- Command: `aws s3control put-public-access-block --account-id ...`
- Result: Blocked public access for ALL buckets
- Use case: Blanket security policy

**Key Difference:**
- Bucket-level = Individual bucket protection
- Account-level = Account-wide protection (strongest)

**Hierarchy:** Account-level > Bucket-level > Bucket Policy > ACL

**Best Practice:** Enable BOTH levels in production
