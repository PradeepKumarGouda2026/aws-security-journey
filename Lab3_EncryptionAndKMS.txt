# **LAB 14: KMS KEY POLICIES (ADVANCED)**

## **Understanding Key Policies:**

```
KMS Key Policy = Resource-based policy
(Like S3 bucket policy, but for KMS keys)

Components:
1. Principal: Who can use the key
2. Action: What they can do (Encrypt, Decrypt, etc.)
3. Resource: The key itself (usually "*" in key policy)
4. Condition: Optional restrictions
```

---

## **Step 1: View Current Key Policy**

```
KMS → Customer managed keys → my-first-kms-key

Key policy tab

Click "Switch to policy view" (if in default view)

You'll see JSON policy (created when you made the key)
```

---

## **Step 2: Add Condition - Encryption Context**

```
Key policy → Edit

Find the statement for key users (Decrypt/Encrypt)

Add a condition:

{
  "Sid": "Allow use of the key",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::ACCOUNT_ID:user/alice"
  },
  "Action": [
    "kms:Decrypt",
    "kms:Encrypt",
    "kms:GenerateDataKey*"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:EncryptionContext:Project": "SecretProject"
    }
  }
}

Save changes

What this does:
- alice can ONLY use the key if encryption context includes "Project=SecretProject"
- Adds additional access control layer
- Used for audit trails
```

---

## **Step 3: Test Encryption Context**

```
AWS CLI (from your computer or EC2):

# Encrypt WITH correct context (should work):
echo "Secret data" > test.txt

aws kms encrypt \
  --key-id alias/my-first-kms-key \
  --plaintext fileb://test.txt \
  --encryption-context Project=SecretProject \
  --output text \
  --query CiphertextBlob > encrypted.txt

# Encrypt WITHOUT context (should fail):
aws kms encrypt \
  --key-id alias/my-first-kms-key \
  --plaintext fileb://test.txt \
  --output text

# Error: AccessDeniedException
# The encryption context must include Project=SecretProject!
```

# **LAB 15: KMS GRANTS (TEMPORARY PERMISSIONS)**

## **What are Grants?**

```
Grant = Temporary, programmatic permission to use a key

Use cases:
- Allow Lambda to decrypt data for one execution
- Grant EC2 instance access for specific task
- Delegate KMS permissions without changing key policy

Unlike key policy:
✅ Can be created/revoked programmatically
✅ Temporary (can be time-limited)
✅ Don't require editing key policy
```

---

## **Step 1: Create a Grant (CLI)**

```bash
# Get your key ID
aws kms list-keys

# Create grant for EC2 role to use the key
aws kms create-grant \
  --key-id 12345678-1234-1234-1234-123456789012 \
  --grantee-principal arn:aws:iam::ACCOUNT_ID:role/EC2-S3-ReadOnly-Role \
  --operations Encrypt Decrypt GenerateDataKey

# Output:
{
  "GrantToken": "AQpAM2RhODI...",
  "GrantId": "abcdef123456..."
}

# Save the GrantId - you'll need it to revoke
```

---

## **Step 2: Test the Grant**

```bash
# From EC2 instance with EC2-S3-ReadOnly-Role:

# This should now work (grant gives permission):
aws kms encrypt \
  --key-id 123456789998998 \
  --plaintext "Test data" \
  --output text \
  --query CiphertextBlob
```

---

## **Step 3: Revoke the Grant**

```bash
# Revoke grant (removes permission):
aws kms revoke-grant \
  --key-id 12345678-1234-1234-1234-123456789012 \
  --grant-id abcdef123456...

# Now EC2 role can't use the key anymore
# Try encryption again - should fail!
```

# **LAB 16: ENVELOPE ENCRYPTION (UNDERSTAND THE CONCEPT)**

## **Visual: How Envelope Encryption Works**

```
You want to encrypt 1GB file:

WRONG WAY (doesn't scale):
File (1GB) → Send to KMS → KMS encrypts → Return encrypted file
├─ Problem: 1GB over network to KMS
├─ Problem: KMS has 4KB API limit
└─ Won't work! ❌

RIGHT WAY (envelope encryption):
1. Request data key from KMS
   └─ KMS generates 256-bit data key
   └─ Returns BOTH:
      - Plaintext data key
      - Encrypted data key (encrypted with CMK)

2. Use plaintext data key to encrypt 1GB file locally
   └─ Fast! No network transfer

3. Delete plaintext data key from memory
   └─ Security!

4. Store encrypted file + encrypted data key together

When decrypting:
1. Send encrypted data key to KMS
2. KMS decrypts it with CMK
3. Returns plaintext data key
4. Use plaintext data key to decrypt file locally
5. Delete plaintext data key
```

---

## **Hands-On: Envelope Encryption**

```bash
# Step 1: Generate data key
aws kms generate-data-key \
  --key-id <id>
  --key-spec AES_256

# Output:
{
  "CiphertextBlob": "AQIDAHi...",  ← Encrypted data key (store this!)
  "Plaintext": "base64...",         ← Plaintext data key (use then delete!)
  "KeyId": "arn:aws:kms:..."
}

# Step 2: Use plaintext data key to encrypt data locally
# (In real app, you'd use crypto library with the plaintext key)

# Step 3: Delete plaintext from memory
# unset PLAINTEXT_KEY

# Step 4: Store encrypted data + CiphertextBlob together

# When you need to decrypt:
aws kms decrypt \
  --ciphertext-blob fileb://encrypted-data-key.bin

# Returns plaintext data key
# Use it to decrypt your data locally
# Delete plaintext key again
```

# **KEY POLICIES vs IAM POLICIES - COMPLETE GUIDE**

This is a **critical exam topic**! Let me break it down clearly.

---

## **SIMPLE ANALOGY:**

**Key Policy = Building entrance rules**
- "Who can enter THIS building?"
- Attached to the building (resource)

**IAM Policy = Employee badge permissions**
- "What can THIS employee do?"
- Attached to the employee (identity)

**To enter and do work:**
- ✅ Building must allow you in (Key Policy)
- ✅ Your badge must authorize the action (IAM Policy)
- **BOTH must say YES!**

---

## **TECHNICAL COMPARISON:**

| Feature | Key Policy | IAM Policy |
|---------|-----------|------------|
| **Type** | Resource-based | Identity-based |
| **Attached to** | KMS key | User/Group/Role |
| **Default** | Required (every key has one) | Optional |
| **Controls** | Access to specific key | Access to AWS services |
| **Scope** | One key only | All resources matching |
| **Cross-account** | ✅ Can allow other accounts | ❌ Only same account |
| **Who creates** | Key owner | IAM administrator |
| **Principal** | Must specify WHO | Implicit (attached identity) |

---

## **KEY POLICY (RESOURCE-BASED):**

### **What it is:**
- Attached to the **KMS key itself**
- Defines WHO can use THIS key
- Required (every KMS key MUST have one)

### **Structure:**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "Allow alice to use this key",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/alice"
      },
      "Action": [
        "kms:Encrypt",
        "kms:Decrypt"
      ],
      "Resource": "*"
    }
  ]
}
```

**Key parts:**
- `Principal`: WHO (must explicitly list ARNs)
- `Action`: WHAT they can do
- `Resource`: Usually `"*"` (means this key)

---

## **IAM POLICY (IDENTITY-BASED):**

### **What it is:**
- Attached to **IAM user/group/role**
- Defines what THIS identity can do
- Optional (users start with no permissions)

### **Structure:**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowKMSOperations",
      "Effect": "Allow",
      "Action": [
        "kms:Encrypt",
        "kms:Decrypt"
      ],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/12345678-..."
    }
  ]
}
```

**Key parts:**
- NO `Principal` (implicit - it's alice because policy is attached to alice)
- `Action`: WHAT alice can do
- `Resource`: WHICH keys (specific ARN or `*` for all)

---

## **HOW THEY WORK TOGETHER:**

### **Evaluation Logic:**

```
User alice tries to encrypt data with key-ABC:

Step 1: Check for explicit DENY
├─ Key policy DENY? → ❌ Access denied
└─ IAM policy DENY? → ❌ Access denied

Step 2: Check Key Policy
├─ Does key policy allow alice to encrypt? 
│  ├─ NO → ❌ Access denied (stop here)
│  └─ YES → Continue to Step 3

Step 3: Check IAM Policy (if key policy enables IAM)
├─ Does alice's IAM policy allow kms:Encrypt on this key?
│  ├─ NO → ❌ Access denied
│  └─ YES → ✅ Access granted

Result: BOTH must allow (unless only using key policy)
```

---

## **THREE ACCESS PATTERNS:**

### **Pattern 1: Key Policy Only**

**Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:user/alice"
  },
  "Action": "kms:*",
  "Resource": "*"
}
```

**IAM Policy:** None

**Result:** ✅ alice CAN use the key
- Key policy explicitly allows alice
- No IAM policy needed

**Use case:** Simple access, few users

---

### **Pattern 2: Key Policy + IAM Policy (MOST COMMON)**

**Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:root"
  },
  "Action": "kms:*",
  "Resource": "*"
}
```
*Note: `root` = entire AWS account*

**IAM Policy (attached to alice):**
```json
{
  "Effect": "Allow",
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt"
  ],
  "Resource": "arn:aws:kms:*:*:key/*"
}
```

**Result:** ✅ alice CAN use the key
- Key policy allows the account (root)
- IAM policy allows alice within the account
- **BOTH evaluated**

**Use case:** Large organizations, centralized IAM management

---

### **Pattern 3: Key Policy Blocks, IAM Policy Allows**

**Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:user/bob"
  },
  "Action": "kms:*",
  "Resource": "*"
}
```
*Only bob is listed!*

**IAM Policy (attached to alice):**
```json
{
  "Effect": "Allow",
  "Action": "kms:*",
  "Resource": "*"
}
```

**Result:** ❌ alice CANNOT use the key
- IAM policy says YES
- **But key policy says NO (alice not listed)**
- Key policy wins!

**Use case:** Restrict key to specific users only

---

## **CROSS-ACCOUNT ACCESS:**

### **Only Key Policies Can Allow Other Accounts!**

**Scenario:** Account A wants to allow Account B to use a key

**Account A - Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::999888777666:root"
  },
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt"
  ],
  "Resource": "*"
}
```
*Allows entire Account B (999888777666)*

**Account B - IAM Policy (for user charlie):**
```json
{
  "Effect": "Allow",
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt"
  ],
  "Resource": "arn:aws:kms:us-east-1:123456789012:key/12345678-..."
}
```
*Allows charlie to use Account A's key*

**Result:** ✅ charlie (in Account B) CAN use Account A's key
- **BOTH accounts must configure!**

---

## **ENABLING IAM POLICIES:**

### **The Magic Statement:**

For IAM policies to work, key policy MUST have this:

```json
{
  "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:root"
  },
  "Action": "kms:*",
  "Resource": "*"
}
```

**What this does:**
- `"Principal": {"AWS": "....:root"}` = Entire AWS account
- Delegates permission management to IAM
- Now IAM policies can grant access

**Without this statement:**
- IAM policies are IGNORED! ❌
- Only key policy matters
- Must list every user explicitly in key policy

---

## **REAL-WORLD EXAMPLES:**

### **Example 1: Developer Team Access**

**Goal:** All developers can use encryption key

**Solution: Use IAM Groups**

**Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::123456789012:root"
  },
  "Action": "kms:*",
  "Resource": "*"
}
```

**IAM Policy (attached to "Developers" group):**
```json
{
  "Effect": "Allow",
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt",
    "kms:GenerateDataKey"
  ],
  "Resource": "arn:aws:kms:us-east-1:123456789012:key/dev-key-*"
}
```

**Benefit:**
- Add user to Developers group → instant KMS access
- No need to edit key policy for every new dev!

---

### **Example 2: Sensitive Production Key**

**Goal:** Only 2 specific people can use production encryption key

**Solution: Key Policy Only**

**Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": [
      "arn:aws:iam::123456789012:user/admin1",
      "arn:aws:iam::123456789012:user/admin2"
    ]
  },
  "Action": "kms:*",
  "Resource": "*"
}
```

**No IAM Policy needed!**

**Benefit:**
- Even if someone gets AdministratorAccess IAM policy, they STILL can't use this key!
- Key policy is the gatekeeper

---

### **Example 3: Service Access (S3 using KMS)**

**Goal:** Allow S3 service to use key for SSE-KMS

**Key Policy:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "Service": "s3.amazonaws.com"
  },
  "Action": [
    "kms:Decrypt",
    "kms:GenerateDataKey"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:ViaService": "s3.us-east-1.amazonaws.com"
    }
  }
}
```

**What this does:**
- Allows S3 service to use key
- Only when request comes through S3 (not direct)
- Only in us-east-1 region

## **PERMISSION BOUNDARIES (BONUS):**

**Where do they fit?**

```
Final Permission = Key Policy ∩ IAM Policy ∩ Permission Boundary ∩ SCPs

All must allow (intersection)
Any explicit DENY wins
```

**Example:**
- Key Policy: ✅ Allows alice
- IAM Policy: ✅ Allows kms:Encrypt
- Permission Boundary: ❌ Limits alice to S3 only (not KMS)
- **Result:** ❌ alice CANNOT use KMS (boundary blocks)

## **EXAM SCENARIOS:**

### **Q1: alice has AdministratorAccess but can't use KMS key. Why?**

**A:** Key policy doesn't list alice or enable IAM policies.

**Fix:**
- Add alice to key policy, OR
- Add the "Enable IAM User Permissions" statement

---

### **Q2: Key policy allows alice, but she still can't encrypt. Why?**

**A:** alice's IAM policy doesn't grant kms:Encrypt action.

**Fix:**
- Add IAM policy to alice allowing kms:Encrypt

---

### **Q3: Can IAM policy alone grant KMS access without key policy?**

**A:** NO! Key policy MUST allow access first. IAM policy can only further restrict.

---

### **Q4: How to allow another AWS account to use your KMS key?**

**A:** 
1. Update key policy to allow their account (root ARN)
2. They must add IAM policy in their account
3. Both sides must configure!

---

### **Q5: What's the minimum key policy needed?**

**A:**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:root"
      },
      "Action": "kms:*",
      "Resource": "*"
    }
  ]
}
```
This enables IAM policies to work.

## **BEST PRACTICES:**

### **✅ DO:**
- Use key policy to enable IAM (delegate to IAM for flexibility)
- Use IAM policies for day-to-day access management
- Use key policy for cross-account access
- Use key policy for highly sensitive keys (explicit user list)
- Document which keys use which pattern

### **❌ DON'T:**
- Give everyone full KMS access via IAM
- Forget to enable IAM in key policy
- List every user in key policy (use IAM groups instead)
- Ignore key policy when troubleshooting access issues

## **DECISION TREE:**

```
Need to grant KMS access?
│
├─ Few specific users only?
│  └─ Use KEY POLICY ONLY
│     List each user explicitly
│
├─ Large team / many users?
│  └─ Use KEY POLICY + IAM POLICY
│     Key policy: Enable IAM
│     IAM policy: Attach to groups
│
├─ Cross-account access?
│  └─ MUST use KEY POLICY
│     Both accounts configure
│
└─ AWS service needs access?
   └─ Use KEY POLICY
      Principal: Service
      Condition: ViaService
```

## **MEMORIZATION CHEAT SHEET:**

**Key Policy:**
- Resource-based ✅
- Attached to KEY ✅
- Must have Principal ✅
- Can do cross-account ✅
- Required (every key has one) ✅

**IAM Policy:**
- Identity-based ✅
- Attached to USER/ROLE ✅
- No Principal (implicit) ✅
- Same account only ✅
- Optional ✅

**Both:**
- Evaluated together (intersection) ✅
- Explicit DENY always wins ✅
- JSON format ✅
