## 1.1 Service Overview & Purpose

### What is Lambda Security?
AWS Lambda is a serverless compute service. Lambda Security is not a single service — it is the **complete security model** around Lambda functions: controlling who invokes them, what they can access, how code is validated, how secrets are handled, how networking is controlled, and how runtime activity is monitored.

### Why Does It Exist?
```
Without Lambda Security Controls:
├── Any AWS principal can invoke your function
├── Function has admin-level AWS access (over-privileged role)
├── Database passwords stored as plaintext env vars
├── Function reaches the internet directly (data exfiltration risk)
├── Compromised dependency packages run without validation
├── No visibility into what the function actually does at runtime
└── Runaway function consumes all account concurrency (self-DoS)

With Lambda Security Controls:
├── Resource-based policy gates all invocations
├── Execution role scoped to exact permissions needed
├── Secrets fetched from Secrets Manager at runtime
├── VPC placement with private subnets + security groups
├── Code signing enforces trusted deployment packages only
├── CloudWatch + X-Ray + GuardDuty provide full observability
└── Reserved concurrency prevents runaway execution
```

### Exam Weight & Importance
- Appears in **Domain 3: Infrastructure Security** (22%) and **Domain 2: Security Logging** (20%)
- Expect **3–5 questions** involving Lambda security
- Commonly tested: execution role vs resource policy distinction, VPC Lambda networking, secrets management, kill switch (concurrency=0)

  │Cross-acct │             │   exact ARNs)     │       └─────────────────┘
  └──────────┘              └──────────────────┘
                                     │
                            ┌────────▼────────┐
                            │  Lambda Function │
                            │  ┌────────────┐ │
                            │  │ Function   │ │◀── Code Signing
                            │  │ Code       │ │    (AWS Signer)
                            │  └────────────┘ │

                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                 ▼

             (stdout/stderr)    (distributed)    (anomaly)
```

### Data Flow
1. Event source triggers invocation → **resource-based policy checked**
2. Lambda assumes **execution role** → temporary credentials injected
3. Code runs in isolated Firecracker microVM
4. **Env vars decrypted** via KMS at runtime
5. Secrets fetched from Secrets Manager via SDK (best practice)
6. Downstream AWS calls made using execution role credentials
7. All output streamed to **CloudWatch Logs**
8. GuardDuty monitors network traffic for anomalies

## 1.3 Deep Dive — Every Sub-Topic

### A. Execution Roles

The execution role is the IAM role Lambda **assumes** when your function runs. It defines what AWS services the function can call.

**Trust policy (who can assume):**
```json
{
  "Effect": "Allow",
  "Principal": { "Service": "lambda.amazonaws.com" },
  "Action": "sts:AssumeRole"
}
```

**Baseline managed policies:**
- `AWSLambdaBasicExecutionRole` → CloudWatch Logs write access (mandatory)
- `AWSLambdaVPCAccessExecutionRole` → ENI management for VPC Lambda

**Least privilege pattern:**
```
BAD:  "Action": "*", "Resource": "*"
GOOD: "Action": ["dynamodb:GetItem"], "Resource": "arn:aws:dynamodb:...:table/MyTable"
```

⚠️ **Gotcha:** Missing `AWSLambdaBasicExecutionRole` = function fails silently (no logs written, no output visible).

---

### B. Resource-Based Policies

Controls **who can invoke** the function. Separate from execution role.

```
Execution Role  →  What the function can DO  (outbound)
Resource Policy →  Who can INVOKE the function (inbound)
```

**Cross-account invocation:**
```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::PARTNER-ACCOUNT:root" },
  "Action": "lambda:InvokeFunction",
  "Resource": "arn:aws:lambda:ap-south-1:MYACCOUNT:function:MyFunc"
}
```

⚠️ **Gotcha:** Resource-based policies have a **20KB size limit**. Many cross-account principals = hit limit fast.

---

### C. VPC Integration

By default, Lambda runs **outside your VPC** — cannot reach private RDS, ElastiCache, or internal services.

```
Without VPC Config:              With VPC Config:
Lambda → Public Internet         Lambda → Private Subnet → RDS
Lambda → AWS Public APIs         Lambda → VPC Endpoint → S3/DDB
```

**Security implications:**
- Function gets an ENI in your subnet via **Hyperplane** (sub-second cold starts since 2019)
- Security groups apply to the ENI
- No internet access by default → need NAT Gateway or VPC endpoints
- Use **Interface Endpoints** for AWS services to keep traffic off internet

⚠️ **Gotcha:** VPC Lambda loses internet access entirely unless NAT Gateway is configured. Very common production misconfiguration.

---

### D. Environment Variable Encryption

| Type | Key | Audit Trail | Cost |
|---|---|---|---|
| Default | AWS/lambda (managed) | Limited | Free |
| CMK | Customer KMS key | Full CloudTrail | KMS costs |

⚠️ **Gotcha:** Env vars are **visible in plaintext** via `lambda:GetFunctionConfiguration` to anyone with that permission — regardless of KMS encryption. KMS only protects at rest on disk.

**Best practice:** Don't store secrets as env vars. Fetch from Secrets Manager at runtime:
```python
import boto3, json
def lambda_handler(event, context):
    sm = boto3.client('secretsmanager')
    secret = json.loads(sm.get_secret_value(SecretId='prod/db')['SecretString'])
```

---

### E. Code Signing

Prevents deployment of tampered or unauthorized packages.

```
Developer → AWS Signer → Signed ZIP → S3
                                        │
Lambda (Code Signing Config attached) ◀─┘
         validates signature on deploy
```

**Enforcement modes:**
- `Warn` → deploys but logs warning
- `Enforce` → **blocks** deployment if signature invalid/untrusted

⚠️ **Gotcha:** Code signing validates the **deployment package only** — does NOT prevent runtime code injection via `exec()` or dynamic imports inside the function.

---

### F. Concurrency as a Security Control

| Setting | Use Case |
|---|---|
| Reserved concurrency = N | Cap function scale; protect other functions |
| Reserved concurrency = 0 | **Kill switch** — disables function instantly |
| Provisioned concurrency | Pre-warming; no security impact |

**Incident response kill switch:**
```bash
aws lambda put-function-concurrency \
  --function-name MyFunction \
  --reserved-concurrent-executions 0
```

---

### G. Lambda Layers Security

- Layers have own resource-based policies
- Default: private to your account
- Public layers = **supply chain risk**

⚠️ **Gotcha:** Using public layers from unknown sources is equivalent to running untrusted third-party code in your function.

## 1.4 Comparison Tables

### Secrets Storage for Lambda

| Option | Security Level | Auto-Rotation | Cost | Best For |
|---|---|---|---|---|
| Env Variables | Low | No | Free | Non-sensitive config only |
| SSM Param Store Standard | High | No | Free | Simple secrets |
| SSM Param Store Advanced | High | Yes | $0.05/param/mo | Medium complexity |
| Secrets Manager | Highest | Yes (native) | $0.40/secret/mo | DB creds, API keys |

### Execution Role vs Resource Policy

| Aspect | Execution Role | Resource Policy |
|---|---|---|
| Controls | What function can DO | Who can INVOKE function |
| Direction | Outbound (function → AWS) | Inbound (caller → function) |
| Type | IAM role | Resource-based policy |
| Cross-account | Via role trust | Via principal ARN |
| Size limit | IAM limits | 20KB |

| Framework | Lambda Control |
|---|---|
| CIS AWS | Least-privilege roles, no wildcard permissions |
| PCI-DSS | CMK env vars, VPC isolation, no secrets in env vars |
| ISO 27001 | Code signing, CloudTrail logging |

### Common Misconfigurations (Top 7)
1. Wildcard `*` in execution role
2. Secrets stored as plaintext environment variables
3. Lambda in public subnet with direct internet route
4. Missing CloudWatch Logs policy — silent failures
5. Resource policy with `"Principal": "*"` 
6. Layers pulled from untrusted public sources
7. No reserved concurrency — vulnerable to runaway execution

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** Your Lambda function needs to read from an RDS database in a private subnet. The function has no VPC configuration. What is the minimum required change?

A) Add RDS endpoint as an environment variable  
B) Configure Lambda to run inside the VPC in a private subnet with a security group allowing outbound to RDS port, and attach `AWSLambdaVPCAccessExecutionRole`  
C) Add the RDS connection string to Secrets Manager  
D) Enable Lambda PrivateLink  

**Answer: B**

Lambda must be placed inside the VPC to reach private resources. It needs a private subnet, security group allowing outbound on port 3306/5432, and `AWSLambdaVPCAccessExecutionRole` so Lambda can create ENIs. VPC endpoints are needed to reach other AWS services. Env vars don't fix network routing. PrivateLink is not a Lambda-specific feature.

---

**Q2.** A developer stored a database password as a Lambda environment variable with the default AWS-managed KMS key. A PCI-DSS audit flags this. What should be recommended?

A) Switch to a CMK for environment variable encryption  
B) Move the secret to Secrets Manager and fetch at runtime; remove the environment variable  
C) Base64-encode the password before storing  
D) Use an Advanced SSM parameter with SecureString  

**Answer: B**

The PCI-DSS issue is that the secret is visible via `lambda:GetFunctionConfiguration` regardless of KMS. Moving to Secrets Manager removes the secret from the Lambda config entirely and adds native rotation. Option A (CMK) improves audit trail but doesn't fix the visibility problem. Base64 is not encryption. SSM SecureString is acceptable but Secrets Manager with auto-rotation is the gold standard for PCI-DSS.

---

**Q3.** You need to ensure only your CI/CD pipeline deploys code to Lambda and no tampered packages ever execute. Which TWO controls address this?

A) Code Signing with AWS Signer (Enforce mode) + IAM restricting `lambda:UpdateFunctionCode` to the CI/CD role  
B) Reserved concurrency limit + VPC placement  
C) Resource-based policy restricting invocations + CloudTrail logging  
D) CMK for environment variables + X-Ray tracing  

**Answer: A**

Code Signing (Enforce) validates the deployment package signature — rejects tampered code. IAM restriction on `lambda:UpdateFunctionCode` ensures only the CI/CD role can deploy. Together these address both tampered packages and unauthorized deployments. B/C/D don't address deployment integrity.

---

**Q4.** A Lambda function is invoked thousands of times unexpectedly, consuming all account concurrency and throttling other functions. What is the IMMEDIATE mitigation?

A) Delete the function  
B) Set reserved concurrency to 0  
C) Detach the execution role  
D) Move the function to a VPC  

**Answer: B**

Setting reserved concurrency to 0 is the **kill switch** — it immediately stops all invocations without deleting the function or losing its configuration. Deleting is destructive and irreversible. Detaching the execution role would cause failures but not stop invocations. VPC placement is irrelevant to invocation volume.

---

**Q5.** An external partner in account 999999999999 needs to invoke your Lambda function in account 111111111111. No IAM user sharing is allowed. What is the CORRECT approach?

A) Create an IAM user in your account for the partner  
B) Add a resource-based policy on the Lambda function granting `lambda:InvokeFunction` to `arn:aws:iam::999999999999:root`  
C) Share the function via AWS RAM  
D) Enable public function URL with IAM auth  

**Answer: B**

Resource-based policies support cross-account access natively. The partner's role in their own account invokes the function — no IAM user sharing needed. Lambda functions cannot be shared via RAM. A public function URL would expose the function publicly unless carefully restricted, and IAM auth there still requires your account credentials.

---

**Q6.** GuardDuty generates finding `UnauthorizedAccess:Lambda/MaliciousIPCaller`. What should be the FIRST action?

A) Rotate the KMS key used for environment variables  
B) Set reserved concurrency to 0, then investigate CloudWatch Logs and X-Ray traces  
C) Delete and redeploy the Lambda function  
D) Disable GuardDuty to avoid false positives  

**Answer: B**

Immediate containment = kill switch (concurrency = 0). Then investigate: CloudWatch Logs show what the function did, X-Ray shows outbound calls, CloudTrail shows API activity. Rotating KMS key doesn't stop the function. Deleting loses forensic evidence. Disabling GuardDuty removes your detection capability.

---

**Q7.** Lambda function in a VPC private subnet cannot reach Secrets Manager. No NAT Gateway exists. What is the correct solution?

A) Move Lambda to a public subnet  
B) Add NAT Gateway to the VPC  
C) Create a VPC Interface Endpoint for Secrets Manager  
D) Store the secret as an environment variable instead  

**Answer: C**

VPC Interface Endpoint for Secrets Manager (`com.amazonaws.region.secretsmanager`) keeps traffic within the AWS network without requiring a NAT Gateway. Moving to a public subnet exposes the function unnecessarily. NAT Gateway works but adds cost and routes traffic externally. Moving back to env vars is a security regression.

---

**Q8.** You want to audit every time someone retrieves a Lambda function's configuration (which shows encrypted env var names). Which service provides this visibility?

A) CloudWatch Logs  
B) X-Ray  
C) CloudTrail  
D) GuardDuty  

**Answer: C**

CloudTrail logs all Lambda API calls including `GetFunctionConfiguration`, capturing caller identity, timestamp, and source IP. CloudWatch Logs captures function runtime output only. X-Ray traces function execution, not API calls to the Lambda service. GuardDuty detects threats but doesn't provide full API audit trails.

---

**Q9.** What is the key difference between Lambda's execution role and resource-based policy?

A) Execution role controls network access; resource policy controls data access  
B) Execution role defines what the function can DO (outbound); resource policy defines who can INVOKE the function (inbound)  
C) Both are identical and interchangeable  
D) Resource policy controls KMS access; execution role controls S3 access  

**Answer: B**

This is a fundamental distinction. Execution role = IAM role the function assumes, governing all AWS API calls made BY the function. Resource policy = attached to the function itself, governing who is allowed to invoke it. They are complementary and both required for secure Lambda deployment.

---

**Q10.** A Lambda layer is being shared publicly. What security risk does this introduce?

A) Increased cold start time  
B) Supply chain risk — any account can use the layer; if compromised or maliciously updated, all consumers are affected  
C) The layer becomes read-only  
D) Functions using it automatically become public  

**Answer: B**

Public layers introduce supply chain risk. Malicious actors can create convincing public layers with backdoors. Even legitimate layers can be compromised. Best practice: build your own layers or restrict sharing to specific trusted account IDs. Cold start time is a performance issue, not security. Layers don't change function visibility.

---

**Q11.** Which Lambda feature ensures only signed, unmodified deployment packages from a specific signing profile are executed?

A) VPC endpoint policy  
B) Execution role condition  
C) Code Signing Configuration with AWS Signer  
D) Lambda resource policy  

**Answer: C**

Code Signing Configuration references one or more AWS Signer signing profiles. When set to `Enforce` mode, Lambda rejects any deployment where the package signature doesn't match a trusted profile. This prevents unauthorized or tampered code from ever running. VPC endpoints and resource policies don't address code integrity.

---

**Q12.** Your Lambda execution role has `s3:*` on `*`. What is the correct remediation?

A) Add a deny statement for dangerous S3 actions  
B) Replace with specific actions (`s3:GetObject`, `s3:PutObject`) scoped to the specific bucket ARN the function actually needs  
C) Move the role to a permission boundary  
D) Enable S3 Block Public Access  

**Answer: B**

Least privilege = specific actions on specific resources. The role should only allow the exact S3 operations the function performs, against the exact bucket ARN. Deny statements are a backup control, not a replacement for least privilege. Permission boundaries are useful but don't replace scoping. S3 Block Public Access is unrelated to IAM permissions.

---

**Q13.** A Lambda function has Reserved Concurrency = 50. 51 simultaneous invocations arrive. What happens?

A) All 51 execute, slightly degraded  
B) The 51st request is throttled and Lambda returns 429 TooManyRequestsException  
C) Lambda automatically scales beyond the limit  
D) The function is deleted  

**Answer: B**

Reserved concurrency is a hard cap. The 51st invocation is **throttled immediately** — Lambda returns a 429 without executing the function. The caller must implement retry logic (with backoff). This behavior is intentional — it protects other functions from this one consuming all account-level concurrency.

---

**Q14.** An attacker gains access to Lambda execution role temporary credentials leaked in application logs. What is the FASTEST way to invalidate them?

A) Delete the IAM role  
B) Rotate the KMS key  
C) Attach an inline deny policy to the role with condition `aws:TokenIssueTime` before current time  
D) Change the function's execution role to a new role  

**Answer: C**

The `aws:TokenIssueTime` condition technique revokes all sessions issued before a specific timestamp — effectively invalidating all outstanding temporary credentials immediately without deleting the role. Deleting the role breaks the function. Rotating KMS key doesn't affect IAM credentials. Changing execution role leaves the leaked credentials still valid until natural expiry.

---

**Q15.** What does enabling X-Ray tracing on Lambda provide that CloudWatch Logs does NOT?

A) Function error messages  
B) Distributed trace showing downstream service calls, latency breakdown, and service map  
C) CloudTrail API call history  
D) GuardDuty threat findings  

**Answer: B**

X-Ray provides distributed tracing — showing the complete call graph from the Lambda function to every downstream service (DynamoDB, S3, external APIs), with latency at each hop and a visual service map. CloudWatch Logs captures stdout/stderr output. CloudTrail captures API calls to AWS services. GuardDuty monitors for threats.

---

**Q16.** A company wants to prevent Lambda functions from making outbound internet calls to prevent data exfiltration. What architecture achieves this?

A) Set reserved concurrency = 0  
B) Place Lambda in a VPC private subnet with no NAT Gateway; use VPC endpoints for AWS services  
C) Add a deny rule in the execution role for all internet-bound APIs  
D) Enable X-Ray tracing  

**Answer: B**

Placing Lambda in a VPC private subnet with no NAT Gateway completely prevents internet egress. VPC endpoints allow access to required AWS services (S3, DynamoDB, Secrets Manager) without internet routing. Concurrency = 0 disables the function. IAM execution roles don't control network traffic. X-Ray is observability, not network control.

---

**Q17.** Lambda environment variables are at rest encrypted by default. Why might this still not be sufficient for compliance?

A) Default KMS keys cannot be used with Lambda  
B) The encrypted values are still visible as plaintext through `GetFunctionConfiguration` API to anyone with that IAM permission  
C) Environment variables are not actually encrypted  
D) KMS keys expire after 90 days  

**Answer: B**

The encryption protects the data on AWS storage infrastructure — but the Lambda service decrypts and presents the values when you call `GetFunctionConfiguration`. Anyone with that IAM permission sees the plaintext values. This is why compliance frameworks require moving secrets out of env vars entirely into Secrets Manager.

---

**Q18.** Which TWO services together provide the most complete picture of a Lambda security incident?

A) CloudWatch Logs + CloudTrail  
B) X-Ray + Shield  
C) GuardDuty + WAF  
D) Config + Macie  

**Answer: A**

CloudWatch Logs shows what the function executed (runtime behavior, errors, outputs). CloudTrail shows all API calls TO the Lambda service (who deployed, who changed the role, who invoked). Together they cover both runtime behavior and infrastructure-level actions. X-Ray provides tracing but not control plane visibility. Shield/WAF are for network/web protection.

---

**Q19.** A function needs to access DynamoDB without routing traffic over the internet, and Lambda is inside a VPC. What is needed?

A) NAT Gateway  
B) Internet Gateway  
C) VPC Gateway Endpoint for DynamoDB  
D) Lambda function URL  

**Answer: C**

DynamoDB supports **Gateway Endpoints** (free). Adding a Gateway Endpoint for DynamoDB to the VPC's route table routes all DynamoDB traffic through the AWS private network — no NAT Gateway, no internet routing. Internet Gateway routes to the public internet. Lambda function URL is an invocation mechanism, not network routing.

---

**Q20.** During a security review, you discover a Lambda function has `"Principal": "*"` in its resource-based policy with no conditions. What is the risk and remediation?

A) No risk — Lambda requires authentication regardless  
B) Anyone on the internet can invoke the function; remediate by restricting Principal to specific account/service ARNs and adding Condition blocks  
C) The function will fail — wildcard principals are invalid  
D) Only IAM users can invoke via wildcard principal  

**Answer: B**

`"Principal": "*"` with no conditions means **any unauthenticated caller can invoke the function**. This is a critical misconfiguration. Remediation: replace with specific principals (service ARN, account ARN, or role ARN) and add `Condition` blocks (e.g., `aws:SourceAccount`, `ArnLike` for source ARN). Lambda does NOT auto-authenticate wildcard principals.

## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: Env var encryption = secrets are safe**
> ❌ Wrong: "KMS-encrypted env vars protect secrets from exposure"
> ✅ Right: Anyone with `lambda:GetFunctionConfiguration` sees plaintext values — use Secrets Manager

**Trap 2: VPC Lambda has internet access**
> ❌ Wrong: "Lambda in a VPC can reach the internet normally"
> ✅ Right: VPC Lambda loses ALL internet access — NAT Gateway or VPC endpoints required

**Trap 3: Code signing prevents runtime injection**
> ❌ Wrong: "Code signing prevents exec() calls inside the function"
> ✅ Right: Code signing validates only the deployment package — not runtime behavior

**Trap 4: Resource policy alone secures Lambda**
> ❌ Wrong: "Resource policy controls both invocation and permissions"
> ✅ Right: Resource policy = who invokes; Execution role = what it can do. Both needed.

**Trap 5: Default KMS = same protection as CMK**
> ❌ Wrong: "Default AWS-managed key provides equivalent security to CMK"
> ✅ Right: CMK gives you key policy control, full CloudTrail audit, and rotation management

**Trap 6: Concurrency = 0 deletes the function**
> ❌ Wrong: "Setting concurrency to 0 removes the function"
> ✅ Right: Concurrency = 0 is a reversible kill switch — function config preserved

**Trap 7: Execution role credentials are long-lived**
> ❌ Wrong: "Lambda execution role credentials last until manually rotated"
> ✅ Right: Lambda rotates temporary credentials automatically (roughly every hour)

**Trap 8: Public layers are safe if they're popular**
> ❌ Wrong: "Popular public layers from AWS Marketplace are always safe"
> ✅ Right: Always audit layer content; public layers are supply chain risk regardless of popularity

**Trap 9: GuardDuty Lambda findings = code-level bugs**
> ❌ Wrong: "GuardDuty finding means there's a bug in the function code"
> ✅ Right: GuardDuty detects behavioral anomalies (unusual outbound, crypto mining) — not code bugs

**Trap 10: X-Ray replaces CloudTrail for Lambda**
> ❌ Wrong: "Enable X-Ray for complete Lambda audit trail"
> ✅ Right: X-Ray = runtime tracing. CloudTrail = control plane API audit. Both serve different purposes.

## 2.4 Elimination Strategies

**Strategy 1: VPC Lambda + can't reach AWS service → VPC Endpoint**
Any scenario: Lambda in VPC, no internet, can't reach service → eliminate NAT GW (cost) → **VPC endpoint (Interface or Gateway)**

**Strategy 2: Secrets in env vars → Secrets Manager**
Any compliance question about Lambda secrets → eliminate env vars regardless of encryption → **Secrets Manager with runtime fetch**

**Strategy 3: Stop runaway function → Reserved Concurrency = 0**
Need to stop Lambda without deleting → eliminate "delete function" → **reserved concurrency = 0**

**Strategy 4: Who can invoke → Resource Policy**
Question about controlling which service/account invokes Lambda → eliminate execution role → **resource-based policy**

**Strategy 5: What function can access → Execution Role**
Question about Lambda accessing S3/DDB/SM → eliminate resource policy → **execution role with least privilege**

**Strategy 6: Tampered deployment → Code Signing (Enforce)**
Need deployment integrity guarantee → eliminate IAM alone → **Code Signing with Enforce mode**

**Strategy 7: Credential leak invalidation → TokenIssueTime**
Need to revoke outstanding STS credentials fast → eliminate "rotate role" → **inline deny with aws:TokenIssueTime condition**

## 1.1 Service Overview & Purpose

### What is ECS/EKS Security?
**Amazon ECS (Elastic Container Service)** is AWS's native container orchestration service. **Amazon EKS (Elastic Kubernetes Service)** is managed Kubernetes on AWS. Container security encompasses: image security, runtime security, IAM for containers, network isolation, secrets management, and control plane security.

### Why Does It Exist?
```
Container Security Challenges:
├── Container images may contain vulnerabilities
├── Containers run as root by default (privilege escalation risk)
├── Multiple containers share host kernel (breakout risk)
├── Secrets injected via env vars or insecure mounts
├── East-west traffic between containers unencrypted
├── Container registries publicly exposed
└── Over-privileged task/pod roles accessing all AWS services

AWS Container Security Controls:
├── ECR image scanning (basic + enhanced via Inspector)
├── Task roles (ECS) / IRSA (EKS) for pod-level AWS access
├── VPC CNI + Security Groups for Pods (EKS)
├── Secrets Manager / SSM integration for secrets injection
├── AWS Fargate enforced read-only root filesystem
├── OPA/Kyverno/PSA for Kubernetes policy enforcement
└── GuardDuty EKS Runtime Monitoring for threat detection
```

### Exam Weight & Importance
- **Domain 3: Infrastructure Security** (22%)
- Expect **3–4 questions** on container security
- Commonly tested: Task roles vs instance roles, IRSA, image scanning, Fargate security model, Secrets injection patterns

## 1.3 Deep Dive — Every Sub-Topic

### A. ECR Image Security

**Image Scanning:**

| Type | Engine | Triggers | Findings |
|---|---|---|---|
| Basic Scanning | Clair (open source) | Push or manual | CVEs in OS packages |
| Enhanced Scanning | Amazon Inspector | Continuous | OS + app libraries + programming language pkgs |

**Enhanced scanning** integrates with Inspector and provides near-real-time findings as new CVEs are published — even for images already pushed.

**ECR Security Controls:**
- **Private repositories** by default
- **Repository policies** (resource-based) control cross-account pull
- **ECR pull-through cache** can mirror public registries securely
- **Image tag immutability** prevents overwriting a tag (`:latest` attack prevention)
- **Lifecycle policies** remove old/unscanned images automatically
- **Encryption** — images encrypted at rest with KMS CMK

⚠️ **Gotcha:** Basic scanning only runs at push time — a new CVE published after push won't be detected until rescan. Enhanced scanning is continuous.

---

### B. ECS Task Roles vs EC2 Instance Roles

This is the **most important ECS security concept for the exam.**

```
Instance Profile (BAD pattern):
EC2 instance → IAM role → ALL tasks on that instance
inherit ALL permissions of the instance role
= any task can access everything the host can

Task Role (GOOD pattern):
Individual task → dedicated IAM role → scoped permissions
= each task has only what it needs
```

**How task roles work:**
- Defined in Task Definition under `taskRoleArn`
- ECS injects credentials via **task metadata endpoint** (169.254.170.2)
- Credentials are task-scoped and auto-rotated
- Works with both EC2 launch type and Fargate

⚠️ **Gotcha:** On EC2 launch type, containers can still access the EC2 instance metadata service (169.254.169.254) unless you block it at the network level. A container escaping to the instance metadata service can steal instance-level credentials — bypassing task roles.

**Block EC2 IMDS from containers:**
```bash
# iptables rule to block containers from reaching EC2 IMDS
iptables --insert FORWARD 1 --in-interface docker+ \
  --destination 169.254.169.254/32 --jump DROP
```

---

### C. IRSA — IAM Roles for Service Accounts (EKS)

IRSA is the EKS equivalent of ECS task roles — pod-level IAM permissions.

```
Pod → Service Account → IAM Role (via OIDC federation)

How it works:
1. EKS cluster has OIDC provider URL
2. IAM role trust policy references OIDC provider + service account
3. Pod assumes the role via projected service account token
4. AWS SDK in pod automatically uses IRSA credentials
```

**Trust policy for IRSA:**
```json
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::ACCOUNT:oidc-provider/oidc.eks.region.amazonaws.com/id/EXAMPLID"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "oidc.eks.region.amazonaws.com/id/EXAMPLID:sub": "system:serviceaccount:NAMESPACE:SA-NAME"
    }
  }
}
```

⚠️ **Gotcha:** If IRSA is not configured, pods default to using the EC2 node's instance profile — meaning ALL pods on that node share the same permissions. This is the equivalent of the ECS instance profile anti-pattern.

---

### D. Fargate Security Model

Fargate removes EC2 instances from the picture entirely. Security benefits:

| Aspect | EC2 Launch Type | Fargate |
|---|---|---|
| Host OS access | Possible (SSH to EC2) | ❌ Not possible |
| Container escape to host | Possible | Extremely difficult (ephemeral microVM) |
| Shared kernel risk | All tasks on same host | Task isolated in own microVM |
| Node patching | Your responsibility | AWS responsibility |
| Read-only root filesystem | Optional | Configurable |
| Instance profile access | Possible from containers | ❌ No instance metadata |

⚠️ **Gotcha:** Fargate still requires task roles for AWS API access — there is no EC2 instance role to fall back on.

---

### E. Secrets Injection for Containers

| Method | ECS Support | EKS Support | Security Level |
|---|---|---|---|
| Environment variables (plaintext) | ✅ | ✅ | ❌ Low |
| Secrets Manager (native integration) | ✅ | ✅ (via CSI driver) | ✅ High |
| SSM Parameter Store (native) | ✅ | ✅ (via CSI driver) | ✅ High |
| Kubernetes Secrets (base64) | ❌ | ✅ | ⚠️ Medium |
| External Secrets Operator | ❌ | ✅ | ✅ High |
| AWS Secrets Store CSI Driver | ❌ | ✅ | ✅ High |

**ECS native Secrets Manager injection:**
```json
"secrets": [
  {
    "name": "DB_PASSWORD",
    "valueFrom": "arn:aws:secretsmanager:region:account:secret:prod/db/password"
  }
]
```
The value is injected as an env var but **fetched at task launch from Secrets Manager** — not hardcoded in the task definition.

⚠️ **Gotcha:** Kubernetes Secrets are only base64 encoded by default — **not encrypted**. Anyone with `kubectl get secret` can decode them. Use **Envelope Encryption** with KMS to encrypt etcd at rest.

---

### F. EKS RBAC

EKS uses Kubernetes RBAC + AWS IAM together:

```
AWS IAM AuthN → EKS AuthZ (RBAC)

aws-auth ConfigMap maps:
  IAM Role ARN → Kubernetes username/groups
  IAM User ARN → Kubernetes username

Kubernetes RBAC then controls what that user/group can do.
```

**Principle of least privilege in RBAC:**
- Use `Role` + `RoleBinding` (namespace-scoped) over `ClusterRole` + `ClusterRoleBinding` (cluster-wide)
- Avoid binding to `system:masters` group (full admin)
- Audit with `kubectl auth can-i --as <user> <verb> <resource>`

---

### G. Network Security for Containers

**ECS:**
- Security Groups applied at **task level** (not instance level) with `awsvpc` network mode
- Each task gets its own ENI → fine-grained SG control
- `awsvpc` mode required for Fargate

**EKS:**
- **Security Groups for Pods** — assign SGs directly to pods (requires VPC CNI)
- **Network Policies** — Calico or Cilium for pod-to-pod traffic control
- **Service mesh** (App Mesh / Istio) — mTLS between services

⚠️ **Gotcha:** EKS default networking has no network policy — ALL pods can talk to ALL pods by default. Deploy a network policy engine (Calico, Cilium) to enforce east-west isolation.

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** Multiple ECS tasks on EC2 launch type need different levels of AWS access. The current setup uses an EC2 instance profile. What is the correct security improvement?

A) Create separate EC2 instances for each task  
B) Assign individual IAM task roles in each Task Definition  
C) Use different AWS accounts for each task  
D) Rotate the instance profile credentials more frequently  

**Answer: B**

Task roles provide per-task IAM isolation. Each Task Definition gets its own `taskRoleArn` with scoped permissions. Separate EC2 instances is wasteful and doesn't scale. Separate accounts is extreme. Rotating credentials doesn't scope permissions — all tasks still share the instance profile.

---

**Q2.** An EKS pod needs to write to an S3 bucket. The node's instance profile doesn't have S3 access. What is the correct approach?

A) Add S3 permissions to the node's instance profile  
B) Hardcode AWS credentials in the container  
C) Configure IRSA — link the pod's service account to an IAM role with S3 permissions  
D) Mount an AWS credential file as a Kubernetes Secret  

**Answer: C**

IRSA provides pod-level IAM access without modifying the node's instance profile or hardcoding credentials. Adding S3 to the node profile gives ALL pods on that node S3 access. Hardcoded credentials are a security anti-pattern. Kubernetes Secrets storing credentials are base64 only (not encrypted) and credentials become stale.

---

**Q3.** A security audit finds that Kubernetes Secrets in an EKS cluster are not encrypted at rest. What is the recommended remediation?

A) Base64-encode all secret values  
B) Enable envelope encryption for etcd using KMS CMK  
C) Store secrets in a ConfigMap instead  
D) Restrict `kubectl get secret` via RBAC  

**Answer: B**

Envelope encryption with KMS CMK encrypts Kubernetes Secrets in etcd using a customer-managed key. Base64 is NOT encryption — it's the current (insufficient) state. ConfigMaps are not meant for secrets and are not encrypted. RBAC restriction is a good additional control but doesn't encrypt the data at rest.

---

**Q4.** A container in an ECS task on EC2 launch type calls 169.254.169.254 and retrieves the EC2 instance profile credentials. What security control prevents this?

A) VPC endpoint for EC2 metadata  
B) iptables rule blocking container access to 169.254.169.254 on the EC2 host  
C) Enabling Fargate launch type  
D) Task role with an explicit deny for `sts:AssumeRole`  

**Answer: B**

An iptables rule on the EC2 host blocking the IMDS address (169.254.169.254) from container network interfaces prevents containers from stealing instance credentials. Fargate doesn't have this issue (no accessible instance metadata). Task role deny doesn't block direct IMDS HTTP calls. VPC endpoints don't apply to link-local addresses.

---

**Q5.** What is the key security advantage of Fargate over EC2 launch type for ECS?

A) Lower cost  
B) Tasks run in isolated microVMs with no shared kernel, and there is no host OS to access or compromise  
C) Faster container startup  
D) Built-in load balancing  

**Answer: B**

Fargate uses ephemeral microVMs — each task runs in complete isolation with its own kernel. There is no EC2 host to SSH into, no shared kernel between tasks, and no instance profile to steal. This eliminates entire classes of container escape attacks. Cost and startup time are operational concerns, not security.

---

**Q6.** An EKS cluster has no Network Policy configured. What is the default behavior?

A) All pod-to-pod communication is blocked  
B) All pods can communicate with all other pods in the cluster by default  
C) Only pods in the same namespace can communicate  
D) Only pods with matching labels can communicate  

**Answer: B**

Kubernetes has **no default network isolation** — all pods can reach all other pods across all namespaces unless a Network Policy engine (Calico, Cilium) is deployed and policies are defined. This is a critical security gap in default EKS deployments.

---

**Q7.** You want ECR to continuously scan images even after they are pushed, as new CVEs are published. Which scanning type provides this?

A) Basic Scanning (push-triggered)  
B) Enhanced Scanning via Amazon Inspector  
C) Manual rescan via CLI  
D) AWS Config rule for ECR  

**Answer: B**

Enhanced Scanning integrates with Amazon Inspector and provides **continuous scanning** — when a new CVE is published, Inspector re-evaluates already-pushed images and generates new findings. Basic scanning is push-triggered only. Manual rescan requires human action. Config rules don't scan image contents.

---

**Q8.** What ECS network mode is required for assigning individual security groups to each task?

A) `bridge`  
B) `host`  
C) `awsvpc`  
D) `overlay`  

**Answer: C**

`awsvpc` mode gives each task its own ENI, allowing security groups to be applied at the task level (not the EC2 instance level). `bridge` mode shares the EC2 instance's network namespace. `host` mode shares the host network stack. `overlay` is not an ECS network mode.

---

**Q9.** How are ECS secrets from Secrets Manager injected into containers securely?

A) Stored in plaintext in the Task Definition  
B) Referenced by ARN in the Task Definition `secrets` field — fetched from Secrets Manager at task launch  
C) Baked into the container image at build time  
D) Downloaded by a sidecar container and written to a shared volume  

**Answer: B**

ECS natively integrates with Secrets Manager — you reference the secret ARN in the task definition. ECS fetches the value at task launch and injects it as an environment variable. The secret value is never stored in the task definition. Baking into images is an anti-pattern. Sidecar download is a pattern used in EKS (not native ECS).

---

**Q10.** In EKS, what is the purpose of the `aws-auth` ConfigMap?

A) Stores AWS API credentials for pods  
B) Maps IAM roles/users to Kubernetes RBAC users and groups  
C) Configures VPC networking for pods  
D) Defines pod resource limits  

**Answer: B**

The `aws-auth` ConfigMap is the bridge between AWS IAM identity and Kubernetes RBAC. It maps IAM role ARNs to Kubernetes usernames/groups, which are then governed by Kubernetes RBAC (Roles/ClusterRoles). Without proper entries, IAM principals cannot interact with the Kubernetes API.

---

**Q11.** What is the risk of using `:latest` tag in production ECS task definitions without image tag immutability?

A) Images load slower  
B) A new malicious or broken image push to `:latest` automatically affects all new task launches without any change to the task definition  
C) ECR charges more for latest-tagged images  
D) CloudTrail stops logging ECR pulls  

**Answer: B**

Without tag immutability, `:latest` can be overwritten silently. Any new task launch or service update will pull the new (potentially malicious or broken) image. Enable **image tag immutability** in ECR so tags cannot be overwritten, and use **digest-pinned** image references in production.

---

**Q12.** A company requires mTLS between all microservices in EKS. Which service enables this?

A) ACM Private CA only  
B) A service mesh such as AWS App Mesh or Istio with mTLS policy  
C) VPC Security Groups  
D) IAM roles for service accounts  

**Answer: B**

A service mesh (App Mesh, Istio, Linkerd) provides mTLS between pods — all service-to-service communication is mutually authenticated and encrypted. ACM Private CA can provide certificates to the mesh but doesn't enforce mTLS by itself. Security Groups control network access but don't provide mutual authentication. IRSA is about AWS API access, not inter-pod communication.

---

**Q13.** Pod Security Standards in EKS have three profiles. Which profile enforces the strictest security (no privilege escalation, no host namespace sharing, read-only root FS)?

A) Privileged  
B) Baseline  
C) Restricted  
D) Enforced  

**Answer: C**

**Restricted** is the most stringent PSS profile — it enforces running as non-root, prohibits privilege escalation, blocks host namespace/PID/network sharing, requires read-only root filesystem, and limits allowed volume types. Privileged allows everything. Baseline prevents known privilege escalations but is less strict. Enforced is not a PSS profile name.

---

**Q14.** GuardDuty EKS Runtime Monitoring detects `Execution:Kubernetes/ExecInContainer`. What does this indicate?

A) A pod crashed and restarted  
B) Someone executed a command directly inside a running container via `kubectl exec`  
C) A container image was pushed to ECR  
D) A pod was scheduled on a new node  

**Answer: B**

`kubectl exec` allows direct command execution inside running containers — a common attacker technique for lateral movement after compromising cluster credentials. GuardDuty flags this as suspicious when it deviates from baseline behavior. Pod restarts generate different events. ECR pushes are CloudTrail events. Pod scheduling is an EKS audit log event.

---

**Q15.** What is the difference between ECS Task Execution Role and ECS Task Role?

A) They are the same role with different names  
B) Task Execution Role is used by ECS agent to pull images and fetch secrets; Task Role is used by the application code inside the container  
C) Task Execution Role runs the application; Task Role manages the ECS service  
D) Task Role is only used with Fargate  

**Answer: B**

**Task Execution Role** — used by the ECS agent/Fargate platform: pulls container images from ECR, fetches secrets from Secrets Manager/SSM, sends logs to CloudWatch. **Task Role** — used by the application code running inside the container: makes AWS SDK/API calls (DynamoDB, S3, SQS, etc.). Both are separate IAM roles with different purposes.

---

**Q16.** An EKS cluster node has a broad IAM instance profile. An attacker compromises a pod and accesses AWS services. Which control would have prevented the lateral movement to AWS?

A) VPC Security Groups  
B) IRSA with scoped per-pod IAM roles, and removing broad permissions from node instance profile  
C) Encrypting etcd with KMS  
D) Enabling EKS audit logs  

**Answer: B**

The root cause is the over-privileged instance profile. IRSA scopes permissions to individual pods via OIDC, and the node instance profile should have minimal permissions (just node bootstrap and ECR pull). An attacker in a pod with IRSA can only reach what that specific pod's service account is allowed to. Audit logs and etcd encryption don't prevent the lateral movement.

---

**Q17.** What is the recommended approach for passing secrets to an EKS pod?

A) Hardcode in Dockerfile as ENV  
B) Store in ConfigMap  
C) Use AWS Secrets Store CSI Driver or External Secrets Operator to sync from Secrets Manager  
D) Set as node environment variables  

**Answer: C**

AWS Secrets Store CSI Driver mounts secrets directly from Secrets Manager/SSM into pods as files or env vars, with automatic rotation. External Secrets Operator syncs SM/SSM secrets into Kubernetes Secrets with encryption. Hardcoding is a critical anti-pattern. ConfigMaps are not encrypted. Node env vars expose secrets to ALL pods.

---

**Q18.** Amazon Inspector's enhanced scanning of ECR images provides findings for which categories?

A) OS vulnerabilities only  
B) OS vulnerabilities + application library dependencies (npm, pip, gem, etc.) + programming language packages  
C) Only critical CVEs  
D) Only vulnerabilities with available patches  

**Answer: B**

Enhanced Scanning (Inspector) covers OS packages AND application library dependencies across languages (Node.js npm, Python pip, Ruby gems, Java Maven/Gradle, .NET NuGet, Go modules). Basic scanning (Clair) covers OS packages only. All severity levels are reported. Findings are generated regardless of patch availability.

---

**Q19.** What is the security risk of binding a Kubernetes service account to the `system:masters` ClusterRole?

A) The pod runs slower  
B) The pod (and any attacker who compromises it) has unrestricted admin access to the entire Kubernetes cluster  
C) The pod cannot access external AWS services  
D) Network policies stop applying  

**Answer: B**

`system:masters` is equivalent to cluster admin. Any compromised pod bound to this ClusterRole gives an attacker full control: create/delete any resource, access all secrets in all namespaces, modify RBAC itself, and escalate to other workloads. Always use namespace-scoped Roles with minimal verbs.

---

**Q20.** When should you use Security Groups for Pods in EKS vs Kubernetes Network Policies?

A) They are identical and interchangeable  
B) Security Groups for Pods control traffic to/from AWS resources (RDS, ElastiCache) at the ENI level; Network Policies control pod-to-pod traffic within the cluster  
C) Network Policies replace all need for Security Groups  
D) Security Groups for Pods only work with Fargate  

**Answer: B**

**Security Groups for Pods** — AWS-native, ENI-level control. Best for restricting pod access to AWS resources like RDS (port 5432), ElastiCache, etc. Natively enforced in the network layer. **Network Policies** — Kubernetes-native, pod-to-pod traffic. Best for east-west isolation within the cluster. Both are complementary and should be used together.

## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: EC2 instance profile = all tasks share permissions**
> ❌ Wrong: "Instance profile scopes permissions per task"
> ✅ Right: Instance profile gives ALL tasks the SAME permissions — use Task Roles

**Trap 2: Kubernetes Secrets = encrypted**
> ❌ Wrong: "Kubernetes Secrets store data securely"
> ✅ Right: Kubernetes Secrets are base64 only by default — enable KMS envelope encryption for etcd

**Trap 3: EKS has default network isolation**
> ❌ Wrong: "Pods can only communicate within their namespace by default"
> ✅ Right: All pods can talk to all pods by default — Network Policy engine required

**Trap 4: Basic ECR scanning = continuous**
> ❌ Wrong: "ECR basic scanning detects new CVEs in existing images"
> ✅ Right: Basic scanning is push-time only — Enhanced Scanning (Inspector) is continuous

**Trap 5: Task Role and Task Execution Role are the same**
> ❌ Wrong: "Task Role is used to pull images from ECR"
> ✅ Right: Execution Role = ECS agent (pull images, fetch secrets); Task Role = application code

**Trap 6: Fargate doesn't need task roles**
> ❌ Wrong: "Fargate handles AWS credentials automatically"
> ✅ Right: Fargate requires explicit Task Roles for AWS API access — no instance profile fallback

**Trap 7: awsvpc is optional for security groups per task**
> ❌ Wrong: "Any ECS network mode supports task-level security groups"
> ✅ Right: Only `awsvpc` mode gives each task its own ENI for security group attachment

**Trap 8: `:latest` tag = pinned version**
> ❌ Wrong: ":latest always pulls the same image"
> ✅ Right: `:latest` can be overwritten — use immutable tags or digest pinning in production

**Trap 9: IRSA works without OIDC provider**
> ❌ Wrong: "IRSA works on any EKS cluster automatically"
> ✅ Right: IRSA requires an OIDC identity provider to be associated with the EKS cluster

**Trap 10: Network Policy removes need for Security Groups**
> ❌ Wrong: "Kubernetes Network Policy replaces AWS Security Groups"
> ✅ Right: Network Policy controls pod-to-pod; Security Groups control ENI-level to AWS resources. Both needed.

**Strategy 1: Pod AWS access → IRSA (not node profile)**

**Strategy 6: Task Role vs Execution Role**
App code needs AWS access → Task Role | ECS agent needs to pull images → Execution Role

## 1.1 Service Overview & Purpose

### What Are Secrets in Containers?
Containers need credentials to access databases, APIs, and other services. "Secrets in Containers" refers to the **secure lifecycle management** of these credentials: how they are stored, injected into containers, rotated, and audited — without exposing them in code, images, environment variables, or Kubernetes manifests.

### The Problem
```
Insecure Patterns (Anti-patterns):
├── Secret hardcoded in Dockerfile: ENV DB_PASS=mypassword
├── Secret in docker-compose.yml committed to Git
├── Secret as Kubernetes Secret (base64 only)
├── Secret as ECS Task Definition env var (plaintext in API response)
├── Secret baked into container image layer
└── Secret passed as docker run -e DB_PASS=mypassword

Secure Patterns:
├── Secrets Manager: central vault, auto-rotation, fine-grained access
├── SSM Parameter Store: SecureString with KMS, no rotation
├── Vault (HashiCorp): self-managed secrets engine
├── Kubernetes External Secrets Operator: sync SM → K8s Secrets
├── AWS Secrets Store CSI Driver: mount SM secrets as files
└── ECS native integration: ARN reference in secrets[] field
```

### Exam Weight & Importance
- **Domain 3: Infrastructure Security** + **Domain 1: Incident Response**
- Expect **2–3 questions** on secrets management patterns
- Commonly tested: SM vs SSM, rotation, ECS injection, EKS CSI driver, detecting exposed secrets

## 1.3 Deep Dive — Every Sub-Topic

### A. AWS Secrets Manager (Deep Dive)

**Core features:**
- Stores secrets as key-value JSON
- **Automatic rotation** via Lambda (built-in for RDS, Redshift, DocumentDB, others)
- Cross-account access via resource policy
- Versioning: `AWSCURRENT`, `AWSPENDING`, `AWSPREVIOUS`
- Replication to multiple regions for DR

**Rotation flow:**
```
1. SM creates new secret version (AWSPENDING)
2. SM invokes rotation Lambda
3. Lambda updates the actual database password
4. Lambda tests the new credentials work
5. SM promotes AWSPENDING → AWSCURRENT
6. Old version becomes AWSPREVIOUS (kept for rollback)
```

⚠️ **Gotcha:** Applications must always call `GetSecretValue` at runtime — not cache the secret value permanently. Rotation is useless if the app caches credentials indefinitely.

**Resource policy for cross-account:**
```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::TRUSTED-ACCOUNT:root" },
  "Action": "secretsmanager:GetSecretValue",
  "Resource": "*"
}
```

---

### B. SSM Parameter Store vs Secrets Manager

| Feature | SSM Parameter Store | Secrets Manager |
|---|---|---|
| Cost | Free (Standard tier) | $0.40/secret/month |
| Auto-rotation | ❌ No (manual only) | ✅ Yes (Lambda-driven) |
| Max value size | 4KB (Standard), 8KB (Advanced) | 64KB |
| Cross-account | ❌ Not natively | ✅ Resource policy |
| Hierarchical paths | ✅ `/app/prod/db/pass` | ❌ |
| KMS encryption | ✅ SecureString | ✅ Always |
| Versioning | ✅ Limited | ✅ Full (CURRENT/PENDING/PREVIOUS) |
| Best for | Config + non-rotating secrets | DB creds, API keys needing rotation |

⚠️ **Gotcha:** SSM Parameter Store Advanced parameters ($0.05/param/month) support higher throughput and larger values — but still no auto-rotation.

---

### C. ECS Secrets Injection (Native)

ECS supports native injection from both Secrets Manager and SSM:

```json
"containerDefinitions": [{
  "name": "myapp",
  "secrets": [
    {
      "name": "DB_PASSWORD",
      "valueFrom": "arn:aws:secretsmanager:region:acct:secret:prod/db/password"
    },
    {
      "name": "API_KEY",
      "valueFrom": "arn:aws:ssm:region:acct:parameter/prod/apikey"
    }
  ]
}]
```

**Requirements:**
- Task Execution Role must have `secretsmanager:GetSecretValue` or `ssm:GetParameters`
- Secrets are injected at **task launch** — not dynamically during runtime
- Secret value is injected as environment variable

⚠️ **Gotcha:** ECS injects the secret **at task launch time**. If Secrets Manager rotates the secret after the task starts, the running task uses the old value until it restarts. Design rotation to overlap with task restart cycles.

---

### D. EKS Secrets Injection (CSI Driver + ESO)

**AWS Secrets Store CSI Driver:**
```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: aws-secrets
spec:
  provider: aws
  parameters:
    objects: |
      - objectName: "prod/db/password"
        objectType: "secretsmanager"
```
- Mounts secret as file into pod at runtime
- Supports auto-rotation (pod sees updated file)
- Requires IRSA for the pod to access SM

**External Secrets Operator (ESO):**
- Watches SM/SSM and syncs values into Kubernetes Secrets
- Kubernetes Secret is then used normally
- Supports refresh interval for rotation awareness

⚠️ **Gotcha:** ESO syncs SM secrets INTO Kubernetes Secrets. Unless etcd envelope encryption is enabled, the synced secret exists in plaintext in etcd. CSI Driver mounts directly without creating a K8s Secret, which is more secure.

---

### E. Detecting Exposed Secrets

**AWS Native:**
- **Amazon Macie** — scans S3 for exposed credentials, API keys, passwords
- **AWS Config** — rules checking for secrets in task definitions, launch configurations
- **GuardDuty** — detects usage of exposed credentials (`CredentialAccess:IAMUser/AnomalousBehavior`)
- **CodeGuru Reviewer** — static analysis of code for hardcoded secrets
- **ECR Enhanced Scanning** — detects secrets baked into image layers (via Inspector)

**Response to exposed secret:**
1. Rotate/revoke immediately (SM rotation or IAM key deactivation)
2. Review CloudTrail for unauthorized usage of the exposed credential
3. GuardDuty findings for credential abuse
4. Remediate the source (remove from code/config, git history)

---

### F. Secret Rotation Patterns

**RDS Auto-Rotation (built-in):**
- SM has native rotation support for RDS MySQL, PostgreSQL, Oracle, MSSQL
- Lambda function created automatically in your account
- Single user vs multi-user rotation (zero-downtime)

**Multi-user rotation (zero downtime):**
```
User A (AWSCURRENT) ← app uses this
User B (AWSPENDING) ← SM creating/testing new password
After success: B becomes AWSCURRENT, A becomes AWSPREVIOUS
```

**Custom rotation Lambda:**
```
createSecret → setSecret → testSecret → finishSecret
```

⚠️ **Gotcha:** Single-user rotation has a brief window where the old password is changed but the app hasn't refreshed — can cause connection errors. Multi-user rotation eliminates this.

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** An RDS database password is stored in Secrets Manager. The ECS task needs to use it without it appearing in the task definition as plaintext. What is the correct approach?

A) Set the password as an environment variable in the task definition  
B) Reference the Secrets Manager ARN in the `secrets` field of the task definition  
C) Store the password in S3 and download at startup  
D) Hardcode in the Docker image  

**Answer: B**

The ECS `secrets` field accepts Secrets Manager or SSM ARNs. The value is fetched at task launch by the ECS agent using the Task Execution Role. The plaintext never appears in the task definition. Env var in the task definition stores plaintext. S3 download requires additional code. Hardcoding is the worst pattern.

---

**Q2.** A company needs automatic rotation of RDS credentials every 30 days with zero application downtime. Which approach satisfies this?

A) SM single-user rotation with 30-day schedule  
B) Manual password change on a calendar reminder  
C) SM multi-user rotation with 30-day schedule  
D) SSM Parameter Store with Lambda rotation  

**Answer: C**

Multi-user rotation creates and validates a new password for an alternate user before switching, ensuring the current credentials remain valid throughout. Single-user rotation has a brief window of unavailability. Manual rotation is not automated. SSM Parameter Store has no built-in auto-rotation.

---

**Q3.** A developer accidentally committed an AWS access key to a public GitHub repository. What is the IMMEDIATE response order?

A) Rotate, then review CloudTrail  
B) Deactivate/delete the key immediately, review CloudTrail for unauthorized usage, rotate affected resources, remediate the source  
C) Email the developer first  
D) Wait 24 hours to see if anyone uses it  

**Answer: B**

Immediate deactivation stops the bleeding. CloudTrail review identifies if the key was already used maliciously. Rotate all affected downstream resources. Then remediate source (git history). Speed is critical — automated tools scan GitHub for AWS keys within seconds of commit.

---

**Q4.** What is the maximum size for a secret value stored in Secrets Manager?

A) 4 KB  
B) 8 KB  
C) 64 KB  
D) 256 KB  

**Answer: C**

Secrets Manager supports up to **64KB** per secret value. This is important for secrets that contain multiple fields or large certificates. SSM Standard is 4KB, SSM Advanced is 8KB.

---

**Q5.** An EKS pod has a mounted Secrets Store CSI volume from Secrets Manager. Secrets Manager rotates the secret. When does the pod see the updated value?

A) Never — the pod must be restarted  
B) Within the CSI Driver's rotation poll interval (configurable)  
C) Immediately upon rotation  
D) After the namespace is recycled  

**Answer: B**

The CSI Driver polls Secrets Manager at a configurable interval (`rotationPollIntervalInSeconds`) and updates the mounted file when the secret changes. The application code must re-read the file to pick up the new value. This is more rotation-aware than ECS native injection (which only refreshes at task restart).

---

**Q6.** Which service detects that an AWS API key has been hardcoded in source code in a CodeCommit repository?

A) GuardDuty  
B) Amazon Macie  
C) Amazon CodeGuru Reviewer  
D) AWS Config  

**Answer: C**

CodeGuru Reviewer performs **static code analysis** and detects hardcoded secrets, API keys, passwords, and credentials in source code. GuardDuty detects active usage of compromised credentials. Macie scans S3 objects for data classification. Config monitors resource configurations, not source code.

---

**Q7.** What versioning labels does Secrets Manager use during rotation?

A) v1, v2, v3  
B) AWSCURRENT, AWSPENDING, AWSPREVIOUS  
C) ACTIVE, ROTATING, ARCHIVED  
D) CURRENT, NEW, OLD  

**Answer: B**

- **AWSCURRENT** — active version in use by applications
- **AWSPENDING** — new version being tested during rotation
- **AWSPREVIOUS** — last successfully rotated version (rollback capability)
Applications should always request `AWSCURRENT` (default behavior).

---

**Q8.** A container in EKS receives its DB password via a Kubernetes Secret. etcd is not encrypted. What is the risk?

A) The password is transmitted over plaintext network  
B) Anyone with access to the etcd datastore or backups can read the base64-decoded password  
C) Kubernetes Secrets auto-expire  
D) The container cannot read environment variables  

**Answer: B**

Kubernetes Secrets are stored as base64 in etcd. Base64 is trivially reversible. Anyone with read access to etcd (node-level access, etcd backup access) can decode all secrets. Enable KMS envelope encryption for etcd to encrypt the Secret objects at rest.

---

**Q9.** The SSM Parameter Store SecureString type uses which service for encryption?

A) S3 Server-Side Encryption  
B) AWS KMS  
C) AWS Certificate Manager  
D) AWS Secrets Manager  

**Answer: B**

SecureString parameters are encrypted using **AWS KMS** — either the AWS-managed key (`aws/ssm`) or a customer-managed KMS key (CMK). The CMK option provides full audit trail via CloudTrail and customer-controlled key policy.

---

**Q10.** What is the key advantage of using SM VPC Interface Endpoint for container workloads?

A) Reduces SM cost  
B) Allows containers in private VPC subnets to reach Secrets Manager without routing traffic through the internet or NAT Gateway  
C) Enables automatic rotation  
D) Removes the need for IAM permissions  

**Answer: B**

VPC Interface Endpoints for Secrets Manager (`com.amazonaws.region.secretsmanager`) allow private subnet resources to call SM APIs through the AWS backbone — no internet gateway, no NAT Gateway, no public IP needed. This reduces attack surface and cost while keeping traffic private.

---

**Q11.** A company stores secrets in SM but wants to prevent any service in account B from reading them. What control achieves this?

A) VPC endpoint policy  
B) SM resource-based policy with an explicit Deny for account B principal  
C) KMS key policy with Deny for account B  
D) IAM boundary policy  

**Answer: B**

SM resource-based policies control cross-account access. An explicit `Deny` for account B's principal overrides any Allow. The VPC endpoint policy controls which SM APIs can be called from the VPC endpoint, not cross-account access. KMS key policy can deny decryption but doesn't block the SM API call itself.

---

**Q12.** What happens to a Secrets Manager secret during the rotation window if single-user rotation is used?

A) The application auto-reconnects transparently  
B) There is a brief period where the old password no longer works and the new password is being tested — potential connection failures  
C) All application connections are queued  
D) Nothing — rotation is instantaneous  

**Answer: B**

Single-user rotation changes the password for the existing user. There is a window between the password change and application refresh where the application may fail to authenticate. This is why **multi-user rotation** is recommended for production — it creates a new user, tests it, then switches, maintaining zero downtime.

---

**Q13.** Which AWS service provides continuous scanning of S3 buckets to detect if secrets or credentials have been accidentally stored in object data?

A) AWS Config  
B) GuardDuty  
C) Amazon Macie  
D) Amazon Inspector  

**Answer: C**

Amazon Macie uses ML and pattern matching to scan S3 objects for sensitive data including credentials, API keys, private keys, passwords, and tokens. GuardDuty detects threats using logs/DNS/flow data. Config monitors resource configurations. Inspector scans EC2/containers/Lambda for software vulnerabilities.

---

**Q14.** An ECS Task Execution Role is missing `secretsmanager:GetSecretValue`. What happens at task launch?

A) Task launches normally and fetches secrets lazily  
B) Task fails to start — ECS agent cannot retrieve the secret to inject it  
C) Task starts but the secret environment variable is empty  
D) Task uses cached secrets from previous launch  

**Answer: B**

The Task Execution Role is used by the ECS agent to fetch secrets **before** starting the container. If the permission is missing, the task fails at the placement stage with an access denied error — the container never starts. There is no lazy fetching or caching mechanism.

---

**Q15.** You need to share an SM secret with a workload in a different AWS account. What is required?

A) Copy the secret to the other account  
B) Add a resource-based policy on the secret granting `GetSecretValue` to the other account's role, AND ensure the KMS CMK key policy allows the other account's role to use the key  
C) Use AWS RAM to share the secret  
D) Grant the other account IAM admin access  

**Answer: B**

Cross-account SM access requires BOTH: (1) SM resource policy granting GetSecretValue to the other account principal, AND (2) KMS key policy granting the other account role Decrypt permission on the CMK. If either is missing, access fails. SM cannot be shared via RAM.

---

**Q16.** What rotation Lambda stages are called in order during Secrets Manager rotation?

A) create → update → verify → complete  
B) createSecret → setSecret → testSecret → finishSecret  
C) generateSecret → pushSecret → validateSecret → activateSecret  
D) newSecret → applySecret → confirmSecret → archiveSecret  

**Answer: B**

The SM rotation Lambda must implement exactly these four steps:
1. **createSecret** — create new secret version (AWSPENDING)
2. **setSecret** — update the actual resource (DB password)
3. **testSecret** — verify new credentials work
4. **finishSecret** — move AWSPENDING → AWSCURRENT

---

**Q17.** A company uses HashiCorp Vault for secrets management. They run workloads on EKS. What AWS-native integration connects Vault to EKS pods?

A) AWS Secrets Store CSI Driver with Vault provider  
B) Direct Lambda integration  
C) SM replication to Vault  
D) ECS native secrets[] field  

**Answer: A**

The AWS Secrets Store CSI Driver supports multiple providers including Vault (via the Vault provider plugin). Pods mount secrets from Vault using the CSI interface with IRSA for authentication. SM replication doesn't push to Vault. ECS secrets[] field only supports SM and SSM.

---

**Q18.** What is the purpose of the `AWSPREVIOUS` label in Secrets Manager?

A) It stores the factory default password  
B) It allows rollback to the last working credential if rotation testing fails  
C) It marks secrets scheduled for deletion  
D) It stores audit history  

**Answer: B**

`AWSPREVIOUS` retains the last successfully active secret version. If rotation fails or the new credentials cause application errors, you can rollback by promoting `AWSPREVIOUS` to `AWSCURRENT`. SM keeps this version for rollback until the next successful rotation.

---

**Q19.** Which approach provides the most complete secrets audit trail in AWS?

A) Enabling VPC Flow Logs  
B) CloudTrail logging for SM API calls (GetSecretValue, CreateSecret, RotateSecret) with CloudWatch Alerts  
C) GuardDuty threat detection  
D) Inspector vulnerability scanning  

**Answer: B**

CloudTrail logs every SM API call including `GetSecretValue` — showing who accessed which secret, when, from where. Combining with CloudWatch Alerts on anomalous access (unusual time, unexpected principal) provides full audit capability. VPC Flow Logs show network traffic. GuardDuty detects threats. Inspector scans software.

---

**Q20.** An ECS task is running with a database password injected at launch time. Secrets Manager rotates the password 2 hours later. What happens to the running task?

A) The task automatically picks up the new password  
B) The running task continues using the old (now rotated) password until it is stopped and restarted  
C) The task crashes immediately  
D) ECS sends a signal to the task to refresh credentials  

**Answer: B**

ECS injects secrets at launch time — the running container has the old value in its environment variables. SM rotation changes the actual DB password, but the ECS task doesn't automatically refresh. Applications must either: (1) implement in-code SM client refresh logic, or (2) be restarted after rotation. This is a critical design consideration.

## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: SM rotation = app automatically refreshes**
> ❌ Wrong: "Rotation ensures all apps immediately use new credentials"
> ✅ Right: Apps must re-call GetSecretValue; ECS tasks need restart; cached values become stale

**Trap 2: SSM SecureString has auto-rotation**
> ❌ Wrong: "SSM SecureString rotates like Secrets Manager"
> ✅ Right: SSM has NO auto-rotation — manual only. Use SM for rotation.

**Trap 3: SM and SSM are interchangeable**
> ❌ Wrong: "Use either SM or SSM — same features"
> ✅ Right: SM = auto-rotation, cross-account, $0.40/mo. SSM = free, no rotation, hierarchical.

**Trap 4: CSI Driver requires Kubernetes Secret in etcd**
> ❌ Wrong: "CSI Driver syncs secrets into Kubernetes Secrets"
> ✅ Right: CSI Driver mounts secrets directly as files — no K8s Secret created (more secure than ESO)

**Trap 5: Base64 in K8s = encrypted**
> ❌ Wrong: "Kubernetes Secrets are encrypted"
> ✅ Right: Base64 is encoding, not encryption. Enable KMS envelope encryption for etcd.

**Trap 6: SM cross-account = only need SM resource policy**
> ❌ Wrong: "SM resource policy alone enables cross-account access"
> ✅ Right: Need BOTH SM resource policy AND KMS key policy (if CMK used)

**Trap 7: Deleting SM secret = instant deletion**
> ❌ Wrong: "Delete immediately removes the secret"
> ✅ Right: SM has a **recovery window** of 7–30 days (default 30). Use `--force-delete-without-recovery` to skip.

**Trap 8: Rotation Lambda tested automatically**
> ❌ Wrong: "SM tests the rotation Lambda before enabling rotation"
> ✅ Right: You must test the rotation Lambda manually before enabling — failed rotation can lock you out.

**Trap 9: Task Definition ARN reference = live refresh**
> ❌ Wrong: "ECS fetches the latest secret value on every API call"
> ✅ Right: ECS fetches at task launch only — value is static for the task's lifetime

**Trap 10: SM regional = global availability**
> ❌ Wrong: "SM secret in us-east-1 is accessible from ap-south-1"
> ✅ Right: SM is regional by default. Use SM replication to other regions for DR.

│ SSM Standard max size            │ 4 KB                    │
│ SSM Advanced max size            │ 8 KB                    │
│ SM auto-rotation                 │ Yes (Lambda-driven)     │
│ SSM auto-rotation                │ No                      │
│ SM cost                          │ $0.40/secret/month      │
│ SSM Standard cost                │ Free                    │
│ SM version labels                │ CURRENT/PENDING/PREVIOUS│
│ Rotation Lambda stages           │ create/set/test/finish  │
│ Zero-downtime rotation           │ Multi-user rotation     │
│ ECS secret injection timing      │ Task launch only        │
│ CSI Driver injection timing      │ Mount + rotation poll   │
│ K8s Secret encryption            │ KMS envelope (etcd)     │
│ Hardcoded secret detection       │ CodeGuru Reviewer       │
│ S3 secret detection              │ Amazon Macie            │
│ Credential abuse detection       │ GuardDuty               │
│ SM audit trail                   │ CloudTrail              │
│ SM cross-account needs           │ SM policy + KMS policy  │
│ SM recovery window               │ 7–30 days default       │
│ SM replication                   │ Cross-region DR         │
└──────────────────────────────────┴─────────────────────────┘
```

## 2.4 Elimination Strategies

**Strategy 1: Auto-rotation needed → Secrets Manager (not SSM)**
Automated credential rotation → eliminate SSM Parameter Store → **Secrets Manager**

**Strategy 2: Zero-downtime rotation → Multi-user**
Production DB rotation with no app downtime → eliminate single-user → **multi-user rotation**

**Strategy 3: Detect hardcoded secrets in code → CodeGuru**
Static analysis of source code → eliminate GuardDuty/Macie → **CodeGuru Reviewer**

**Strategy 4: Detect secrets in S3 objects → Macie**
Scan S3 data for credentials → eliminate GuardDuty/Config → **Amazon Macie**

**Strategy 5: Cross-account SM → SM policy + KMS policy**
Share secret across accounts → eliminate "IAM alone" → **SM resource policy AND KMS key policy**

**Strategy 6: EKS secrets without K8s etcd exposure → CSI Driver**
Most secure EKS injection → eliminate ESO/K8s Secrets → **Secrets Store CSI Driver**

## 1.1 Service Overview & Purpose

### What is AWS Config?
AWS Config is a **continuous configuration assessment, audit, and compliance service**. It records the configuration state of AWS resources over time, evaluates configurations against desired rules, and provides a timeline of configuration changes.

Think of Config as a **CCTV system for your AWS resource configurations** — it doesn't prevent changes, but it records everything and alerts you when something drifts from the desired state.

### Why Does It Exist?
```
Problems Config Solves:
├── "When did someone open port 22 to 0.0.0.0/0?"
├── "What did this security group look like 3 months ago?"
├── "Is encryption enabled on all S3 buckets right now?"
├── "Which EC2 instances are missing required tags?"
├── "Did anyone change the root MFA setting this week?"
├── "Are all CloudTrail trails enabled across all regions?"
└── "Show me everything that changed before the breach"
```

### Exam Weight & Importance
- **Domain 4: Identity & Access Management** + **Domain 2: Logging & Monitoring**
- Compliance and governance questions heavily feature Config
- Expect **4–6 questions** — one of the highest-frequency services in the exam
- Commonly tested: Config rules vs SCPs, conformance packs, remediation actions, Config aggregator

## 1.3 Deep Dive — Every Sub-Topic

### A. Configuration Recorder

Records configuration changes for supported AWS resource types.

**Key points:**
- One recorder **per region per account**
- Can record all resources or specific types
- Stores data in a **Config delivery channel** → S3 bucket
- Also sends notifications via SNS
- Configuration items include: resource ID, type, tags, relationships, config attributes, event time

⚠️ **Gotcha:** Config recorder must be **turned on** — it is NOT enabled by default. Many organizations skip this, leaving a gap in their audit trail.

---

### B. Config Rules

Rules evaluate whether resource configurations comply with desired settings.

**Three types of Config rules:**

| Type | Who Defines | Trigger | Latency |
|---|---|---|---|
| AWS Managed Rules | AWS (pre-built ~300+) | Change-triggered or periodic | Near real-time |
| Custom Lambda Rules | You (Lambda) | Change-triggered or periodic | Near real-time |
| Proactive Rules | AWS Managed | Before deployment (CloudFormation) | Pre-deployment |

**Common exam-relevant managed rules:**

| Rule | What It Checks |
|---|---|
| `s3-bucket-public-read-prohibited` | No S3 buckets allow public read |
| `encrypted-volumes` | All EBS volumes encrypted |
| `root-account-mfa-enabled` | Root account has MFA |
| `cloudtrail-enabled` | CloudTrail is active |
| `vpc-sg-open-only-to-authorized-ports` | No open security groups |
| `iam-password-policy` | IAM password policy meets requirements |
| `rds-instance-public-access-check` | RDS not publicly accessible |
| `access-keys-rotated` | IAM access keys rotated within N days |
| `iam-root-access-key-check` | Root account has no access keys |
| `multi-region-cloudtrail-enabled` | Multi-region CloudTrail active |

⚠️ **Gotcha:** Config rules **evaluate** compliance but do NOT **prevent** non-compliant changes. To prevent, use SCPs (AWS Organizations) or IAM policies.

---

### C. Conformance Packs

A **conformance pack** is a collection of Config rules and remediation actions deployed together as a single unit.

**AWS pre-built conformance packs:**
- `Operational Best Practices for CIS AWS Foundations Benchmark`
- `Operational Best Practices for PCI DSS`
- `Operational Best Practices for HIPAA`
- `Operational Best Practices for NIST 800-53`
- `AWS Control Tower Guardrails as Conformance Pack`

**Benefits:**
- Deploy 50+ rules with one action
- Organization-wide deployment via Config aggregator
- Pre-mapped to compliance frameworks

⚠️ **Gotcha:** Conformance packs are **read-only** — you can't edit individual rules within them. For customization, build your own pack.

---

### D. Config Aggregator

Aggregates Config data from **multiple accounts and regions** into a single account.

```
Account A (ap-south-1) ─────┐
Account B (us-east-1)  ─────┤──▶ Config Aggregator (Management Account)
Account C (eu-west-1)  ─────┤    ├── View all compliance data
Account D (ap-south-1) ─────┘    ├── Cross-account compliance dashboard
                                  └── Organization-wide rule evaluation
```

**Two types:**
- **Account-based aggregator** — specific accounts listed
- **Organization-based aggregator** — uses AWS Organizations, auto-includes all accounts

⚠️ **Gotcha:** Member accounts must **authorize** the aggregator account — Config doesn't automatically aggregate without authorization. Organizations aggregator bypasses this requirement.

---

### E. Remediation Actions

Config can trigger automated remediation when a rule finds non-compliance.

**Remediation modes:**
- **Manual remediation** — triggers SSM Automation document, but requires human to click
- **Automatic remediation** — triggers SSM Automation document automatically on non-compliance

**Common remediation examples:**

| Non-Compliance | Remediation Action |
|---|---|
| S3 bucket public access enabled | `AWS-DisableS3BucketPublicReadWrite` |
| EC2 instance with public IP in private subnet | `AWS-StopEC2Instance` |
| Security group with port 22 open to world | `AWS-DisablePublicAccessForSecurityGroup` |
| EBS volume not encrypted | Snapshot + encrypt + replace |

⚠️ **Gotcha:** Auto-remediation can cause outages if not tested. A misconfigured remediation could stop production EC2 instances. Always test with manual remediation first.

---

### F. Config vs Other Services

| Scenario | Use Config | Use Instead |
|---|---|---|
| Detect non-compliant S3 bucket | ✅ | — |
| Prevent non-compliant S3 creation | ❌ | SCP / IAM / S3 Block Public Access |
| Real-time threat detection | ❌ | GuardDuty |
| Network traffic monitoring | ❌ | VPC Flow Logs |
| Configuration history (who changed what) | ✅ (Config) + CloudTrail | — |
| Multi-account compliance dashboard | ✅ (Aggregator) | — |
| Pre-deployment compliance check | ✅ (Proactive rules + CloudFormation) | — |

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** A security team wants to know if any S3 bucket in the last 90 days had public access enabled, even briefly. Which service provides this historical view?

A) CloudTrail  
B) AWS Config configuration history  
C) S3 Access Logs  
D) Amazon Macie  

**Answer: B**

AWS Config records the configuration state of S3 buckets over time, including public access settings. The configuration timeline shows every state change, making it easy to see if public access was ever enabled. CloudTrail shows API calls but not the resulting configuration state. S3 logs show access patterns. Macie classifies data.

---

**Q2.** A company wants to ensure all new EBS volumes are encrypted. They want non-compliant volumes detected AND automatically encrypted. What services accomplish this?

A) AWS Config rule (`encrypted-volumes`) + SSM Automation remediation  
B) CloudTrail + Lambda  
C) GuardDuty + SNS  
D) Security Hub + Config  

**Answer: A**

Config rule `encrypted-volumes` detects non-compliant EBS volumes. SSM Automation document attached as remediation action can automatically snapshot, encrypt, and replace the volume. This covers both detection and remediation. CloudTrail+Lambda could work but is custom-built. GuardDuty doesn't check encryption. Security Hub aggregates but doesn't remediate.

---

**Q3.** An enterprise has 200 AWS accounts. They want a single dashboard showing PCI-DSS compliance posture across all accounts. Which Config feature provides this?

A) Config Rules deployed in each account manually  
B) Config Aggregator with Organization-based source + PCI-DSS conformance pack  
C) Security Hub across all accounts  
D) Trusted Advisor Enterprise  

**Answer: B**

Config Aggregator with Organization source automatically includes all 200 accounts. Deploying the PCI-DSS conformance pack organization-wide gives a centralized compliance dashboard. Security Hub also aggregates findings but for this use case, Config conformance packs + aggregator is the targeted answer. Trusted Advisor doesn't map to PCI-DSS rules.

---

**Q4.** AWS Config rule `s3-bucket-public-read-prohibited` finds a non-compliant bucket. Can Config prevent the bucket from being created in the first place?

A) Yes — Config rules can block resource creation  
B) No — Config detects non-compliance after the fact. Use SCPs or IAM policies to prevent creation.  
C) Yes — with auto-remediation enabled  
D) Yes — using proactive rules with CloudFormation  

**Answer: B** (with note on D)

Config rules are **detective controls** — they evaluate existing resource configurations and flag non-compliance. They do NOT prevent API calls. To prevent public bucket creation: use SCP `s3:PutBucketPublicAccessBlock` deny, or enable S3 Block Public Access at account/org level.

Note: Proactive rules (D) check CloudFormation templates before deployment — a form of prevention for IaC, but not for all resource creation methods.

---

**Q5.** What is a conformance pack in AWS Config?

A) A collection of CloudFormation templates  
B) A collection of Config rules and optional remediation actions packaged together, mappable to compliance frameworks  
C) A collection of IAM policies  
D) A collection of CloudTrail trails  

**Answer: B**

A conformance pack bundles multiple Config rules + optional SSM remediation actions into a single deployable unit. AWS provides pre-built packs for CIS, PCI-DSS, HIPAA, NIST. Organizations can build custom packs. They can be deployed to all accounts via Organization-level conformance packs.

---

**Q6.** Config reports a resource as `NON_COMPLIANT`. What does this mean?

A) The resource is currently broken or down  
B) The resource's current configuration does not meet the conditions defined in the Config rule  
C) The resource was created without proper tagging  
D) The resource has a security vulnerability  

**Answer: B**

`NON_COMPLIANT` means the resource configuration fails the rule's evaluation logic. The resource is still running — just configured in a way that violates the rule. It doesn't imply a security incident, just a configuration drift from desired state.

---

**Q7.** A company wants Config to evaluate compliance of resources BEFORE they are provisioned via CloudFormation. Which Config feature enables this?

A) Custom Lambda rules  
B) Conformance packs  
C) Proactive rules  
D) Config aggregator  

**Answer: C**

**Proactive rules** integrate with CloudFormation to evaluate resource configurations in a stack before the stack is deployed. Non-compliant configurations cause the stack deployment to fail, preventing non-compliant resources from ever being created.

---

**Q8.** What must be true for a Config aggregator to collect data from accounts in an AWS Organization?

A) Each account must have identical Config rules  
B) Each account must have Config recorder enabled, and the organization management account must enable Config for the organization  
C) All accounts must be in the same region  
D) Accounts must grant root access to the aggregator account  

**Answer: B**

The Config recorder must be enabled in each account/region to record configurations. The Organization-based aggregator uses the management account's Organizations trust — member accounts don't need individual authorization as with account-based aggregators. Accounts can be in different regions. Root access is never required.

---

**Q9.** What is the difference between Config configuration history and Config snapshots?

A) They are identical  
B) Configuration history records every change over time per resource; snapshots capture the state of ALL resources at a point in time  
C) Snapshots are real-time; history is monthly  
D) History is in DynamoDB; snapshots are in S3  

**Answer: B**

**Configuration history** — per-resource timeline of every state change (delivered to S3 as Config items).
**Configuration snapshots** — full-state capture of all recorded resources at a point in time, delivered to S3 on schedule. Both are stored in the Config delivery S3 bucket.

---

**Q10.** Which combination provides both WHO changed a resource AND WHAT the resource looked like before and after the change?

A) GuardDuty + Macie  
B) CloudTrail (who changed) + AWS Config (what it looked like before/after)  
C) CloudWatch + Config  
D) Config alone  

**Answer: B**

Config records the configuration state before and after a change with timestamps. CloudTrail records the API call that caused the change with the caller's identity. Together they answer: "At 14:32 UTC, John Doe (IAM user) called `AuthorizeSecurityGroupIngress` — here's what the SG looked like before and after."

---

**Q11.** A custom Config rule needs to evaluate whether EC2 instances have a specific tag. What is used to build this custom rule?

A) AWS CloudFormation template  
B) AWS Lambda function that receives Config events and returns COMPLIANT or NON_COMPLIANT  
C) AWS Step Functions  
D) AWS Systems Manager document  

**Answer: B**

Custom Config rules use a Lambda function as the evaluator. Config invokes the Lambda with the configuration item data. The Lambda evaluates the configuration and calls `PutEvaluations` API with COMPLIANT, NON_COMPLIANT, or NOT_APPLICABLE status per resource.

---

**Q12.** A Config auto-remediation action is configured to stop non-compliant EC2 instances. A production instance is incorrectly flagged as non-compliant. What happens?

A) Config will alert but not act automatically  
B) Config automatically stops the production instance — causing an outage  
C) Config waits for human approval  
D) The auto-remediation only applies to test accounts  

**Answer: B**

Auto-remediation executes without human intervention. This is why testing with manual remediation first is critical. Incorrect rule logic or false positives in auto-remediation mode can cause production outages. Always test, add retries with delays, and consider excluding production resources from auto-remediation.

---

**Q13.** Which Config managed rule checks that AWS CloudTrail is enabled and logging to S3?

A) `cloudtrail-s3-dataevents-enabled`  
B) `cloudtrail-enabled`  
C) `multi-region-cloudtrail-enabled`  
D) Both B and C for full coverage  

**Answer: D**

`cloudtrail-enabled` — verifies at least one CloudTrail trail is enabled.
`multi-region-cloudtrail-enabled` — verifies a trail covering all regions.
Both are needed for full coverage. Many compliance frameworks require multi-region CloudTrail as a specific requirement.

---

**Q14.** An organization wants to deploy the same 40 Config rules across all 150 accounts in AWS Organizations simultaneously. What is the most efficient approach?

A) Deploy rules account by account using AWS CLI  
B) Use CloudFormation StackSets  
C) Use Organization Conformance Pack  
D) Use Config aggregator with manual sync  

**Answer: C**

Organization Conformance Packs deploy a set of Config rules to ALL accounts in an organization simultaneously from the management account. They handle new accounts automatically. CloudFormation StackSets can also do this but requires more setup. CLI and manual sync are operationally impractical at 150 accounts.

---

**Q15.** Config rule `iam-root-access-key-check` returns NON_COMPLIANT. What does this indicate?

A) Root account MFA is disabled  
B) The root account has active access keys (which should never exist)  
C) Root account password is expired  
D) Root account has too many IAM policies  

**Answer: B**

This rule checks specifically that the root account has no access keys. Root access keys are a critical security risk — they have unrestricted access and cannot be restricted by SCPs or IAM policies. The immediate remediation is to delete the root access keys. Root MFA is a separate rule (`root-account-mfa-enabled`).

---

**Q16.** What happens to Config data when a resource is deleted?

A) Config data is immediately deleted  
B) Config continues to retain the configuration history and marks the resource as DELETED  
C) Config creates a backup of the resource  
D) Config sends an alert but loses the history  

**Answer: B**

Config marks deleted resources as `DELETED` in the configuration timeline and **retains the full history** for the configured retention period (default 7 years). This is valuable for forensic analysis — you can see the complete lifecycle of a deleted resource including its configuration at time of deletion.

---

**Q17.** A Config rule is triggered `PERIODICALLY` rather than on changes. What does this mean?

A) The rule runs only when manually triggered  
B) The rule evaluates all in-scope resources on a schedule (1hr, 3hr, 6hr, 12hr, 24hr) rather than on every configuration change  
C) The rule runs continuously  
D) The rule runs only during maintenance windows  

**Answer: B**

Periodic rules run on a schedule independent of configuration changes. Useful for rules that can't be change-triggered (e.g., checking whether MFA has been used recently, validating time-based compliance). Change-triggered rules run when Config detects a configuration change to an in-scope resource.

---

**Q18.** Config delivers configuration snapshots to which destination?

A) CloudWatch Logs  
B) DynamoDB  
C) S3 bucket (configured delivery channel)  
D) SNS only  

**Answer: C**

Config uses a **delivery channel** to deliver configuration history files and snapshots to an **S3 bucket**. SNS is used for **notifications** (compliance changes, delivery status). Config data is not stored in CloudWatch Logs or DynamoDB natively.

---

**Q19.** Which Config rule is most relevant for detecting IAM access keys that haven't been rotated?

A) `iam-user-mfa-enabled`  
B) `access-keys-rotated`  
C) `iam-password-policy`  
D) `iam-root-access-key-check`  

**Answer: B**

`access-keys-rotated` evaluates whether IAM user access keys have been rotated within the configured number of days (default 90 days). Non-compliant = key older than the threshold. This is a key CIS Benchmark requirement.

---

**Q20.** A security architect wants Config to automatically disable public access on S3 buckets that are found non-compliant. What is the correct architecture?

A) Config rule + CloudWatch Alarm + Lambda  
B) Config rule → EventBridge → Lambda  
C) Config rule with SSM Automation remediation action (`AWS-DisableS3BucketPublicReadWrite`)  
D) Macie → Config → remediation  

**Answer: C**

AWS Config supports native remediation actions via SSM Automation. The `AWS-DisableS3BucketPublicReadWrite` SSM Automation document can be attached as the remediation action for the S3 public access rule — either manual or automatic. This is the native Config-native approach without building custom Lambda functions.

## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: Config prevents non-compliant changes**
> ❌ Wrong: "Config rule blocks non-compliant S3 bucket creation"
> ✅ Right: Config DETECTS. SCP/IAM PREVENTS. Config is a detective control.

**Trap 2: Config is enabled by default**
> ❌ Wrong: "Config automatically records all resource changes"
> ✅ Right: Config recorder must be MANUALLY enabled per region

**Trap 3: Conformance packs = editable rule sets**
> ❌ Wrong: "Edit individual rules within a conformance pack"
> ✅ Right: Conformance packs are immutable — build custom packs for customization

**Trap 4: Config aggregator auto-collects without authorization**
> ❌ Wrong: "Config aggregator pulls data from all accounts automatically"
> ✅ Right: Account-based aggregator needs member account authorization; Organization aggregator bypasses this

**Trap 5: Auto-remediation is always safe**
> ❌ Wrong: "Enable auto-remediation for all rules immediately"
> ✅ Right: Auto-remediation can cause outages — test with manual first, use retries and delays

**Trap 6: NON_COMPLIANT = resource is broken**
> ❌ Wrong: "NON_COMPLIANT means the resource has failed"
> ✅ Right: NON_COMPLIANT means configuration doesn't match the rule — resource may be fully functional

**Trap 7: Config shows WHO made the change**
> ❌ Wrong: "Config records the API caller for each change"
> ✅ Right: Config shows WHAT changed. CloudTrail shows WHO changed it. Use both.

**Trap 8: Config rules run continuously**
> ❌ Wrong: "Config rules evaluate every second"
> ✅ Right: Change-triggered rules fire on config changes; periodic rules run on schedule

**Trap 9: Config data deleted when resource deleted**
> ❌ Wrong: "Deleting a resource removes its Config history"
> ✅ Right: Config retains full history of deleted resources, marked as DELETED

**Trap 10: Conformance packs require custom rules**
> ❌ Wrong: "You must write Lambda functions for conformance packs"
> ✅ Right: AWS provides pre-built conformance packs for major frameworks using managed rules

## 2.4 Elimination Strategies

**Strategy 1: Detect config drift → Config**
Historical configuration, compliance check, timeline view → eliminate CloudTrail alone → **AWS Config**

**Strategy 2: Prevent non-compliant resource → SCP/IAM**
"Prevent creation of..." → eliminate Config → **SCP (Organizations) or IAM Deny**

**Strategy 3: Multi-account compliance dashboard → Aggregator + Conformance Pack**

## 1.3 Deep Dive — Every Sub-Topic

### A. Service Control Policies (SCPs) — Deep Dive

SCPs are the **most important Organizations feature for the security exam**.

**What SCPs do:**
- Define the **maximum permissions boundary** for accounts in an OU or specific account
- Applied to all principals in the account (including root user in member accounts)
- Work as a **filter** on top of IAM — they don't grant permissions, they restrict the ceiling

**The SCP and IAM Interaction Model:**
```
Effective Permission = SCP ∩ IAM Policy

Both must ALLOW the action:
├── SCP allows + IAM allows = ✅ ALLOWED
├── SCP allows + IAM denies = ❌ DENIED
├── SCP denies + IAM allows = ❌ DENIED
└── SCP denies + IAP denies = ❌ DENIED

Remember: SCPs do NOT apply to management account (ever)
         SCPs do NOT grant permissions — only restrict
```

**FullAWSAccess SCP:**
AWS attaches `FullAWSAccess` SCP to every OU and account by default — this allows all actions. You layer deny SCPs on top, or replace with an allow-list approach.

**Deny-list vs Allow-list approach:**

| Approach | Default State | Management Style |
|---|---|---|
| Deny-list | FullAWSAccess + specific denies | Allow all, explicitly block risky actions |
| Allow-list | Remove FullAWSAccess + explicit allows | Block all, explicitly allow needed services |

⚠️ **Gotcha:** SCPs do NOT apply to the **management account** — this is the most tested SCP gotcha. The management account can always do anything regardless of SCPs attached to root.

⚠️ **Gotcha:** SCPs do NOT affect **service-linked roles** — AWS-managed roles used by services are not restricted by SCPs.

---

### B. Common SCP Patterns

**Deny specific regions:**
```json
{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": ["ap-south-1", "us-east-1"]
    }
  }
}
```

**Deny deletion of security services:**
```json
{
  "Effect": "Deny",
  "Action": [
    "cloudtrail:DeleteTrail",
    "cloudtrail:StopLogging",
    "config:DeleteConfigRule",
    "guardduty:DeleteDetector",
    "securityhub:DisableSecurityHub"
  ],
  "Resource": "*"
}
```

**Require encryption on S3:**
```json
{
  "Effect": "Deny",
  "Action": "s3:PutObject",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "s3:x-amz-server-side-encryption": "aws:kms"
    }
  }
}
```

### C. Organizations Structure — Management vs Member Accounts

| Aspect | Management Account | Member Account |
|---|---|---|
| SCP applicability | SCPs never apply here | SCPs fully apply |
| Services to deploy here | Billing, Organizations, Control Tower | Workloads |
| Best practice | Minimal use — just governance | All actual workloads |
| Cross-account trust | Implicit trust with all members | Explicit only |
| GuardDuty admin | Delegated to security account | — |

**Delegated administrator pattern:**
For most security services, the **management account delegates administration** to a dedicated **security tooling account**:
- GuardDuty: delegate to security account
- Security Hub: delegate to security account
- Config: use aggregator in security account
- Macie: delegate to security account

This keeps the management account clean and reduces blast radius.

---

### D. Tag Policies

Tag policies enforce consistent tagging across the organization.

```json
{
  "tags": {
    "Environment": {
      "tag_key": { "@@assign": "Environment" },
      "tag_value": {
        "@@assign": ["Production", "Development", "Staging"]
      },
      "enforced_for": {
        "@@assign": ["ec2:instance", "s3:bucket"]
      }
    }
  }
}
```

⚠️ **Gotcha:** Tag policies in **report mode** only flag non-compliant tags — they do NOT prevent resource creation with wrong tags. To enforce, you need SCPs or Config rules.

---

### E. Backup Policies

Centrally enforce AWS Backup plans across all accounts/OUs.

- Define backup frequency, retention, vault
- Applied via Organizations to all member accounts
- Cannot be overridden by member account admins

---

### F. Organizations Trust and Cross-Account Access

**Cross-account role assumption pattern:**
```
Developer in Account A 
  → AssumeRole → Role in Account B 
  → Account B role has required permissions
  → SCP in Account B must also allow the action
```

**Important:** Even if a cross-account role grants S3 access, the SCP on Account B must also allow `s3:GetObject` — both the role policy AND the SCP must permit the action.

## 1.5 Security & Compliance Angles

### Critical SCP Best Practices

1. **Never use management account for workloads** — SCPs don't apply there
2. **Protect security services from deletion** — SCP deny on CloudTrail/Config/GuardDuty delete
3. **Restrict to approved regions** — deny actions in unauthorized regions
4. **Require encryption** — SCP deny on unencrypted S3/EBS creation
5. **Prevent root access key creation** — `iam:CreateAccessKey` deny when username is root

### Common Misconfigurations

1. Deploying workloads in management account (SCPs don't protect it)
2. Expecting SCPs to apply to management account — they never do
3. Confusing SCP allow with actual permission grant — SCPs don't grant
4. Forgetting that service-linked roles bypass SCPs
5. Tag policies in report mode thinking they enforce tags

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** An SCP at the root level denies `ec2:TerminateInstances`. An IAM admin in the management account tries to terminate an EC2 instance. What happens?

A) The action is denied because root-level SCP applies to all  
B) The action succeeds because SCPs do NOT apply to the management account  
C) The action requires MFA  
D) The action is partially allowed  

**Answer: B**

SCPs **never apply to the management account** — this is the most critical SCP gotcha. The management account is exempt from all SCPs regardless of where they are attached (root, OU, or account level). This is why workloads should never be in the management account.

---

**Q2.** An IAM user in a member account has `AdministratorAccess`. An SCP on the account allows only `s3:*`. Can the user create an EC2 instance?

A) Yes — AdministratorAccess overrides SCPs  
B) No — the effective permission is the intersection: SCP allows s3:* only, so EC2 actions are denied  
C) Yes — AdministratorAccess includes SCP bypass  
D) It depends on the account's root user  

**Answer: B**

Effective permission = SCP ∩ IAM. The SCP restricts the ceiling to `s3:*` only. Even with `AdministratorAccess`, the user cannot perform EC2 actions because the SCP doesn't allow them. SCPs define the maximum — IAM can only operate within that maximum.

---

**Q3.** A company wants to prevent all accounts from disabling GuardDuty. Where should the SCP be attached for maximum coverage?

A) Individual account level  
B) Root of the organization  
C) Management account only  
D) Security OU only  

**Answer: B**

Attaching the SCP at the **root** applies it to all OUs and accounts in the organization (except the management account). Attaching at individual accounts or specific OUs leaves gaps. Management account is exempt from SCPs anyway.

---

**Q4.** What does `FullAWSAccess` SCP mean, and why is it important?

A) It grants all AWS actions to all principals  
B) It is the default SCP that allows all actions — without it, all API calls in the account are implicitly denied by SCPs  
C) It allows only AWS-managed services to operate  
D) It grants the management account access to all member accounts  

**Answer: B**

SCPs work on an **implicit deny** model — if no SCP allows an action, it's denied. `FullAWSAccess` is the default SCP applied to all OUs/accounts that allows all actions, ensuring accounts work normally. If you accidentally remove it without adding specific allows, all API calls in that account fail.

---

**Q5.** A developer in a member account has an IAM role with `sts:AssumeRole` permission. An SCP on their account does NOT include `sts:AssumeRole` in its allow list. Can they assume a role?

A) Yes — role assumption is always allowed  
B) No — the SCP must allow the action; without it in the allow list, `sts:AssumeRole` is denied  
C) Yes — if the target role is in the same account  
D) It depends on the trust policy of the target role  

**Answer: B**

With an allow-list SCP approach, any action not in the allow list is denied. `sts:AssumeRole` must be explicitly allowed in the SCP for role assumption to work. This is a common misconfiguration when implementing restrictive SCPs — forgetting to include `sts:AssumeRole` breaks many services.

---

**Q6.** What is a delegated administrator in AWS Organizations?

A) An IAM user with admin access in the management account  
B) A member account granted administrative rights for a specific AWS service across the organization  
C) An OU with full AWS access  
D) A cross-account IAM role  

**Answer: B**

Delegated administrator allows a **designated member account** (typically a security tooling account) to manage a specific AWS service (GuardDuty, Security Hub, Config, Macie) across the entire organization — without needing to use the management account. Best practice: use management account only for Organizations/billing, delegate security services to security tooling account.

---

**Q7.** An SCP contains only a Deny statement for `cloudtrail:DeleteTrail`. What is the effect?

A) All CloudTrail actions are denied  
B) Only `DeleteTrail` is denied; all other CloudTrail actions are allowed (assuming FullAWSAccess is still attached)  
C) All S3 logging is disabled  
D) CloudTrail is completely disabled  

**Answer: B**

SCPs use explicit evaluation. With `FullAWSAccess` still attached (which allows everything), adding a specific Deny SCP only blocks that specific action. All other CloudTrail actions (`CreateTrail`, `StartLogging`, `GetTrailStatus`, etc.) remain allowed.

---

**Q8.** A company wants to ensure all new accounts created via Organizations automatically have GuardDuty enabled. What is the BEST approach?

A) Create a manual checklist for each new account  
B) Enable GuardDuty with Organizations integration — auto-enable for new member accounts  
C) Use Lambda to poll for new accounts and enable GuardDuty  
D) Require each account owner to enable it manually  

**Answer: B**

GuardDuty Organizations integration has an **auto-enable** setting. When a new account joins the organization, GuardDuty is automatically enabled in that account. This is the native, zero-touch approach. Lambda polling is a custom workaround. Manual processes are error-prone.

---

**Q9.** An SCP denies `iam:CreateUser`. A developer's IAM policy allows `iam:CreateUser`. Can they create an IAM user?

A) Yes — IAM policy overrides SCP  
B) No — SCP Deny takes precedence over IAM Allow  
C) Only if they have MFA  
D) Only for service accounts  

**Answer: B**

SCP explicit Deny always wins. The evaluation logic: if ANY Deny policy (SCP, IAM, permissions boundary) matches — access is denied. An IAM Allow cannot override an SCP Deny.

---

**Q10.** Which Organizations policy type enforces consistent AWS Backup plans across all accounts?

A) SCP  
B) Tag policy  
C) Backup policy  
D) AI services opt-out policy  

**Answer: C**

**Backup policies** in AWS Organizations centrally define and apply AWS Backup plans to all accounts/OUs. Unlike SCPs (which restrict permissions), backup policies actively create backup plans in member accounts. Tag policies enforce tagging. SCPs restrict API calls.

---

**Q11.** A company uses an allow-list SCP approach. They remove `FullAWSAccess` and add specific service allows. A new Lambda function cannot write to CloudWatch Logs. What is the likely cause?

A) Lambda execution role is missing  
B) `logs:CreateLogGroup`, `logs:CreateLogStream`, `logs:PutLogEvents` are not included in the SCP allow list  
C) CloudWatch is a global service not restricted by SCPs  
D) Lambda is exempt from SCPs  

**Answer: B**

Allow-list SCPs require explicitly listing every action needed. CloudWatch Logs permissions must be in the SCP. This is a common oversight — teams add compute service permissions but forget the logging actions. Review Lambda's Basic Execution Role permissions and ensure all those actions are in the SCP.

---

**Q12.** Where can SCPs be attached in an organization? (Select all valid options)

A) Root only  
B) Root, specific OUs, specific member accounts  
C) Individual IAM roles  
D) Management account only  

**Answer: B**

SCPs can be attached to: the **root** (applies to all), specific **OUs** (applies to all accounts in that OU and child OUs), or specific **member accounts**. They cannot be attached to individual IAM principals (roles/users) — that's what IAM policies and permission boundaries do.

---

**Q13.** A security team wants to prevent member accounts from leaving the organization. Which control achieves this?

A) SCP denying `organizations:LeaveOrganization`  
B) IAM policy in each account  
C) Config rule monitoring organization membership  
D) CloudTrail alerting on leave attempts  

**Answer: A**

An SCP with `"Action": "organizations:LeaveOrganization", "Effect": "Deny"` prevents any principal in member accounts from removing the account from the organization. This is a critical security guardrail — without it, a compromised account could exit the org and escape SCP controls.

---

**Q14.** What is the maximum number of SCPs that can be attached to a single OU or account?

A) 1  
B) 5  
C) 10  
D) Unlimited  

**Answer: B**

A maximum of **5 SCPs** can be attached to any single entity (root, OU, or account). This encourages combining related policies. Note: FullAWSAccess counts as one of the 5 if left attached.

---

**Q15.** An organization wants to deny all actions except in ap-south-1 and us-east-1. Which SCP condition achieves this?

A) `"aws:RequestedRegion": ["ap-south-1", "us-east-1"]` with Deny  
B) `"StringNotEquals": { "aws:RequestedRegion": ["ap-south-1", "us-east-1"] }` with Deny on `*`  
C) Allow only `ec2:*` in those regions  
D) Block all regions in IAM policies  

**Answer: B**

Deny all actions where `aws:RequestedRegion` is NOT in the approved list. This effectively blocks all API calls to other regions. The condition `StringNotEquals` with the approved regions list in a Deny SCP is the correct pattern.

---

**Q16.** Service-linked roles in member accounts — are they affected by SCPs?

A) Yes — SCPs fully restrict service-linked roles  
B) No — service-linked roles bypass SCP restrictions  
C) Only if the SCP explicitly names the service-linked role  
D) Only in the management account  

**Answer: B**

Service-linked roles are AWS-managed roles that enable AWS services to perform actions on your behalf. They are **not restricted by SCPs**. This means even a very restrictive SCP cannot prevent AWS services (like CloudTrail, Config, GuardDuty) from performing their required operations using service-linked roles.

---

**Q17.** What is the recommended account structure for an enterprise landing zone?

A) One account per application  
B) Management Account + Security OU (tooling + log archive) + Workloads OU (prod/dev) + Sandbox OU  
C) Two accounts: production and development  
D) One account per AWS region  

**Answer: B**

AWS recommended landing zone structure:
- **Management Account** — Organizations, billing, governance only
- **Security OU** — Security-Tooling (GuardDuty admin, Security Hub admin) + Log-Archive (CloudTrail, Config logs)
- **Workloads OU** — Production OU + Development OU + Staging OU
- **Sandbox OU** — Free experimentation with restrictions

---

**Q18.** An SCP deny statement has no `Condition` block. A principal has `aws:MultiFactorAuthPresent: true`. Is the deny still applied?

A) No — MFA presence exempts from SCP denies  
B) Yes — an unconditional Deny SCP applies regardless of any request attributes  
C) Only for IAM users, not roles  
D) Depends on the IAM policy  

**Answer: B**

An unconditional Deny SCP (no Condition block) applies to ALL requests matching the Action and Resource, regardless of MFA, source IP, time, or any other attribute. To create an MFA-conditional deny, you would add `"Condition": {"BoolIfExists": {"aws:MultiFactorAuthPresent": "false"}}`.

---

**Q19.** What happens when an account moves from OU-A to OU-B?

A) The account retains OU-A's SCPs until manually removed  
B) The account immediately loses OU-A's SCPs and gains OU-B's SCPs  
C) All resources in the account are terminated  
D) The account becomes temporarily unmanaged  

**Answer: B**

SCP inheritance is **immediate** when accounts move between OUs. The account instantly loses all SCPs from the source OU chain and gains all SCPs from the destination OU chain. This can have immediate impact on what principals in that account can do — plan account moves carefully.

---

**Q20.** A company wants a read-only audit account that can view all CloudTrail logs across 500 accounts. What is the architecture?

A) Grant the audit account root access to all member accounts  
B) Create an Organization CloudTrail with logs delivered to S3 in Log-Archive account; grant audit account read access to that S3 bucket  
C) Install CloudTrail forwarders in each account  
D) Use GuardDuty findings only  

**Answer: B**

Organization CloudTrail captures all API events from all accounts in one trail, delivering to a centralized S3 bucket in the Log-Archive account. Granting the audit account S3 read access (no S3 delete) gives auditors full visibility. The bucket should have MFA delete enabled and versioning to prevent tampering.

## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: SCPs apply to management account**
> ❌ Wrong: "Root-level SCP applies to management account"
> ✅ Right: SCPs NEVER apply to management account — ever

**Trap 2: SCPs grant permissions**
> ❌ Wrong: "Add the action to the SCP to allow it"
> ✅ Right: SCPs only RESTRICT. IAM policies GRANT. Both must allow for access.

**Trap 3: FullAWSAccess removal = all denied**
> ❌ Wrong: "Removing FullAWSAccess and adding specific denies is equivalent"
> ✅ Right: Removing FullAWSAccess WITHOUT adding allows = all API calls denied. SCPs have implicit deny.

**Trap 4: Service-linked roles obey SCPs**
> ❌ Wrong: "SCP can block AWS services' service-linked roles"
> ✅ Right: Service-linked roles bypass SCPs — AWS services always can perform required operations

**Trap 5: Tag policies enforce tagging**
> ❌ Wrong: "Tag policy prevents resource creation without required tags"
> ✅ Right: Tag policies in report mode only detect — they don't prevent. Use SCPs to enforce.

**Trap 6: SCP Deny can be overridden by IAM Allow**
> ❌ Wrong: "AdminAccess can override SCP Deny"
> ✅ Right: SCP Deny always wins over any IAM Allow — no exceptions

**Trap 7: SCPs apply to individual IAM principals**
> ❌ Wrong: "Attach SCP to a specific IAM role"
> ✅ Right: SCPs attach to accounts, OUs, or root — not to IAM principals

**Trap 8: Moving account between OUs has delayed SCP effect**
> ❌ Wrong: "Account retains old OU SCPs for 24 hours after move"
> ✅ Right: SCP changes are immediate when account moves between OUs

**Trap 9: Management account delegating admin = giving up control**
> ❌ Wrong: "Delegating GuardDuty admin removes management account control"
> ✅ Right: Delegated admin is additive — security account gets admin rights; management account doesn't lose control

**Trap 10: 5 SCP limit is per policy type**
> ❌ Wrong: "You can attach unlimited SCPs to an OU"
> ✅ Right: Maximum 5 SCPs per entity (root/OU/account)

## 1.3 Deep Dive — Every Sub-Topic

### A. Guardrails (Controls)

Guardrails are the governance rules enforced by Control Tower. They are now officially called **Controls**.

**Three behavior types:**

| Type | Implementation | What It Does |
|---|---|---|
| Preventive | SCP | Blocks non-compliant API calls |
| Detective | Config Rule | Detects non-compliant configurations |
| Proactive | CloudFormation Hook | Checks resources before deployment |

**Three enforcement types:**

| Category | Default State | Can Disable? |
|---|---|---|
| Mandatory | Always ON | ❌ No |
| Strongly Recommended | ON | ✅ Yes |
| Elective | OFF | ✅ Can enable |

**Examples of Mandatory guardrails:**
- Disallow changes to CloudTrail configuration
- Disallow deletion of Log Archive
- Disallow changes to Config recorder
- Enable CloudTrail in all accounts

**Examples of Strongly Recommended:**
- Disallow public S3 buckets
- Require encryption for EBS volumes
- Disallow RDS public access

⚠️ **Gotcha:** Mandatory guardrails cannot be disabled by anyone, including the management account admin. They are the non-negotiable baseline.

---

### B. Account Factory

Self-service account provisioning system built on Service Catalog.

**How it works:**
1. Account administrator pre-configures Account Factory settings (account baseline, OU, SSO settings)
2. End user requests new account via Service Catalog
3. Control Tower provisions: new AWS account + applies guardrails + sets up SSO + enrolls in Config/CloudTrail
4. Account is ready in ~30 minutes

**Account Factory for Terraform (AFT):**
- Provision and customize accounts using Terraform
- Version-controlled account templates
- CI/CD pipeline for account vending

⚠️ **Gotcha:** Accounts created OUTSIDE Account Factory (manually) are **NOT enrolled** in Control Tower by default. Use **Enroll Account** to bring them into the landing zone.

---

### C. Landing Zone

The Landing Zone is the overall multi-account environment set up by Control Tower.

**Mandatory components:**
- Management account (Control Tower home)
- Log Archive account (centralized logging)
- Audit account (security monitoring)
- CloudTrail org trail
- Config org recorder
- IAM Identity Center (SSO)
- Mandatory guardrails

**Landing Zone version:** Control Tower landing zones are versioned. AWS releases updates periodically — you must manually trigger Landing Zone Update to get new guardrails and features.

---

### D. Control Tower Customizations

**Customizations for Control Tower (CfCT):**
- Deploy custom CloudFormation templates and SCPs to accounts/OUs
- Integrated with Account Factory
- GitOps workflow for landing zone customization

**Account Factory for Terraform (AFT):**
- IaC-based account provisioning
- Custom account baseline via Terraform modules
- Integrates with existing Terraform workflows

---

### E. Control Tower vs DIY Organizations

| Aspect | Control Tower | DIY Organizations |
|---|---|---|

| Opinionated | ✅ Yes | ❌ Flexible |
| Customizability | Limited (within CT bounds) | Unlimited |

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** A company is setting up a new multi-account AWS environment. They want pre-configured security guardrails, centralized logging, and automated account provisioning. What is the recommended starting point?

A) Manually configure AWS Organizations + Config + CloudTrail  
B) AWS Control Tower — sets up landing zone with all of these pre-configured  
C) Deploy Terraform for all accounts individually  
D) Use a single account with multiple VPCs  

**Answer: B**

Control Tower is AWS's recommended starting point for multi-account environments. It provisions the landing zone structure, mandatory guardrails, centralized CloudTrail and Config, Log Archive and Audit accounts, and IAM Identity Center — in hours, not weeks.

---

**Q2.** An account was created manually (outside Account Factory) and needs to be governed by Control Tower. What is required?

A) Delete and recreate the account via Account Factory  
B) Use the "Enroll Account" feature in Control Tower  
C) Manually attach the Control Tower SCPs to the account  
D) Move the account to a Control Tower managed OU  

**Answer: B**

Control Tower provides an **Enroll Account** feature to bring existing accounts under Control Tower governance. This applies guardrails, sets up CloudTrail and Config, and integrates the account with IAM Identity Center without needing to recreate the account.

---

**Q3.** A security administrator wants to disable a mandatory guardrail in Control Tower. Is this possible?

A) Yes — all guardrails can be disabled with the right IAM permissions  
B) No — mandatory guardrails are permanently enabled and cannot be disabled by anyone  
C) Yes — if the account is in the management account  
D) Yes — if submitted as a support case  

**Answer: B**

Mandatory guardrails represent Control Tower's non-negotiable security baseline. They cannot be disabled, overridden, or bypassed by any action in the management account. This is by design — they protect the integrity of the landing zone itself (CloudTrail, Config, Log Archive).

---

**Q4.** What are the two accounts automatically created by Control Tower during landing zone setup?

A) Billing Account and Compliance Account  
B) Log Archive Account and Audit Account  
C) Security Account and Monitoring Account  
D) Management Account and Production Account  

**Answer: B**

Control Tower automatically creates:
- **Log Archive Account** — centralized S3 bucket receiving all CloudTrail logs and Config snapshots from all accounts
- **Audit Account** — receives SNS notifications for compliance violations; security team has read-only access to all accounts from here

---

**Q5.** A Control Tower detective guardrail flags an S3 bucket as non-compliant. The bucket was created 5 minutes ago. What does this tell you?

A) Control Tower blocked the bucket creation  
B) The bucket already exists but its configuration violates the guardrail; Control Tower detected it after creation  
C) Control Tower deleted the bucket  
D) The IAM user who created the bucket lost all permissions  

**Answer: B**

Detective guardrails (Config rules) detect non-compliant configurations **after** resources are created. They don't block creation. The bucket exists but violates the guardrail. To prevent creation, use preventive guardrails (SCPs).

---

**Q6.** A company wants to provision new AWS accounts automatically when developers submit a Jira ticket. What is the architecture?

A) Manual account creation in the AWS console  
B) Jira webhook → Lambda → Control Tower Account Factory API (or AFT pipeline)  
C) Developers create accounts directly with their IAM access  
D) Use AWS Config to provision accounts  

**Answer: B**

Account Factory exposes APIs for programmatic account provisioning. Integration with ticketing systems (Jira, ServiceNow) via webhook → Lambda → Account Factory/AFT enables self-service account vending with full Control Tower governance applied automatically.

---

**Q7.** What does Account Factory for Terraform (AFT) provide over standard Account Factory?

A) Faster account creation  
B) IaC-based account provisioning using Terraform, enabling version control, CI/CD, and custom account baselines as code  
C) Lower cost  
D) Direct EC2 access in new accounts  

**Answer: B**

AFT brings GitOps/IaC practices to account vending. Account templates, customizations, and baselines are version-controlled Terraform code. CI/CD pipelines automate provisioning. This is preferred for organizations with mature Terraform practices or complex account customization needs.

---

**Q8.** Control Tower uses which service for federated access to all accounts in the landing zone?

A) IAM roles with cross-account trust  
B) IAM Identity Center (SSO)  
C) Cognito user pools  
D) AWS Directory Service  

**Answer: B**

IAM Identity Center is the SSO layer set up automatically by Control Tower. Users authenticate once and access multiple accounts/roles based on permission sets. Control Tower configures the IAM Identity Center instance and integrates it with the Account Factory.

---

**Q9.** A proactive guardrail in Control Tower fails. What is the effect?

A) The CloudFormation stack is deployed with a warning  
B) The CloudFormation stack deployment is blocked — non-compliant resources are not created  
C) The resource is created and immediately deleted  
D) The user is notified but deployment proceeds  

**Answer: B**

Proactive guardrails use CloudFormation Hooks. When a CF stack is deployed, the Hook evaluates the resource configuration BEFORE creation. If non-compliant, the Hook returns a failure, and CloudFormation blocks the entire stack or the specific resource from being created.

---

**Q10.** What is the risk of manually modifying SCPs that were created and managed by Control Tower?

A) No risk — SCPs can always be modified  
B) It causes Control Tower drift — Control Tower may overwrite the changes or report the landing zone as out of compliance  
C) The SCP is permanently deleted  
D) All accounts lose internet access  

**Answer: B**

Control Tower owns and manages specific SCPs. Manually editing them causes **drift** — the landing zone is in a state Control Tower doesn't recognize. Control Tower may overwrite changes during updates, and the compliance dashboard may report errors. Use Control Tower's native customization mechanisms (CfCT) instead.

---

**Q11.** Where are centralized CloudTrail logs stored in a Control Tower landing zone?

A) CloudWatch Logs in each account  
B) S3 bucket in the Log Archive account  
C) S3 bucket in the management account  
D) DynamoDB in the Audit account  

**Answer: B**

Control Tower creates a centralized S3 bucket in the **Log Archive account** for all CloudTrail logs and Config snapshots from all accounts in the organization. The Log Archive account has restricted access — even account admins cannot delete logs there.

---

**Q12.** A company wants to ensure all accounts in their Control Tower landing zone get a new detective guardrail enabled. What is the process?

A) Enable the guardrail in each account individually  
B) Enable the guardrail in the OU via Control Tower console — it automatically applies to all accounts in that OU  
C) Deploy a Config rule to each account via CloudFormation StackSets  
D) Modify the management account's Config rules  

**Answer: B**

Guardrails in Control Tower are enabled at the **OU level** — they automatically apply to all accounts in that OU (and child OUs). This is the key management advantage: one action covers all accounts in the OU.

---

**Q13.** What is the difference between the Log Archive account and the Audit account in Control Tower?

A) They are the same account  
B) Log Archive stores CloudTrail/Config data; Audit account provides read-only cross-account access to security team and receives SNS compliance alerts  
C) Log Archive is for billing; Audit is for security  
D) Audit stores logs; Log Archive provides access  

**Answer: B**

**Log Archive** — immutable log storage (CloudTrail, Config). Read-only for most. Versioned S3 with MFA delete.
**Audit** — the security team's operational hub. Has read-only access to all accounts in the org. Receives SNS notifications for compliance violations. Security tooling (GuardDuty, Security Hub) often delegated here.

---

**Q14.** Can an account enrolled in Control Tower be moved to a different OU?

A) No — moving accounts is blocked by Control Tower  
B) Yes — accounts can be moved between OUs; the guardrails from the new OU automatically apply  
C) Yes — but only by AWS Support  
D) Yes — but guardrails must be manually re-applied  

**Answer: B**

Accounts can be moved between OUs in a Control Tower environment. When moved, the account **automatically loses the source OU's guardrails** and **gains the destination OU's guardrails** — the same immediate SCP inheritance behavior as AWS Organizations.

---

**Q15.** A company uses Control Tower and wants to add custom security controls beyond the built-in guardrails. What is the recommended approach?

A) Directly modify Control Tower's managed SCPs  
B) Use Customizations for Control Tower (CfCT) or AFT to deploy custom SCPs, Config rules, and CloudFormation templates  
C) Create a separate Organizations structure  
D) Request AWS to add custom guardrails  

**Answer: B**

**Customizations for Control Tower (CfCT)** is the AWS-native mechanism for adding custom controls to a Control Tower landing zone. It deploys custom CloudFormation templates, SCPs, and Config rules via a pipeline that integrates with Account Factory. This avoids drift by using supported extension mechanisms.

---

**Q16.** Guardrails are now referred to by what name in the AWS Console?

A) Guardrails (unchanged)  
B) Controls  
C) Policies  
D) Boundaries  

**Answer: B**

AWS rebranded guardrails to **Controls** in the Control Tower console. The functionality is identical — the exam may use either term, but officially they are now called Controls.

---

**Q17.** What mechanism does Control Tower use to enforce preventive guardrails?

A) Lambda functions  
B) Config Rules  
C) Service Control Policies (SCPs)  
D) IAM Permission Boundaries  

**Answer: C**

Preventive guardrails are implemented as **SCPs** at the OU level. They block API calls before resources are created. Detective guardrails use Config rules. Proactive guardrails use CloudFormation Hooks.

---

**Q18.** An organization has existing AWS accounts and an existing Organizations structure. They want to adopt Control Tower. What is the process called?

A) Landing Zone Import  
B) Control Tower Adoption  
C) Landing Zone setup on an existing Organizations structure  
D) Account migration  

**Answer: C**

Control Tower can be set up on an **existing AWS Organizations structure**. During setup, it will re-use the existing management account, create the Security OU (Log Archive + Audit accounts), and begin applying guardrails. Existing accounts must be individually enrolled. This is called setting up Control Tower on an existing organization.

---

**Q19.** Which component of Control Tower handles self-service account requests from developers?

A) IAM Identity Center  
B) Account Factory (built on Service Catalog)  
C) Config Conformance Pack  
D) Landing Zone Manager  

**Answer: B**

Account Factory is the self-service provisioning portal built on **AWS Service Catalog**. When a developer submits a request, Account Factory creates the new account with pre-defined settings (OU placement, email domain, SSO user groups, account baseline), applies guardrails, and sets up logging automatically.

---

**Q20.** A Control Tower landing zone is "drifted." What does this mean and how is it resolved?

A) The landing zone is in a different AWS region  
B) The landing zone configuration deviates from Control Tower's expected state (e.g., SCPs modified, Config disabled) — resolved by running "Repair Landing Zone" or "Update Landing Zone"  
C) The account factory is unavailable  
D) The management account password expired  

**Answer: B**

Drift occurs when resources managed by Control Tower are modified outside its processes (manual SCP changes, Config disablement, etc.). The Control Tower dashboard detects and reports drift. Resolution: run **Update Landing Zone** to bring the environment back to the expected state. Severe drift may require re-enrollment of affected accounts.

**Trap 8: Control Tower replaces CloudTrail/Config**
> ❌ Wrong: "Control Tower is a replacement for CloudTrail"

## 1.1 Service Overview & Purpose

### What is AWS Service Catalog?
AWS Service Catalog enables organizations to **create and manage catalogs of approved IT services** — CloudFormation templates, Terraform configs, and other infrastructure — that end users can deploy in a self-service manner, within governance guardrails.

Think of it as an **App Store for AWS resources** — users can only deploy pre-approved, compliant infrastructure templates.

### Why Does It Exist?
```
Without Service Catalog:
├── Developers create EC2 instances with any config (unencrypted, public IP)
├── No standard AMIs, instance types, or security baselines
├── Compliance review happens after deployment (reactive)
├── No self-service — every deployment requires ops team
└── Inconsistent tagging, naming, security configurations

With Service Catalog:
├── Only approved templates available to end users
├── Security controls baked into templates (encryption, no public IP)
├── Self-service deployment within guardrails
├── Automatic tagging enforcement
├── Audit trail of who deployed what
└── Version management for templates
```

### Exam Weight & Importance
- Lower weight — **1–2 questions** typically
- Commonly tested: Relationship to Control Tower Account Factory, portfolio sharing, launch constraints

## 1.3 Deep Dive — Every Sub-Topic

### A. Key Concepts

| Concept | Definition |
|---|---|
| **Portfolio** | Collection of products shared with users/groups |
| **Product** | A CloudFormation template (or Terraform config) |
| **Launch Constraint** | IAM role used to deploy the product (enables privilege separation) |
| **Template Constraint** | Limits parameter values users can set (e.g., instance type list) |
| **Provisioned Product** | A running instance of a deployed product |
| **Tag Option** | Enforces consistent tags on all provisioned products |

### B. Launch Constraints (Key Security Feature)

The launch constraint role allows end users to **deploy resources they don't have direct IAM permissions for** — but only through pre-approved, compliant templates.

```
Without Launch Constraint:
User needs ec2:RunInstances, kms:CreateKey, etc.
→ User has too many direct permissions

With Launch Constraint:
User only needs servicecatalog:ProvisionProduct
→ Service Catalog assumes launch constraint role
→ Launch constraint role has ec2:RunInstances, kms:CreateKey, etc.
→ User gets compliant resources without direct permissions
```

⚠️ **Gotcha:** The launch constraint role must trust the `servicecatalog.amazonaws.com` principal.

### C. Portfolio Sharing

Portfolios can be shared:
- With specific AWS accounts
- With AWS Organizations (entire org or specific OU)
- Imported into other accounts and shared further

Used heavily in Control Tower to distribute approved products to all accounts.

## 1.4 Security Angles

### Security Benefits of Service Catalog

1. **Separation of duties** — users deploy without direct permissions
2. **Compliance by design** — templates bake in encryption, no public IPs, tagging
3. **Least privilege at scale** — launch constraint grants only what the template needs
4. **Audit trail** — CloudTrail records all provisioning events
5. **Tag enforcement** — Tag Options ensure consistent resource tagging

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** A company wants developers to deploy pre-approved, secure infrastructure without having direct IAM permissions to create EC2 instances. What Service Catalog feature enables this?

A) Template Constraints  
B) Launch Constraint (IAM role assumed by Service Catalog during deployment)  
C) Portfolio sharing  
D) Tag Options  

**Answer: B**

Launch Constraints use an IAM role assumed by `servicecatalog.amazonaws.com`. The end user only needs `servicecatalog:ProvisionProduct`. The launch constraint role has the actual permissions (ec2:RunInstances, etc.). This enables least-privilege for users while allowing self-service deployment.

---

**Q2.** A Service Catalog product allows users to choose any EC2 instance type. The company wants to restrict this to only `t3.medium` and `t3.large`. What feature enforces this?

A) Launch Constraint  
B) Template Constraint  
C) Tag Option  
D) Portfolio restriction  

**Answer: B**

**Template Constraints** restrict the allowed values for CloudFormation parameters. For instance type, the constraint creates an allow-list: `["t3.medium", "t3.large"]`. Users cannot enter other values when launching the product.

---

**Q3.** AWS Control Tower's Account Factory is built on which service?

A) CloudFormation StackSets  
B) AWS Service Catalog  
C) AWS Organizations  
D) IAM Identity Center  

**Answer: B**

Control Tower's Account Factory uses **AWS Service Catalog** as its self-service portal. Account templates are Service Catalog products. Users request new accounts through the Service Catalog portal, and Account Factory provisions them via Control Tower APIs.

---

**Q4.** A company wants to share an approved set of CloudFormation templates with all accounts in their AWS Organization automatically. What is the most efficient approach?

A) Deploy CloudFormation StackSets to each account  
B) Share the Service Catalog portfolio with the Organization root  
C) Email templates to each account administrator  
D) Store templates in a public S3 bucket  

**Answer: B**

Service Catalog portfolios can be shared at the **Organization level** (root or specific OU) — one action distributes the portfolio to all current and future member accounts. StackSets deploy templates directly but don't provide the self-service catalog experience. Email/S3 approaches lack governance.

---

**Q5.** What is the purpose of Tag Options in Service Catalog?

A) To color-code products in the catalog  
B) To enforce mandatory, consistent tags on all resources provisioned through Service Catalog  
C) To filter which users see which products  
D) To version-control product templates  

**Answer: B**

Tag Options define mandatory tags and their allowed values (e.g., `CostCenter`, `Environment: [Production, Development]`). When a product is provisioned, these tags are automatically applied to all created resources. This ensures consistent tagging for cost allocation and compliance.

**Q6.** A security audit requires knowing exactly who provisioned which infrastructure resources and when. How does Service Catalog support this?

A) Service Catalog has no audit capability  
B) CloudTrail logs all `servicecatalog:ProvisionProduct` API calls with the user identity, timestamp, and product  
C) Service Catalog sends weekly reports  
D) Config tracks Service Catalog events  

**Answer: B**

Every provisioning action in Service Catalog is recorded in **CloudTrail** — including the IAM principal, timestamp, product name, version, and account. The Provisioned Products dashboard also shows all deployed products with their status and owner.

**Q7.** What is the relationship between a Service Catalog portfolio and products?

A) Portfolio = one product; product = many parameters  
B) Portfolio = container of related products shared with user groups; product = individual deployable template  
C) Portfolio = AWS account; product = IAM role  
D) They are identical concepts  

**Answer: B**

A **portfolio** is a logical container grouping related products (e.g., "Web Application Portfolio" containing EC2, RDS, and Load Balancer products). Portfolios are shared with IAM groups, roles, or accounts. **Products** are the individual CloudFormation templates (or Terraform configs) within a portfolio.

**Q8.** A launch constraint role needs to be able to create KMS keys during product provisioning. What must the launch constraint role's trust policy include?

A) `sts:AssumeRole` from the end user  
B) `servicecatalog.amazonaws.com` as trusted principal  
C) `cloudformation.amazonaws.com` as trusted principal  
D) Both B and C  

**Answer: D**

The launch constraint role must trust:
- `servicecatalog.amazonaws.com` — Service Catalog assumes the role
- `cloudformation.amazonaws.com` — CloudFormation assumes the role to create resources

Both service principals need to be in the trust policy for the provisioning to work end-to-end.

**Q9.** Can a Service Catalog product be updated after deployment to existing provisioned products?

A) No — provisioned products are static  
B) Yes — administrators can update product versions; existing provisioned products can be updated to the new version  
C) Yes — but only by deleting and re-creating  
D) Updates only apply to future deployments  

**Answer: B**

Service Catalog supports product versioning. When an administrator publishes a new version of a product (e.g., updated CFN template with new security controls), they can notify users of the update. Users (or admins) can then update their provisioned products to the new version without re-creating from scratch.

**Q10.** What is the key security difference between deploying directly from CloudFormation vs deploying via Service Catalog?

A) Service Catalog is slower  
B) Direct CloudFormation requires the user to have all necessary IAM permissions; Service Catalog uses launch constraints to allow deployment with minimal user permissions  
C) Service Catalog cannot deploy all CloudFormation resources  
D) CloudFormation has no security features  

**Answer: B**

This is the fundamental security value of Service Catalog. Direct CloudFormation deployment requires the user to have all permissions needed to create the resources. Service Catalog's launch constraint separates the user's identity from the deployment permissions — enabling least privilege while maintaining self-service.

**Q11.** A company wants developers in the sandbox OU to only be able to deploy from an approved Service Catalog portfolio. No ad-hoc CloudFormation is allowed. How is this enforced?

A) Service Catalog alone enforces this  
B) SCP denying `cloudformation:CreateStack` except when called by `servicecatalog.amazonaws.com`  
C) IAM policy denying all EC2 actions  
D) Config rule preventing CFN stack creation  

**Answer: B**

An SCP can deny `cloudformation:CreateStack` with a condition that exempts calls originating from Service Catalog. This forces all infrastructure deployment through approved Service Catalog products, preventing ad-hoc CloudFormation stacks. Service Catalog alone doesn't block direct CFN usage.

**Q12.** What happens to a provisioned product when the user who provisioned it leaves the company?

A) The product is automatically terminated  
B) The provisioned product continues to run; ownership can be transferred to another user  
C) The product is suspended until a new owner is assigned  
D) The product becomes a management account responsibility  

**Answer: B**

Provisioned products are persistent and independent of the user account. When a user is deactivated, their provisioned products continue to run. Service Catalog allows administrators to **transfer ownership** of provisioned products to another user without disrupting the running resources.

**Q13.** Service Catalog supports which infrastructure-as-code frameworks?

A) CloudFormation only  
B) CloudFormation and Terraform  
C) CloudFormation, Terraform, and Ansible  
D) Terraform only  

**Answer: B**

Service Catalog supports:
- **AWS CloudFormation** (native)

Ansible is not supported as a Service Catalog product type.

**Q14.** A portfolio is shared from a hub account to 50 spoke accounts. An administrator in the hub account updates a product. When do the spoke accounts see the update?

B) Immediately — shared portfolio updates are visible in spoke accounts in near real-time  
C) After 24 hours

Portfolio sharing propagates updates (new product versions, added products, removed products) to spoke accounts in near real-time. This is one of the key benefits of portfolio sharing over distributing templates manually.

**Q15.** What is the primary use case for Service Catalog in the context of AWS Control Tower?

**Answer: B**

Control Tower's Account Factory is a **Service Catalog product**. When a user requests a new account, they submit a Service Catalog provisioning request. Control Tower handles the account creation with full governance applied. This is the tightest integration between the two services.

**Q16.** A developer provisions a product and the deployment fails. What happens to the provisioned product status?

**Q17.** Can Service Catalog portfolios be shared across AWS Organizations with automatic inheritance for new accounts?

**Q18.** What CloudTrail event indicates that a user deployed a Service Catalog product?

`servicecatalog:ProvisionProduct` is the primary audit event. CloudTrail also captures the downstream `cloudformation:CreateStack` (called by the launch constraint role) and resource creation events. For auditing who provisioned what product, `servicecatalog:ProvisionProduct` is the key event.

**Q19.** A company has products in Service Catalog that create EC2 instances. They want all EC2 instances to automatically have an `Owner` tag set to the requester's email. What feature enables this?

Tag Options can reference the Service Catalog user's attributes. Using `PrincipalTag` mapping, the `Owner` tag can be automatically populated with the requester's email address from their IAM identity — no manual input required, and the value cannot be overridden.

**Q20.** Which IAM permission does an end user minimally need to deploy a Service Catalog product with launch constraints?

With launch constraints, the end user only needs Service Catalog-specific permissions: `servicecatalog:ProvisionProduct` (to deploy) and `servicecatalog:DescribeProvisioningParameters` (to see the form). ## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: Service Catalog enforces compliance alone**
> ❌ Wrong: "Service Catalog templates ensure users can't create non-compliant resources"
> ✅ Right: Users with direct IAM permissions can still bypass Service Catalog — use SCPs to force SC usage

**Trap 2: Launch constraint = template constraint**
> ❌ Wrong: "Launch constraint restricts parameter values"
> ✅ Right: Launch constraint = IAM role for deployment. Template constraint = parameter value restrictions.

**Trap 3: Portfolio sharing requires per-account setup**
> ❌ Wrong: "Share portfolio separately to each of 100 accounts"
> ✅ Right: Share at Organization or OU level — one action covers all current and future accounts

**Trap 4: Provisioned product owner = account owner**
> ❌ Wrong: "Provisioned products belong to the account, not the user"
> ✅ Right: Products have an individual owner (the provisioner). Ownership can be transferred.

**Trap 5: Service Catalog replaces CloudFormation**
> ❌ Wrong: "Service Catalog is an alternative to CloudFormation"
> ✅ Right: Service Catalog USES CloudFormation (or Terraform) as the underlying engine

**Trap 6: TAINTED means product is running normally**
> ❌ Wrong: "TAINTED is a normal provisioned product state"
> ✅ Right: TAINTED means deployment failed or product is in broken state — needs attention

**Trap 7: Launch constraint trust = user trust**
> ❌ Wrong: "Launch constraint role trusts the end user's ARN"
> ✅ Right: Trust `servicecatalog.amazonaws.com` AND `cloudformation.amazonaws.com`

**Trap 8: Service Catalog has no audit capability**
> ❌ Wrong: "No audit trail for Service Catalog deployments"
> ✅ Right: CloudTrail records all ProvisionProduct events; Service Catalog console shows provisioned products history

**Trap 9: Template constraints restrict user IAM permissions**
> ❌ Wrong: "Template constraint prevents users from having broad IAM"
> ✅ Right: Template constraints restrict CloudFormation PARAMETER VALUES only (e.g., instance type list)

**Trap 10: AFT = Service Catalog**
> ❌ Wrong: "Account Factory for Terraform uses Service Catalog"
> ✅ Right: AFT uses Terraform pipelines; standard Account Factory uses Service Catalog

## 1.1 Service Overview & Purpose

### What is AWS Artifact?
AWS Artifact is a **self-service portal for on-demand access to AWS compliance documentation and agreements**. It provides security and compliance reports (audit reports, certifications) and manages legal agreements with AWS.

Think of it as AWS's **compliance document library** — when an auditor asks "show me AWS's ISO 27001 certificate" or a legal team needs to sign a HIPAA BAA with AWS, AWS Artifact is where you go.

### What It Provides

**Reports (AWS Compliance Documents):**
- SOC 1, SOC 2, SOC 3 reports
- ISO 27001, ISO 27017, ISO 27018 certifications
- PCI DSS Attestation of Compliance (AOC)
- HIPAA eligibility documentation
- FedRAMP authorization packages
- CSA STAR reports
- GDPR DPA (Data Processing Addendum)
- DoD CC SRG packages

**Agreements:**
- Business Associate Agreement (BAA) for HIPAA
- GDPR Data Processing Addendum
- Non-Disclosure Agreements (NDA)

### Exam Weight & Importance
- Low weight — **1–2 questions**
- Simple service — just know what it does and when to use it
- Commonly tested: BAA for HIPAA, SOC reports, distinguishing from Config/Security Hub

---

## 1.2 Key Concepts

### Artifact Reports
- Downloaded as PDFs or packages
- Signed NDAs may be required before downloading
- Reports cover AWS infrastructure compliance — NOT your application on AWS

⚠️ **Critical distinction:** AWS Artifact reports cover AWS's compliance posture. They help you demonstrate the **infrastructure layer** compliance to auditors. Your APPLICATION running on AWS must be separately audited.

### Artifact Agreements
- **BAA (Business Associate Agreement)** — required for HIPAA workloads on AWS; covers how AWS handles PHI
- **NDA** — for accessing certain sensitive compliance documents
- Agreements can be accepted at the **account level** or **organization level** (AWS Organizations)

---

## 1.3 Security & Compliance Angles

### AWS Shared Responsibility Model and Artifact

AWS Artifact provides evidence for the **AWS side** of the shared responsibility model:
```
AWS Responsibility (Artifact covers):
├── Physical security (SOC reports, ISO certs)
├── Infrastructure compliance (FedRAMP, PCI DSS)
└── Service-level security controls

Customer Responsibility (you must separately demonstrate):
├── Your application security
├── Your IAM configuration
├── Your data encryption practices
└── Your access control policies
```

### When to Use Artifact

| Use Case | Service |
|---|---|
| Download AWS ISO 27001 cert for auditor | Artifact Reports |
| Sign HIPAA BAA with AWS | Artifact Agreements |
| Demonstrate AWS PCI compliance to QSA | Artifact Reports |
| Check your OWN compliance posture | Config + Security Hub |
| Get AWS SOC 2 Type II report | Artifact Reports |
| Sign GDPR DPA with AWS | Artifact Agreements |

**Q1.** A healthcare company is deploying a HIPAA-compliant application on AWS. Their legal team needs to ensure AWS has signed obligations regarding PHI handling. What do they need?

HIPAA requires a signed BAA with any business associate that handles PHI on your behalf. AWS is a business associate when processing PHI. ## 1.1 Service Overview & Purpose

### What are Incident Response Playbooks on AWS?
An IR Playbook (also called a Runbook) is a **documented, step-by-step procedure** for responding to a specific type of security incident. On AWS, playbooks combine AWS service capabilities (GuardDuty, CloudTrail, EC2 isolation, IAM revocation) with a structured response workflow.

### Incident Response Lifecycle (NIST SP 800-61)
```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│Preparation│──▶│ Detection │──▶│Containment│──▶│Eradication│
│           │   │ & Analysis│   │           │   │& Recovery │
└──────────┘   └──────────┘   └──────────┘   └──────────┘
       ▲                                             │
       └─────────────────────────────────────────────┘
                Post-Incident Activity (Lessons Learned)
```

### AWS IR Pillars

| Pillar | AWS Services |
|---|---|
| Detection | GuardDuty, CloudTrail, Security Hub, Config, CloudWatch Alarms |
| Analysis | CloudTrail, VPC Flow Logs, CloudWatch Logs Insights, Athena |
| Containment | IAM revocation, Security Group isolation, Lambda containment automation |
| Eradication | EC2 termination, S3 block public access, KMS key revocation |
| Recovery | EC2 from clean AMI, RDS restore from snapshot |
| Forensics | EC2 snapshot, memory capture, isolated forensics account |

### Exam Weight & Importance

- Expect **4–5 questions** on IR concepts and AWS tools
- Commonly tested: IR phases, containment approaches, GuardDuty response, compromised credential response

## 1.3 Deep Dive — IR Playbooks by Incident Type

### A. Compromised IAM Credentials

**Indicators:**
- GuardDuty: `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration`
- CloudTrail: API calls from unusual IP/region/time
- CloudTrail: `ConsoleLogin` from unknown location

**Playbook:**
```
1. IDENTIFY:
   └── CloudTrail: identify all API calls made with compromised key
       └── athena query: SELECT * FROM cloudtrail WHERE useridentity.accesskeyid = 'AKIAEXAMPLE'

2. CONTAIN:
   ├── Deactivate the access key immediately (IAM console or CLI)
   ├── If temporary credentials (STS): attach deny policy with aws:TokenIssueTime
   └── If EC2 instance credential: isolate instance

3. INVESTIGATE:
   ├── What resources were created/modified?
   ├── What data was accessed?
   ├── What IAM changes were made?
   └── What new resources might be persisting (backdoor roles)?

4. ERADICATE:
   ├── Delete compromised access key
   ├── Review and remove any backdoor resources created
   └── Check for unauthorized IAM users/roles created

5. RECOVER:
   ├── Create new access key for legitimate use
   ├── Review and revoke all other access keys for rotation
   └── Enable MFA where missing
```

⚠️ **Gotcha:** Deleting an IAM user doesn't invalidate existing sessions. Use `sts:AssumeRole` session revocation via `TokenIssueTime` condition.

---

### B. Compromised EC2 Instance

**Indicators:**
- GuardDuty: `Backdoor:EC2/C&CActivity` or `CryptoCurrency:EC2/BitcoinTool`
- VPC Flow Logs: unusual outbound connections
- CloudWatch: CPU spike (crypto mining)

**Playbook:**
```
1. IDENTIFY:
   ├── Review GuardDuty finding details
   ├── VPC Flow Logs: what IPs is instance communicating with?
   └── CloudWatch Logs: what processes are running?

2. CONTAIN (isolate, don't terminate):
   ├── Create new "forensics" security group: no inbound, no outbound
   ├── Replace instance's SG with forensics SG
   ├── Do NOT terminate — preserve evidence
   └── Create EBS snapshot for forensic analysis

3. INVESTIGATE:
   ├── Attach EBS snapshot to forensics instance
   ├── Analyze filesystem, logs, running processes
   ├── Check for persistence mechanisms (cron jobs, init scripts)
   └── Use SSM Session Manager for live investigation (if needed)

4. ERADICATE:
   ├── Terminate compromised instance
   └── Remove malicious artifacts

5. RECOVER:
   ├── Launch replacement from known-good AMI
   ├── Apply patch that was exploited
   └── Rotate all credentials the instance had access to
```

⚠️ **Gotcha:** Always **isolate before terminating** — termination destroys evidence. Memory forensics (if needed) must happen before termination.

---

### C. S3 Data Exfiltration

**Indicators:**
- GuardDuty: `Discovery:S3/AnomalousBehavior` or `Exfiltration:S3/ObjectRead.Unusual`
- CloudTrail: high volume `GetObject` calls
- Macie: sensitive data classification

**Playbook:**
```
1. IDENTIFY:
   ├── CloudTrail S3 data events: who accessed what objects?
   ├── Macie: what sensitive data was in the accessed objects?
   └── Determine exfiltration timeline

2. CONTAIN:
   ├── Apply S3 Block Public Access
   ├── Revoke access for the identified principal
   ├── Update bucket policy to deny the offending principal
   └── If access key involved: deactivate immediately

3. INVESTIGATE:
   ├── Complete list of objects accessed
   ├── Volume of data exfiltrated
   ├── Target IP addresses
   └── Was data already public or did attacker gain access?

4. ERADICATE:
   ├── Remove the attack path (close misconfiguration)
   └── Rotate credentials used

5. RECOVER & NOTIFY:
   ├── Assess if notification obligations triggered (GDPR 72hr, DPDPA)
   ├── Encrypt bucket with CMK
   └── Enable Macie on bucket going forward
```

---

### D. Ransomware on EC2

**Indicators:**
- Files renamed with encrypted extensions
- CloudWatch: disk I/O spike
- GuardDuty: `Trojan:EC2/DropPoint`

**Playbook:**
```
1. IDENTIFY AND CONTAIN:
   ├── Immediately isolate EC2 (forensics SG: all blocked)
   ├── Do NOT pay ransom
   └── Snapshot EBS volumes before any action

2. ASSESS BLAST RADIUS:
   ├── What other instances can this instance reach?
   ├── Are backups intact? (Check AWS Backup/RDS snapshots)
   └── Are network shares compromised?

3. RECOVER:
   ├── Restore from last known-good AWS Backup / snapshot
   ├── DO NOT restore from potentially infected snapshot
   └── Verify backup integrity before restore

4. ERADICATE PERSISTENCE:
   ├── Identify how ransomware entered (unpatched AMI, phishing)
   ├── Scan all other instances for indicators of compromise
   └── Rotate credentials, review IAM changes

5. PREVENT RECURRENCE:
   ├── Enable AWS Backup with separate account vault (immutable)
   ├── Test restore procedures regularly
   └── Patch management via SSM Patch Manager
```

## 2.1 Scenario-Based Q&A (20 Questions)

---

**Q1.** A GuardDuty finding `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration` is triggered. An EC2 instance's IAM role credentials were used from an external IP. What is the FIRST action?

A) Terminate the EC2 instance  
B) Attach an inline deny policy to the IAM role with `aws:TokenIssueTime` condition to revoke all outstanding sessions, and isolate the EC2 instance  
C) Delete the IAM role  
D) Disable GuardDuty to prevent false positives  

**Answer: B**

First: revoke outstanding STS sessions (TokenIssueTime deny). Second: isolate the EC2 instance (forensics SG). Don't terminate — preserve evidence. Deleting the role breaks all legitimate services using it. GuardDuty should never be disabled.

---

**Q2.** During incident response, you need to preserve forensic evidence from a compromised EC2 instance while preventing it from doing further damage. What is the correct approach?

A) Terminate the instance and review CloudTrail  
B) Create an EBS snapshot, then replace the instance's security group with one that blocks all inbound and outbound traffic  
C) Stop the instance and delete it after 24 hours  
D) Take a screenshot of the running instance  

**Answer: B**

EBS snapshot preserves the disk state for forensics. Replacing the SG with an all-block group contains the instance (stops C&C communication, data exfiltration) while keeping it running for potential live forensics. Termination destroys volatile memory and prevents further investigation.

---

**Q3.** CloudTrail shows `CreateUser` and `AttachUserPolicy` (AdminAccess) API calls from a compromised access key. What is the priority action beyond revoking the key?

A) Rotate the root account password  
B) Identify and delete any IAM users/roles/backdoors created by the attacker  
C) Enable MFA on the management account  
D) Update the SCP to deny IAM changes  

**Answer: B**

Attackers frequently create persistence mechanisms (new IAM users, roles, access keys) before detection. After revoking the compromised key, immediately audit and remove all IAM entities created during the attack window. CloudTrail provides the exact timeline and list of created resources.

---

**Q4.** Which service provides a visual investigation tool for understanding the relationships between AWS entities (roles, users, EC2 instances) during an incident?

A) CloudTrail  
B) GuardDuty  
C) Amazon Detective  
D) AWS Config  

**Answer: C**

**Amazon Detective** uses ML to automatically analyze and correlate CloudTrail, VPC Flow Logs, and GuardDuty findings. It generates relationship visualizations showing connections between principals, IPs, API calls — dramatically speeding up incident investigation vs. manually querying raw logs.

---

**Q5.** During an S3 data exfiltration incident, what two services provide the most complete picture of what data was accessed?

A) GuardDuty + Macie  
B) CloudTrail S3 data events + Amazon Macie  
C) VPC Flow Logs + CloudWatch  
D) Config + Security Hub  

**Answer: B**

**CloudTrail S3 data events** — `GetObject` calls showing exactly which objects were accessed, by whom, when, from where. **Macie** — classifies what sensitive data (PII, credentials, financial data) was in those objects. Together: "someone accessed these 500 objects containing PII and credit card data."

---

**Q6.** A Lambda function was compromised and is making calls to a crypto mining endpoint. What is the immediate containment action?

A) Delete the Lambda function  
B) Set reserved concurrency to 0  
C) Remove the function's execution role  
D) Disable CloudWatch Logs for the function  

**Answer: B**

Reserved concurrency = 0 is the Lambda kill switch — it immediately stops all invocations without deleting the function. Config and code are preserved for forensic investigation. Deleting is destructive. Removing the role causes failures but doesn't stop invocations from being attempted.

---

**Q7.** What is the NIST IR phase where you determine the scope and nature of an incident?

A) Preparation  
B) Detection and Analysis  
C) Containment  
D) Post-Incident Activity  

**Answer: B**

**Detection and Analysis** — this phase involves detecting the incident (via alerts, logs, GuardDuty findings) and analyzing it to determine: what happened, what is the scope, what systems are affected, what data may be impacted. This analysis drives the subsequent containment strategy.

---

**Q8.** An EC2 instance needs to be investigated while being contained. No SSH keys are available. How can you access the instance for investigation?

A) Create new SSH key pair and relaunch  
B) Use AWS SSM Session Manager — provides secure shell access without SSH or inbound ports  
C) Use RDP with admin credentials  
D) Terminate and relaunch with a key pair  

**Answer: B**

**AWS Systems Manager Session Manager** provides interactive shell access to EC2 instances without requiring SSH keys, inbound security group rules, or a bastion host. During IR, this allows investigation of a contained instance (all inbound/outbound blocked) via SSM which routes through the SSM service endpoint, not the instance's network.

⚠️ SSM Session Manager requires the SSM agent running on the instance and an instance profile with `ssm:StartSession` permission.

---

**Q9.** During incident response, you need to query 90 days of CloudTrail logs from S3 to find all API calls by a specific compromised role. What is the most efficient approach?

A) Download all logs and grep locally  
B) Use Amazon Athena to query the S3 CloudTrail data with SQL  
C) Use CloudTrail Event History (limited to 90 days, limited filters)  
D) Use CloudWatch Logs Insights  

**Answer: B**

**Amazon Athena** can query CloudTrail logs stored in S3 directly using SQL — across billions of log records in seconds. Much faster than local grep for large datasets. CloudTrail Event History in the console is limited to 90 days, read events only, and is slow for complex queries. CloudWatch Logs Insights works for logs streamed to CW Logs.

---

**Q10.** What is the purpose of a "forensics account" in an AWS IR architecture?

A) An account used for security penetration testing  
B) An isolated AWS account with a dedicated VPC where compromised artifacts (EBS snapshots, memory images) are analyzed without risk of cross-contamination  
C) The management account used for auditing  
D) An account where GuardDuty findings are centralized  

**Answer: B**

A forensics account is an isolated environment (separate AWS account, dedicated VPC with no internet, strict security controls) where EBS snapshots from compromised instances are attached and analyzed. Keeping forensics separate: prevents analyst errors from affecting production, prevents the compromised artifact from reaching other systems, and maintains chain of custody.

---

**Q11.** A ransomware attack has encrypted EC2 instance data. AWS Backup has daily snapshots. What is the safest recovery approach?

A) Restore from the most recent snapshot (taken day of attack)  
B) Restore from the last known-good snapshot before the first signs of infection; verify integrity before restoring  
C) Pay the ransom to save time  
D) Wipe and rebuild from a blank AMI  

**Answer: B**

The most recent snapshot may itself be infected if ransomware was silently operating for days before encrypting. Identify when the infection began (using forensics, CloudTrail, endpoint logs), then restore from a snapshot predating that timeline. Always verify backup integrity. Rebuild from blank AMI (option D) is valid but loses all data.

---

**Q12.** After an IAM credential compromise incident, what should be checked in CloudTrail specifically related to IAM changes?

A) Only `GetObject` calls  
B) `CreateUser`, `CreateRole`, `AttachUserPolicy`, `CreateAccessKey`, `PutRolePolicy` events — looking for backdoor accounts created by the attacker  
C) Only `DeleteTrail` events  
D) Only `ConsoleLogin` events  

**Answer: B**

Attackers with IAM credentials commonly create persistence mechanisms. Review CloudTrail for IAM API calls during the attack window: new users, new roles, new access keys, policy attachments. Any IAM entity created by the compromised principal during the incident window should be considered potentially malicious.

---

**Q13.** What AWS service helps automatically trigger remediation actions when a security finding is detected in GuardDuty?

A) CloudWatch Logs  
B) EventBridge rule → Lambda / Step Functions (automated response pipeline)  
C) Config rules  
D) Trusted Advisor  

**Answer: B**

GuardDuty findings generate EventBridge events. An EventBridge rule matching specific finding types can trigger Lambda (for targeted containment) or Step Functions (for multi-step IR workflows). This enables automated response playbooks: finding detected → EventBridge → Lambda isolates instance or revokes credentials — in seconds.

---

**Q14.** VPC Flow Logs show an EC2 instance connecting to a known malicious IP on port 4444. What is the likely threat?

A) Database misconfiguration  
B) Reverse shell / Command & Control (C&C) connection — the instance is likely compromised with a RAT or backdoor  
C) Normal API Gateway traffic  
D) AWS service communication  

**Answer: B**

Port 4444 is a well-known Metasploit reverse shell port. Outbound connections from an EC2 instance to a malicious IP on this port indicates a **Command & Control (C&C) connection** — the instance is compromised. Immediate action: isolate (forensics SG), preserve EBS snapshot, investigate.

**Q15.** What is the "break-glass" account concept in AWS IR?

A) An account used to break SLA agreements  
B) A pre-provisioned, highly privileged emergency access account used when normal access paths are compromised or unavailable during an incident  
C) The management account's root user  
D) An account for testing destructive actions  

**Answer: B**

Break-glass accounts are emergency admin accounts with credentials stored offline (physical safe, HSM) — used only when normal IAM access is compromised (e.g., attacker changed all admin credentials). They are monitored heavily (CloudTrail alert on any use) and their credentials are rotated after each use.

---

**Q16.** During IR, you determine that a GuardDuty finding is a false positive. What is the correct handling?

A) Disable GuardDuty  
B) Archive the finding in GuardDuty and add a suppression rule for the specific pattern to prevent future false positives  
C) Delete the CloudTrail log that triggered it  
D) Modify the GuardDuty detector sensitivity  

**Answer: B**

Archive the specific finding (marks it as reviewed). Add a **suppression rule** for the specific pattern (e.g., this specific IP + resource combination) to auto-archive future occurrences. Never disable GuardDuty — losing all threat detection. Never modify logs.

---

**Q17.** What does the `aws:TokenIssueTime` condition do in an IAM policy for incident response?

A) Limits access to specific hours of the day  
B) Denies all access for temporary credentials (STS tokens) issued before a specific timestamp — effectively revoking all outstanding sessions  
C) Requires token refresh every hour  
D) Enables MFA for session tokens  

**Answer: B**

`aws:TokenIssueTime` in a Deny policy with a date-time condition revokes all STS temporary credentials issued before that time. Since you can't directly invalidate STS tokens (unlike access keys), this is the standard technique to immediately revoke outstanding sessions without deleting the IAM role.

---

**Q18.** An RDS database has been compromised. The attacker has active database connections. What AWS-level containment is possible?

A) No AWS-level containment for active DB connections  
B) Modify the RDS security group to remove all inbound rules; modify the subnet route table; force SSL only; rotate the master password  
C) Terminate the RDS instance  
D) Enable Multi-AZ  

**Answer: B**

Security Group modification immediately drops new connection attempts. Existing active connections may persist briefly but will timeout. Rotating the master password forces re-authentication — drops existing authenticated sessions. Terminating destroys data (unless Multi-AZ/read replicas exist).

---

**Q19.** What is a tabletop exercise in the context of AWS IR?

A) A table-mounted AWS console  
B) A simulated incident scenario discussed by the IR team (no actual systems affected) to test and refine playbooks  
C) A physical security assessment  
D) An automated IR test  

**Answer: B**

A **tabletop exercise** is a discussion-based simulation where the IR team walks through a hypothetical incident scenario step by step — discussing what they would do, which playbooks apply, who would be notified, what commands would be run. No live systems are involved. Used to identify playbook gaps before a real incident.

---

**Q20.** A security event occurred 6 months ago. You need to query CloudTrail logs for that period. CloudTrail Event History only shows 90 days. Where do you find the older logs?

A) AWS Config configuration history  
B) CloudTrail S3 delivery bucket — logs are delivered to S3 indefinitely (by default 0-day retention; configure S3 lifecycle for long-term)  
C) GuardDuty findings archive  
D) CloudWatch Logs (auto-archived)  

**Answer: B**

CloudTrail Event History in the console = 90 days, read events only. CloudTrail **S3 delivery** = unlimited (governed by your S3 lifecycle policy). For long-term IR investigation, query the S3 bucket using Athena. Best practice: S3 lifecycle → S3 Glacier for cost-effective long-term retention.

## 2.2 Common Exam Traps & Distractors (10)

**Trap 1: Terminate compromised EC2 first**
> ❌ Wrong: "Immediately terminate compromised EC2 for containment"
> ✅ Right: ISOLATE first (forensics SG), THEN terminate after forensics. Termination destroys evidence.

**Trap 2: Delete IAM role to revoke credentials**
> ❌ Wrong: "Delete the IAM role to stop credential use"
> ✅ Right: Deleting role breaks legitimate services. Use TokenIssueTime deny policy for instant revocation.

**Trap 3: Access key deactivation = STS session invalidation**
> ❌ Wrong: "Deactivating access key invalidates existing STS sessions"
> ✅ Right: Access key deactivation stops new auth. STS sessions require TokenIssueTime deny for revocation.

**Trap 4: GuardDuty false positive = disable GuardDuty**
> ❌ Wrong: "Too many false positives — disable GuardDuty"
> ✅ Right: Archive findings + add suppression rules. Never disable GuardDuty.

**Trap 5: Most recent backup = always safe for ransomware recovery**
> ❌ Wrong: "Restore from most recent snapshot after ransomware"
> ✅ Right: Most recent snapshot may be post-infection. Restore from pre-infection snapshot.

**Trap 6: CloudTrail Event History = full history**
> ❌ Wrong: "CloudTrail shows all API calls ever made"
> ✅ Right: Event History = 90 days, read events only. Full history is in S3 delivery bucket.

**Trap 7: Detective = GuardDuty**
> ❌ Wrong: "Detective detects threats like GuardDuty"
> ✅ Right: GuardDuty DETECTS. Detective INVESTIGATES (relationship visualization, root cause analysis).

**Trap 8: SSM Session Manager requires SSH**
> ❌ Wrong: "SSM Session Manager needs port 22 open"
> ✅ Right: SSM Session Manager requires NO inbound ports — outbound HTTPS to SSM endpoint only.

**Trap 9: IR = only a technical process**
> ❌ Wrong: "IR is purely technical — just run the playbook"
> ✅ Right: IR includes: technical response + legal/compliance notification + executive communication + lessons learned

**Trap 10: Isolation means termination**
> ❌ Wrong: "Isolated instance = terminated instance"
> ✅ Right: Isolation = still running, all network access blocked (forensics SG). Termination = destroyed.
