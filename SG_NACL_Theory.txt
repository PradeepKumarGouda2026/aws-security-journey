# **PART 1: SECURITY GROUPS VS NACLS - THE DEFINITIVE GUIDE (45 MIN)**

## **The Fundamental Difference:**

```
┌─────────────────────────────────────────────────┐
│         SECURITY GROUPS                          │
│         (Instance-level Firewall)               │
├─────────────────────────────────────────────────┤
│  ┌──────────────────────────────────────────┐  │
│  │  EC2 Instance                            │  │
│  │  ┌────────────────────────────────────┐  │  │
│  │  │                                    │  │  │
│  │  │  Your Application                  │  │  │
│  │  │                                    │  │  │
│  │  └────────────────────────────────────┘  │  │
│  │                                          │  │
│  │  Security Group wraps the INSTANCE       │  │
│  └──────────────────────────────────────────┘  │
│                                                 │
│  Characteristics:                               │
│  ├─ STATEFUL (return traffic automatic)       │
│  ├─ Instance-level (attached to ENI)          │
│  ├─ Only ALLOW rules (no DENY)                │
│  ├─ All rules evaluated (no order)            │
│  └─ Changes apply immediately                  │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│         NETWORK ACLs                            │
│         (Subnet-level Firewall)                 │
├─────────────────────────────────────────────────┤
│  ┌──────────────────────────────────────────┐  │
│  │  Subnet (10.0.1.0/24)                    │  │
│  │  ┌──────┐  ┌──────┐  ┌──────┐          │  │
│  │  │ EC2  │  │ EC2  │  │ EC2  │          │  │
│  │  │  #1  │  │  #2  │  │  #3  │          │  │
│  │  └──────┘  └──────┘  └──────┘          │  │
│  │                                          │  │
│  │  NACL wraps the entire SUBNET            │  │
│  └──────────────────────────────────────────┘  │
│                                                 │
│  Characteristics:                               │
│  ├─ STATELESS (must allow return traffic)     │
│  ├─ Subnet-level (all instances in subnet)    │
│  ├─ ALLOW and DENY rules                      │
│  ├─ Rules numbered (processed in order)       │
│  └─ Changes may have propagation delay        │
└─────────────────────────────────────────────────┘
```

## **STATEFUL vs STATELESS - THE CRITICAL DIFFERENCE:**

### **Security Groups (STATEFUL):**

```
Example: Web server receiving HTTP request

INBOUND REQUEST:
Client (203.0.113.10:54321) → Server (10.0.1.5:80)

Security Group Inbound Rule:
✅ Allow TCP port 80 from 0.0.0.0/0

Traffic allowed? YES ✅

OUTBOUND RESPONSE (AUTOMATIC!):
Server (10.0.1.5:80) → Client (203.0.113.10:54321)

Security Group Outbound Rule:
❓ Do we need a rule for port 54321?
❌ NO! Stateful = return traffic automatically allowed!

Even if outbound rules say "deny all", the response still goes out!

This is STATEFUL behavior! 🎯
```

---

### **Network ACLs (STATELESS):**

```
Example: SAME web server receiving HTTP request

INBOUND REQUEST:
Client (203.0.113.10:54321) → Server (10.0.1.5:80)

NACL Inbound Rule:
✅ Rule 100: Allow TCP port 80 from 0.0.0.0/0

Traffic allowed? YES ✅

OUTBOUND RESPONSE (MANUAL!):
Server (10.0.1.5:80) → Client (203.0.113.10:54321)

NACL Outbound Rule:
❓ Do we need a rule for port 54321?
✅ YES! Must explicitly allow ephemeral ports!
✅ Rule 100: Allow TCP ports 1024-65535 to 0.0.0.0/0

Without this rule, the response is BLOCKED! ❌

This is STATELESS behavior! 🎯
```

---

## **EPHEMERAL PORTS - WHY THEY MATTER:**

```
Ephemeral ports = Temporary ports used for return traffic

How TCP connections work:
├─ Client picks random high port (ephemeral)
├─ Client connects to server's well-known port
├─ Server responds BACK to client's ephemeral port
└─ Port range: 1024-65535 (varies by OS)

Example connection:
Client: 203.0.113.10:54321 (ephemeral) 
   ↓ Request
Server: 10.0.1.5:80 (well-known HTTP port)
   ↓ Response
Client: 203.0.113.10:54321 (same ephemeral)

For NACLs (stateless):
✅ Inbound: Must allow port 80
✅ Outbound: Must allow ports 1024-65535 (ephemeral range!)

For Security Groups (stateful):
✅ Inbound: Allow port 80
❌ Outbound: Not needed! (automatic)

Operating System Ephemeral Ranges:
├─ Linux: 32768-60999
├─ Windows: 49152-65535
├─ AWS default: 1024-65535 (safest!)
```

## **TRAFFIC FLOW - BOTH LAYERS:**

```
Traffic path for inbound request:

Internet
   ↓
Internet Gateway
   ↓
┌─────────────────────────────────────┐
│ LAYER 1: NACL Inbound              │ ← Checked FIRST
│ Rules processed in NUMBER order     │
│ First ALLOW or DENY = action taken │
└─────────────────┬───────────────────┘
                  ↓ (if ALLOW)
┌─────────────────────────────────────┐
│ LAYER 2: Security Group Inbound    │ ← Checked SECOND
│ All ALLOW rules evaluated           │
│ Must match at least one rule        │
└─────────────────┬───────────────────┘
                  ↓ (if ALLOW)
            EC2 Instance
                  ↓
            Process request
                  ↓
          Generate response
                  ↓
┌─────────────────────────────────────┐
│ LAYER 3: Security Group Outbound   │ ← Automatic for
│ Stateful: Return traffic allowed    │   return traffic!
└─────────────────┬───────────────────┘
                  ↓
┌─────────────────────────────────────┐
│ LAYER 4: NACL Outbound             │ ← Must explicitly
│ Stateless: Need ephemeral ports!    │   allow!
└─────────────────┬───────────────────┘
                  ↓
          Internet Gateway
                  ↓
            Internet

Both must ALLOW for traffic to flow! 🔒
```

## **COMMON MISCONCEPTIONS:**

### **Misconception 1: "Security Groups can DENY"**

```
❌ WRONG: Security Groups have DENY rules
✅ CORRECT: Security Groups only have ALLOW rules

How to deny with Security Groups?
└─ Don't create an allow rule = implicit deny!

Example:
Want to block 198.51.100.0/24?
❌ Can't create: DENY 198.51.100.0/24
✅ Instead: Don't allow it! (it's blocked by default)

If you need explicit DENY:
└─ Use NACLs! (they have DENY rules)
```

---

### **Misconception 2: "NACLs are better because they have DENY"**

```
❌ WRONG: Always use NACLs over Security Groups
✅ CORRECT: Use both in layers (defense in depth)

Security Groups = Primary control (instance-level)
├─ Fine-grained per instance/application
├─ Stateful (easier to manage)
└─ Can reference other security groups

NACLs = Secondary control (subnet-level)
├─ Broad subnet-level protection
├─ Explicit DENY for known bad IPs
└─ Backup layer if SG misconfigured

Use BOTH together! 🛡️
```

---

### **Misconception 3: "Stateful means more secure"**

```
❌ WRONG: Stateful = more secure than stateless
✅ CORRECT: Stateful = easier to configure, not inherently more secure

Stateful (Security Groups):
├─ Pros: Easier (auto return traffic), less rules
├─ Cons: Can't see/block return traffic explicitly

Stateless (NACLs):
├─ Pros: Full control (can block return traffic)
├─ Cons: More complex (must allow ephemeral ports)

Security = proper configuration, not state type! 🎯
```

## **WHEN TO USE WHICH:**

### **Primary Control: Security Groups**

```
Use Security Groups as your MAIN firewall for:

✅ Instance-level control
   - Web servers: Allow 80/443 from internet
   - App servers: Allow 8080 from web tier only
   - Databases: Allow 3306 from app tier only

✅ Application segmentation
   - Each tier has its own security group
   - Security groups reference each other

✅ Dynamic environments
   - Auto Scaling (instances come/go)
   - Microservices (many services)

✅ Fine-grained access
   - Different rules per instance
   - Service-to-service communication

Example:
3-tier app = 3 security groups (web-sg, app-sg, db-sg)
Each SG references the previous tier!
```

---

### **Secondary Control: NACLs**

```
Use NACLs as BACKUP/ADDITIONAL protection for:

✅ Subnet-level boundaries
   - Public subnet: Different rules than private
   - DMZ subnet: Extra restrictive

✅ Explicit DENY rules
   - Block known malicious IPs
   - Prevent access to certain ports subnet-wide

✅ Defense in depth
   - Backup if security group misconfigured
   - Compliance requirement (multiple layers)

✅ Broad subnet controls
   - Block entire subnet communication
   - Subnet-to-subnet isolation

Example:
Public subnet NACL: Block countries X, Y, Z
Private subnet NACL: Block all inbound from internet
Even if SG misconfigured, NACL blocks! 🛡️
```

## **REAL-WORLD PATTERNS:**

### **Pattern 1: Multi-Tier Application**

```
┌─────────────────────────────────────────────┐
│  Web Tier (Public Subnet)                   │
│  Security Group: web-sg                     │
│  ├─ Allow 80/443 from 0.0.0.0/0            │
│  └─ Allow 8080 from app-sg                 │
│                                             │
│  NACL: Public-NACL                          │
│  ├─ Inbound: Allow 80/443, SSH from office│
│  ├─ Inbound: DENY known bad IPs (rule 50) │
│  └─ Outbound: Allow all (rule 100)        │
└─────────────────┬───────────────────────────┘
                  ↓
┌─────────────────────────────────────────────┐
│  App Tier (Private Subnet)                  │
│  Security Group: app-sg                     │
│  ├─ Allow 8080 from web-sg only            │
│  └─ Allow 3306 to db-sg only               │
│                                             │
│  NACL: Private-NACL                         │
│  ├─ Inbound: Allow from VPC only           │
│  └─ Outbound: Allow HTTP/HTTPS for updates│
└─────────────────┬───────────────────────────┘
                  ↓
┌─────────────────────────────────────────────┐
│  DB Tier (Private Subnet)                   │
│  Security Group: db-sg                      │
│  ├─ Allow 3306 from app-sg only            │
│  └─ Deny everything else (implicit)        │
│                                             │
│  NACL: Private-NACL                         │
│  ├─ Inbound: Allow from VPC only           │
│  └─ Outbound: DENY internet (rule 200)    │
└─────────────────────────────────────────────┘

Defense in depth! Both SG and NACL protect! 🛡️
```

---

### **Pattern 2: Bastion Host (Jump Box)**

```
Bastion Host Setup:

Public Subnet:
├─ Security Group: bastion-sg
│   ├─ Inbound: SSH (22) from office IP only
│   └─ Outbound: SSH (22) to private-sg
│
└─ NACL: Allow SSH from office, ephemeral return

Private Subnet:
├─ Security Group: private-sg
│   ├─ Inbound: SSH (22) from bastion-sg only
│   └─ No direct internet access
│
└─ NACL: Allow SSH from bastion subnet only

Access flow:
Your laptop (office IP)
   → SSH to Bastion (public IP)
   → SSH from Bastion to Private EC2 (private IP)
   → Access granted! ✅

Even if someone steals private EC2 key:
❌ Can't access from internet (NACL blocks)
❌ Can't access directly (SG blocks)
✅ Must go through bastion (logged and monitored)
```
