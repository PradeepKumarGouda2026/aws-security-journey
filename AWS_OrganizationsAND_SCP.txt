## 📚 Theory Block (45 mins)

### 1. AWS Organizations — Security Perspective
- **Management Account** (formerly master) — never deploy workloads here
- **Organizational Units (OUs)** — logical grouping of accounts
- **SCPs attach at**: Root, OU, or individual account level
- **SCPs do NOT grant permissions** — they only *restrict* what IAM can grant

### 2. SCP Evaluation Logic
```
Effective Permission = IAM Policy ∩ SCP
```
- If SCP **denies** → blocked, even if IAM allows
- If SCP **doesn't mention** an action → IAM decides
- Management account is **exempt** from SCPs ⚠️

### 3. SCP Strategies
| Strategy | Use Case |
|---|---|
| **Allowlist** | Only listed actions permitted (strict) |
| **Denylist** | All allowed except listed (flexible, default AWS approach) |

### 4. Key SCP Use Cases for Exam
- Prevent leaving the organization
- Restrict regions (deny actions outside `us-east-1`)
- Enforce MFA for sensitive actions
- Prevent disabling CloudTrail
- Block root user activity

## 🧠 Exam-Focus Q&A

**Q1: An SCP is attached to an OU denying S3 access. An IAM policy in a member account grants S3 full access. Can the user access S3?**
> ❌ No. SCP overrides IAM. Effective permission = IAM ∩ SCP.

**Q2: Does an SCP apply to the management account?**
> ❌ No. Management account is always exempt from SCPs.

**Q3: You need to restrict all accounts from creating resources outside eu-west-1. Where should the SCP be attached?**
> ✅ At the **Root** level of the organization, using `aws:RequestedRegion` condition.

**Q4: What's the difference between an SCP Allowlist vs Denylist approach?**
> - **Allowlist**: Replace the default `FullAWSAccess` SCP with only what's permitted. Strict.
> - **Denylist**: Keep `FullAWSAccess`, add explicit Deny statements. Flexible, AWS default.

## ❌ Missing Two Topics

### 1. SCP Inheritance Model
This is actually **exam-critical** and we skipped it. Key concepts:

- SCPs **inherit downward** — an SCP on a parent OU applies to all child OUs and accounts beneath it
- A **child cannot override** a parent's Deny
- **Effective permission** at any account = intersection of ALL SCPs in the hierarchy chain (Root → OU → Sub-OU → Account)

```
Root SCP (Deny CloudTrail delete)
    └── OU: Production
            └── OU: Finance        ← also inherits Root SCP
                    └── Account A  ← inherits both Root + Production + Finance SCPs
```

Even if Finance OU has no SCP attached, Account A is still governed by Root and Production SCPs.

---


## 📝 Inheritance Model — Exam Trap to Remember

| Scenario | Result |
|---|---|
| Parent OU has Deny SCP, child OU has Allow SCP | ❌ Deny wins |
| No SCP attached to child OU | ✅ Inherits parent SCP |
| Management account has Deny SCP attached | ✅ Still exempt, SCP ignored |
| Member account has Allow SCP but parent has Deny | ❌ Parent Deny wins |

# 📚 Day 31 — Full Theory Block

## 1. AWS Organizations Hierarchy

### Structure
```
Management Account (Root)
        │
        ├── Root (/)
        │     │
        │     ├── OU: Security
        │     │     └── Account: Security Tooling
        │     │
        │     ├── OU: Production
        │     │     ├── OU: Finance
        │     │     │     └── Account: Finance Prod
        │     │     └── OU: HR
        │     │           └── Account: HR Prod
        │     │
        │     ├── OU: Sandbox
        │     │     └── Account: Dev/Test
        │     │
        │     └── OU: Suspended
        │           └── Account: Decommissioned accounts
```

### Key Components

**Management Account:**
- The account used to create the Organization
- Has full control over all member accounts
- **Never deploy workloads here** — it's exempt from SCPs, making it a security risk if compromised
- Responsible for consolidated billing
- Can invite or create member accounts

**Organizational Units (OUs):**
- Logical containers for accounts
- Can be **nested up to 5 levels deep**
- An account can only belong to **one OU at a time**
- OUs help apply consistent policies across similar accounts

**Member Accounts:**
- Regular AWS accounts within the organization
- Can be **created** (new) or **invited** (existing)
- Governed by SCPs from the hierarchy above them
- Can still have their own IAM policies, but SCPs set the ceiling

**AWS Organizations Features:**
| Feature Set | What it includes |
|---|---|
| **Consolidated Billing only** | Just billing aggregation, no SCPs |
| **All Features** | SCPs + billing + delegated admin + more |

> ⚠️ Exam tip: SCPs are **only available** when "All Features" is enabled. If you see a question where SCPs aren't working, check if the org is in "Consolidated Billing only" mode.

## 2. SCP vs IAM Policy Evaluation

### The Core Rule
```
Effective Permission = IAM Policy ∩ SCP
```

SCPs and IAM policies work **together**, not independently. Both must allow an action for it to succeed.

### Full Policy Evaluation Order (Exam Critical)
```
1. Explicit DENY in SCP           → DENY (stop, no further check)
2. Explicit ALLOW in SCP?         → Continue to IAM check
3. Action not in SCP?             → Continue to IAM check (implicit allow passthrough)
4. Explicit DENY in IAM Policy    → DENY
5. Explicit ALLOW in IAM Policy   → ALLOW
6. No explicit ALLOW in IAM       → DENY (implicit deny)
```

### Comparison Table

| Aspect | SCP | IAM Policy |
|---|---|---|
| **Attached to** | Root, OU, Account | User, Group, Role, Resource |
| **Grants permissions** | ❌ Never | ✅ Yes |
| **Can Deny** | ✅ Yes | ✅ Yes |
| **Applies to management account** | ❌ No | ✅ Yes |
| **Applies to root user of member account** | ✅ Yes | ❌ No (root ignores IAM) |
| **Scope** | Account-level ceiling | Identity/Resource level |

> ⚠️ **Biggest exam trap:** SCPs **do apply to the root user of member accounts** but do NOT apply to the management account's root user. Many candidates get this wrong!

### Practical Example
```
SCP on OU:        Allow s3:*, ec2:*  (allowlist style)
IAM Policy:       Allow s3:*, rds:*

Effective:        s3:* only
                  (ec2 allowed by SCP but not IAM = denied)
                  (rds allowed by IAM but not SCP = denied)
```

## 3. SCP Strategies — Denylist vs Allowlist

### Strategy 1: Denylist (Default AWS Approach)
- AWS attaches `FullAWSAccess` SCP to every OU/account by default
- You add **explicit Deny** statements on top for what you want to block
- Everything else remains available (subject to IAM)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyExpensiveServices",
      "Effect": "Deny",
      "Action": [
        "sagemaker:*",
        "rekognition:*",
        "comprehend:*"
      ],
      "Resource": "*"
    }
  ]
}
```

**Pros:** Flexible, easier to manage, less risk of accidental lockout
**Cons:** Less strict, easier to miss something

---

### Strategy 2: Allowlist (Strict/Zero Trust Approach)
- **Remove** the default `FullAWSAccess` SCP
- Replace with an SCP that **only lists what's permitted**
- Anything not listed = implicitly denied

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOnlyApprovedServices",
      "Effect": "Allow",
      "Action": [
        "ec2:*",
        "s3:*",
        "iam:*",
        "cloudtrail:*",
        "logs:*"
      ],
      "Resource": "*"
    }
  ]
}
```

**Pros:** Very strict, zero-trust aligned, nothing slips through
**Cons:** High maintenance, easy to accidentally block needed services

> ⚠️ Exam tip: If a question says "most restrictive" or "least privilege at org level" → think **Allowlist strategy**

## 4. Common SCP Patterns (Exam Favorites)

### Pattern 1: Region Restriction
Prevent any action outside approved regions:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "organizations:*",
        "support:*",
        "sts:AssumeRole",
        "cloudfront:*",
        "route53:*",
        "waf:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": [
            "ap-south-1",
            "us-east-1"
          ]
        }
      }
    }
  ]
}
```
> ⚠️ Must use `NotAction` (not `Action`) to exclude global services like IAM, Route53, CloudFront which don't operate in a specific region

---

### Pattern 2: Protect Security Services
Prevent tampering with GuardDuty, CloudTrail, Config:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectSecurityServices",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "cloudtrail:UpdateTrail",
        "guardduty:DeleteDetector",
        "guardduty:DisassociateFromMasterAccount",
        "config:DeleteConfigRule",
        "config:StopConfigurationRecorder",
        "securityhub:DisableSecurityHub"
      ],
      "Resource": "*"
    }
  ]
}
```

---

### Pattern 3: Prevent Leaving Organization
```json
{
  "Sid": "PreventLeavingOrg",
  "Effect": "Deny",
  "Action": "organizations:LeaveOrganization",
  "Resource": "*"
}
```

---

### Pattern 4: Enforce Encryption
Deny S3 uploads without server-side encryption:
```json
{
  "Sid": "DenyUnencryptedS3Uploads",
  "Effect": "Deny",
  "Action": "s3:PutObject",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "s3:x-amz-server-side-encryption": [
        "AES256",
        "aws:kms"
      ]
    }
  }
}
```

---

### Pattern 5: Restrict Root User Activity
```json
{
  "Sid": "RestrictRootUser",
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringLike": {
      "aws:PrincipalArn": "arn:aws:iam::*:root"
    }
  }
}
```
> ✅ This is how you **restrict root user in member accounts** via SCP — another common exam scenario

---

### Pattern 6: Require MFA
```json
{
  "Sid": "DenyWithoutMFA",
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}
```
> ⚠️ Use `BoolIfExists` (not `Bool`) — handles cases where MFA context key doesn't exist (e.g., CLI with access keys)

## 5. SCP Inheritance Model (Deep Dive)

### How Inheritance Works
```
Root SCP: Deny cloudtrail:DeleteTrail
    │
    ├── OU: Production  (no SCP attached)
    │       │
    │       ├── OU: Finance  (SCP: Allow s3:* only)
    │       │       │
    │       │       └── Account A
    │       │           Inherits: Root SCP + Finance SCP
    │       │           Effective: Cannot delete CloudTrail
    │       │                      AND limited to s3:* only
    │       │
    │       └── Account B
    │               Inherits: Root SCP only
    │               Effective: Cannot delete CloudTrail
    │                          All other services available (per IAM)
```

### Inheritance Rules

**Rule 1 — Cumulative Restriction:**
Every SCP in the chain from Root → Account applies. Permissions = intersection of ALL of them.

**Rule 2 — No Override Upward:**
A child OU or account **cannot** override a Deny from a parent SCP. Even if the child has an explicit Allow, parent Deny wins.

**Rule 3 — Detached SCP = No Effect:**
If no SCP is attached to an OU, that level has no restriction (but parent SCPs still apply).

**Rule 4 — Management Account Exemption:**
The management account is **completely exempt** from all SCPs, even if an SCP is explicitly attached to the Root.

**Rule 5 — Service-Linked Roles:**
SCPs **do apply** to service-linked roles in member accounts. This is a common gotcha — blocking `iam:*` with an SCP can break service-linked role creation.

### Inheritance Scenario Table (Exam Style)

| Root SCP | OU SCP | Account SCP | IAM Policy | Result |
|---|---|---|---|---|
| Allow ec2:* | Allow s3:* | — | Allow ec2:* | ❌ Denied (SCP chain = ec2 ∩ s3 = nothing) |
| Deny s3:Delete | — | — | Allow s3:* | ❌ s3:Delete denied, rest of s3 allowed |
| — | Deny ec2:Terminate | Allow ec2:* | Allow ec2:* | ❌ Terminate denied |
| Allow ec2:* | — | — | Allow s3:* | ❌ Denied (s3 not in SCP allowlist) |
| FullAWSAccess | Deny rds:* | — | Allow rds:* | ❌ rds denied by OU SCP |
