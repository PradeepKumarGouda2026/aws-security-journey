### **What is AWS WAF?**

```
AWS WAF = Web Application Firewall (Layer 7)

Layer 7 = Application Layer (OSI Model)
├─ Layer 7: HTTP/HTTPS, application protocols
├─ Layer 6: Presentation (encryption, compression)
├─ Layer 5: Session (connections)
├─ Layer 4: Transport (TCP/UDP) ← Network Firewall
├─ Layer 3: Network (IP) ← Security Groups, NACLs
├─ Layer 2: Data Link (MAC addresses)
└─ Layer 1: Physical (cables, signals)

WAF operates at Layer 7, meaning:
✅ Understands HTTP/HTTPS protocols
✅ Can read HTTP headers, body, cookies
✅ Can inspect URLs, query strings
✅ Can detect application-level attacks
✅ Pattern matching in requests/responses

What Network Firewall CANNOT do:
❌ Rate limiting per user/session
❌ CAPTCHA challenges
❌ Cookie-based rules
❌ Geo-blocking by country
❌ Bot detection (user-agent analysis)

WAF fills the gap! 🎯
```

### **WAF Core Components - Deep Dive:**

```
1. WEB ACL (Access Control List)
   └─ The main container for rules
   
   Properties:
   ├─ Name: Unique identifier
   ├─ Scope: REGIONAL or CLOUDFRONT
   │   └─ REGIONAL: ALB, API Gateway, AppSync (region-specific)
   │   └─ CLOUDFRONT: CloudFront distributions (global)
   ├─ Default Action: ALLOW or BLOCK
   │   └─ What to do if NO rule matches
   ├─ Rules: Ordered list of rules to evaluate
   ├─ Capacity: WCU (Web ACL Capacity Units)
   │   └─ Each rule consumes WCUs
   │   └─ Maximum: 1500 WCUs per Web ACL
   └─ Resource Associations: Which resources this protects
   
   Default action strategy:
   
   Approach 1: Default ALLOW (most common)
   ├─ Allow everything EXCEPT what's explicitly blocked
   ├─ Rules define what to BLOCK
   ├─ Good for: Public websites
   └─ Example: Block only known attacks
   
   Approach 2: Default BLOCK (strict)
   ├─ Block everything EXCEPT what's explicitly allowed
   ├─ Rules define what to ALLOW
   ├─ Good for: High-security APIs
   └─ Example: Allow only specific patterns

2. RULES
   └─ Individual security checks
   
   Rule types:
   
   A) REGULAR RULES
      ├─ Custom conditions you define
      ├─ Match statements (what to look for)
      ├─ Action (what to do if matched)
      └─ Examples: IP match, geo match, string match
   
   B) RATE-BASED RULES
      ├─ Count requests per 5-minute window
      ├─ Threshold: 100 to 2,000,000,000 requests
      ├─ Scope: Per IP or per session
      ├─ Action: Block for 10 minutes (default)
      └─ Perfect for: DDoS mitigation, brute force protection
   
   C) MANAGED RULE GROUPS
      ├─ Pre-built rules by AWS
      ├─ Maintained and updated by AWS
      ├─ Cover OWASP Top 10
      └─ Free or paid (Bot Control)
   
   Rule actions:
   ├─ ALLOW: Let request through
   ├─ BLOCK: Block request (403 Forbidden)
   ├─ COUNT: Count only (monitoring mode)
   ├─ CAPTCHA: Challenge with CAPTCHA
   └─ Challenge: JavaScript challenge (bot detection)
   
   Rule priority:
   ├─ Rules evaluated in order (priority 0, 1, 2...)
   ├─ First match = action taken
   ├─ No match = default action
   └─ Lower number = higher priority

3. MATCH STATEMENTS
   └─ Conditions to check in requests
   
   Available match types:
   
   Geographic Match:
   ├─ Match by country code (US, UK, CN, etc.)
   ├─ Use: Geo-blocking, compliance
   └─ Example: Block all traffic from specific countries
   
   IP Set Match:
   ├─ Match against list of IPs/CIDRs
   ├─ IP Set can contain up to 10,000 IPs
   ├─ Use: Allowlist, blocklist
   └─ Example: Block known malicious IPs
   
   Regex Pattern Set Match:
   ├─ Regular expression matching
   ├─ Up to 10 regex patterns per set
   ├─ Use: Complex pattern detection
   └─ Example: Match credit card patterns
   
   Size Constraint:
   ├─ Check size of request component
   ├─ Operators: EQ, NE, GT, GE, LT, LE
   ├─ Use: Limit request body size
   └─ Example: Block requests > 8 KB
   
   SQL Injection Match:
   ├─ Detect SQL injection patterns
   ├─ AWS-managed signatures
   ├─ Use: Database protection
   └─ Example: Block "UNION SELECT"
   
   XSS Match:
   ├─ Detect cross-site scripting
   ├─ AWS-managed signatures
   ├─ Use: Prevent XSS attacks
   └─ Example: Block <script> tags
   
   String Match:
   ├─ Simple string matching
   ├─ Case-sensitive or insensitive
   ├─ Position: EXACTLY, STARTS_WITH, ENDS_WITH, CONTAINS
   ├─ Transformations: LOWERCASE, URL_DECODE, HTML_DECODE
   └─ Example: Block requests with "admin" in path
   
   Request Components (where to look):
   ├─ URI path (/admin/login)
   ├─ Query string (?id=123&name=test)
   ├─ HTTP method (GET, POST, PUT, DELETE)
   ├─ Headers (User-Agent, Cookie, etc.)
   ├─ Body (POST data)
   ├─ Cookies
   └─ Single header (specific header)

4. IP SETS
   └─ Lists of IP addresses/CIDR ranges
   
   Use cases:
   ├─ Blocklist: Known malicious IPs
   ├─ Allowlist: Trusted IPs (office, partners)
   ├─ Dynamic: Update via API/Lambda
   └─ Threat intelligence: Import from feeds
   
   Capacity:
   ├─ Up to 10,000 IP addresses per set
   ├─ IPv4 and IPv6 supported
   ├─ CIDR ranges supported (/8, /16, /24, /32)
   └─ Updates: Instant propagation
   
   Example:
   Blocklist IP Set:
   ├─ 198.51.100.0/24
   ├─ 203.0.113.0/24
   ├─ 192.0.2.15/32
   └─ 2001:0db8::/32 (IPv6)
   
   Allowlist IP Set (office):
   ├─ 203.0.113.0/24 (HQ office)
   ├─ 198.51.100.0/28 (Remote office)
   └─ Use in rule: ALLOW if IP matches

5. REGEX PATTERN SETS
   └─ Regular expression patterns
   
   Use cases:
   ├─ Credit card detection
   ├─ SSN detection
   ├─ Custom attack patterns
   └─ Data loss prevention
   
   Capacity:
   ├─ Up to 10 regex patterns per set
   ├─ Each pattern up to 200 characters
   └─ Evaluated against request components
   
   Example patterns:
   Credit cards:
   └─ \b(?:4[0-9]{12}(?:[0-9]{3})?|5[1-5][0-9]{14})\b
   
   SSN:
   └─ \b\d{3}-\d{2}-\d{4}\b
   
   Email:
   └─ \b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b
   
   SQL Injection:
   └─ (union.*select|select.*from|insert.*into)
   
   Performance note:
   └─ Complex regex = slower evaluation
   └─ Keep patterns simple when possible

6. RULE GROUPS
   └─ Collections of rules (reusable)
   
   Types:
   
   AWS Managed Rule Groups (Free):
   ├─ Core Rule Set (CRS)
   ├─ Admin Protection
   ├─ Known Bad Inputs
   ├─ SQL Database
   ├─ Linux/Windows OS
   ├─ PHP/WordPress
   ├─ IP Reputation
   └─ Anonymous IP
   
   AWS Managed Rule Groups (Paid):
   └─ Bot Control ($10/month + $1/million requests)
   
   Custom Rule Groups:
   ├─ Your own rules
   ├─ Reusable across Web ACLs
   ├─ Share within organization
   └─ Capacity: Up to 1500 WCUs
   
   AWS Marketplace Rule Groups:
   ├─ Third-party vendors
   ├─ Specialized protection
   ├─ Additional cost
   └─ Examples: F5, Fortinet, Imperva
```

### **Rate-Based Rules - Deep Dive:**

```
Rate-based rules = Count requests and block if threshold exceeded

How they work:
1. Track requests per IP (or other scope)
2. Count over 5-minute rolling window
3. If count > threshold: Take action
4. Block duration: Configurable (default 10 min)
5. After block expires: IP can try again

Configuration:

Threshold:
├─ Minimum: 100 requests per 5 minutes
├─ Maximum: 2,000,000,000 requests per 5 minutes
├─ Typical: 2000-10000 for most applications
└─ Adjust based on legitimate traffic patterns

Scope (what to count):
├─ IP: Per source IP address (most common)
├─ FORWARDED_IP: Per X-Forwarded-For header (behind proxy)
├─ CUSTOM_KEYS: Custom aggregation
└─ Example: Count per User-Agent + IP combination

Action on rate limit:
├─ BLOCK: HTTP 403 Forbidden
├─ CAPTCHA: Challenge user to solve CAPTCHA
├─ CHALLENGE: JavaScript challenge
└─ COUNT: Monitor only (no action)

Use cases:

1. DDoS Mitigation
   Threshold: 10,000 requests per 5 min per IP
   Action: BLOCK
   Reason: Normal user won't send 10k requests in 5 min
   
2. Login Protection (Brute Force)
   Threshold: 20 requests per 5 min per IP
   Path: /login, /signin
   Action: CAPTCHA
   Reason: Prevent password guessing
   
3. API Rate Limiting
   Threshold: 1000 requests per 5 min per IP
   Action: BLOCK
   Reason: Fair usage, prevent abuse
   
4. Search Rate Limiting
   Threshold: 500 requests per 5 min per IP
   Path: /search
   Action: CHALLENGE
   Reason: Expensive operation, prevent scraping
   
5. Registration Protection
   Threshold: 5 requests per 5 min per IP
   Path: /register, /signup
   Action: CAPTCHA
   Reason: Prevent fake account creation

Advanced: Custom Keys

Aggregate by multiple dimensions:
Example: Count by IP + User-Agent

{
  "RateBasedStatement": {
    "Limit": 2000,
    "AggregateKeyType": "CUSTOM_KEYS",
    "CustomKeys": [
      {"IP": {}},
      {"Header": {"Name": "User-Agent"}}
    ]
  }
}

Result: Same IP with different User-Agent = separate counters
Use: Detect distributed attacks from same source

Block duration:
├─ Not directly configurable
├─ Default: IP blocked for duration of rate limit window
├─ After window expires: Counter resets, IP unblocked
└─ Continuous high rate = continuous blocking

Important notes:
├─ Rate limit applies PER Web ACL (not global)
├─ Multiple Web ACLs = separate rate counters
├─ CloudFront + ALB = different rate limits possible
└─ Monitor CloudWatch metrics to tune thresholds

Cost: Same as regular rules ($1/month per rule)
```

### **CAPTCHA & Challenge - User Experience:**

```
CAPTCHA action:

What happens:
1. User sends request
2. WAF evaluates rules
3. CAPTCHA rule matches
4. WAF returns CAPTCHA challenge
5. User solves CAPTCHA
6. Token generated
7. Request retried with token
8. WAF verifies token
9. Request allowed

CAPTCHA types:
├─ Image-based (default)
│   └─ "Select all images with traffic lights"
├─ Audio alternative (accessibility)
│   └─ Listen and type what you hear
└─ AWS-managed, secure

Token validity:
├─ Duration: 300 seconds (5 minutes)
├─ Scope: IP + User-Agent
├─ Single-use or time-based
└─ Stored in browser cookie

User experience:
├─ Legitimate user: Solve once, access for 5 min
├─ Bot/Attacker: Difficult to automate
└─ Balance: Security vs. UX

Challenge action:

What happens:
1. User sends request
2. WAF returns JavaScript challenge
3. Browser executes JavaScript
4. Proof of work computed
5. Token generated
6. Request retried with token
7. WAF verifies computation
8. Request allowed

JavaScript Challenge:
├─ Invisible to user (no interaction needed)
├─ Blocks headless browsers, bots
├─ Allows real browsers automatically
└─ Better UX than CAPTCHA

Use case comparison:

CAPTCHA:
├─ Use when: Human verification critical
├─ Example: Login, registration, payment
├─ UX: Slight friction, but acceptable
└─ Security: High (hard to automate)

Challenge:
├─ Use when: Bot detection needed, UX priority
├─ Example: API endpoints, search
├─ UX: Transparent (no user interaction)
└─ Security: Good (blocks most bots)

BLOCK:
├─ Use when: Known malicious, no false positives
├─ Example: Known bad IPs, attack patterns
├─ UX: None (request blocked immediately)
└─ Security: Highest (no access)

COUNT:
├─ Use when: Testing rules, observing patterns
├─ Example: New rule deployment, analytics
├─ UX: No impact (request allowed)
└─ Security: None (monitoring only)

Best practice workflow:
1. Deploy rule in COUNT mode
2. Monitor for false positives (1-2 weeks)
3. Tune rule if needed
4. Switch to CHALLENGE mode (test user impact)
5. Monitor user complaints
6. If acceptable, switch to CAPTCHA or BLOCK
7. Continuous monitoring and tuning
```

### **Geo-Blocking - Country-Level Control:**

```
Geographic match statement:

Purpose: Block or allow by country

Country codes: ISO 3166-1 alpha-2
├─ US = United States
├─ CN = China
├─ RU = Russia
├─ GB = United Kingdom
├─ DE = Germany
└─ 249 countries total

Use cases:

1. Compliance Requirements
   Example: GDPR, only serve EU users
   Rule: ALLOW if country in [EU countries list]
   Default: BLOCK all others
   
2. Reduce Attack Surface
   Example: US-only service
   Rule: ALLOW if country = US
   Default: BLOCK all others
   
3. Sanctions Compliance
   Example: Block OFAC-sanctioned countries
   Rule: BLOCK if country in [sanctioned list]
   Countries: Iran (IR), North Korea (KP), Syria (SY), etc.
   
4. Cost Optimization
   Example: High fraud from specific countries
   Rule: BLOCK if country in [high-fraud list]
   Result: Reduce chargebacks, processing costs
   
5. Licensing Restrictions
   Example: Content licensed for US only
   Rule: BLOCK if country != US
   Reason: Legal compliance

How geo-location works:
├─ IP to geolocation database (MaxMind)
├─ AWS updates database regularly
├─ Accuracy: ~95-99% for country-level
├─ Edge cases: VPNs, proxies show VPN location
└─ Tor: Shows exit node location

Limitations:
├─ VPN users appear to be in VPN country
├─ Proxy services can bypass
├─ Tor can bypass
├─ Consider combining with Anonymous IP rule
└─ Not foolproof, but good first defense

Example rule:

Block access from high-risk countries:
{
  "Name": "GeoBlockHighRisk",
  "Priority": 1,
  "Statement": {
    "GeoMatchStatement": {
      "CountryCodes": [
        "CN",  // China
        "RU",  // Russia
        "KP",  // North Korea
        "IR",  // Iran
        "SY"   // Syria
      ]
    }
  },
  "Action": {
    "Block": {}
  }
}

Allow only specific countries:
{
  "Name": "AllowOnlyUS",
  "Priority": 1,
  "Statement": {
    "NotStatement": {
      "Statement": {
        "GeoMatchStatement": {
          "CountryCodes": ["US"]
        }
      }
    }
  },
  "Action": {
    "Block": {}
  }
}

Logic: If NOT US, then BLOCK
Result: Only US traffic allowed
```

## **AWS SHIELD - DDoS PROTECTION:**

### **What is DDoS?**

```
DDoS = Distributed Denial of Service

Goal: Overwhelm target with traffic, make it unavailable

Attack types:

LAYER 3 (Network Layer):
├─ UDP Flood: Massive UDP packets
├─ ICMP Flood: Ping flood
├─ IP Fragment: Malformed IP packets
└─ Amplification: NTP, DNS, SSDP reflection

LAYER 4 (Transport Layer):
├─ SYN Flood: Half-open TCP connections
├─ ACK Flood: TCP ACK packets
├─ RST Flood: TCP reset packets
└─ Connection exhaustion

LAYER 7 (Application Layer):
├─ HTTP Flood: Valid HTTP requests (hardest to detect)
├─ Slowloris: Slow HTTP requests
├─ RUDY: Slow POST requests
└─ DNS Query Flood

Attack scale:
├─ Small: 1-10 Gbps
├─ Medium: 10-100 Gbps
├─ Large: 100-500 Gbps
├─ Massive: 500+ Gbps
└─ Record: 2.3 Tbps (AWS mitigated in 2020!)

Why DDoS is effective:
├─ Cheap to launch (botnets for rent)
├─ Hard to distinguish from legitimate traffic
├─ Overwhelms infrastructure
├─ Causes downtime = revenue loss
└─ Ransom potential (pay or we attack)
```
