## 1.1 Service Overview & Purpose

### What is AWS WAF?
AWS WAF (Web Application Firewall) is a managed service that lets you **monitor, filter, and block HTTP/HTTPS requests** to your web applications based on rules you define. It protects against common web exploits and attacks at **Layer 7 (application layer)**.

Think of WAF as a **smart security guard** at your application's front door — it inspects every incoming HTTP request and decides whether to allow, block, or count it based on your rules.

### What is AWS Shield?
AWS Shield is a **DDoS (Distributed Denial of Service) protection service** that safeguards your AWS applications against volumetric, protocol, and application-layer attacks. It operates at **Layers 3, 4, and 7**.

Think of Shield as a **flood barrier** — it absorbs and deflects massive volumetric attacks before they reach your infrastructure.

### Why Do They Exist?
```
Without WAF:
├── SQL injection attacks reach your database
├── XSS attacks execute in user browsers
├── Bot traffic floods your application
├── Scrapers steal your content at scale
├── Credential stuffing attacks your login pages
└── Known CVEs exploited before you patch

Without Shield:
├── SYN flood exhausts your server connections
├── UDP flood saturates your bandwidth
├── HTTP flood overwhelms your application
├── Application becomes unavailable for legitimate users
└── No DDoS response team support
```

```
With WAF:
├── SQL injection patterns blocked at edge
├── XSS attempts filtered before reaching app
├── Bot traffic identified and managed
├── Rate limiting prevents abuse
├── Managed rules cover OWASP Top 10 automatically
└── Custom rules for your specific threats

With Shield:
├── Always-on DDoS detection and mitigation
├── Automatic attack absorption (Standard)
├── Advanced: 24/7 DDoS Response Team (SRT)
├── Real-time attack visibility
├── Cost protection for scaling during attacks
└── Advanced: proactive engagement from AWS
```

### Exam Weight & Importance
- Appears in **Domain 3: Infrastructure Security** (22%)
- Expect **4–6 questions** involving WAF and Shield
- Commonly tested: WAF rule evaluation order, Shield Advanced features, integration patterns, rate limiting

## 1.3 Deep Dive — Every Sub-Topic

### A. WAF Web ACLs (Full Detail)

#### Web ACL Scope
```
WAF Web ACLs have two scopes:
├── REGIONAL
│     ├── Protects: ALB, API Gateway, AppSync,
│     │            Cognito, App Runner
│     └── Must be created in same region as resource
│
└── CLOUDFRONT
      ├── Protects: CloudFront distributions only
      └── Must be created in us-east-1
            (same as CloudFront certificates)
```

> ⚠️ **Exam critical:** WAF for CloudFront must be created in **us-east-1** regardless of where your origin is. Regional WAF cannot protect CloudFront.

#### Web ACL Capacity Units (WCU)
```
Every WAF rule consumes WCU (Web ACL Capacity Units):
├── Web ACL maximum: 5,000 WCU
├── Simple rule: 1 WCU
├── Regex match: 10 WCU
├── SQL injection match: 20 WCU
├── Managed rule group: varies (50-700 WCU)
└── Rate-based rule: 2 WCU

Pricing: $1.00 per million requests
         + rule costs
```

#### Rule Evaluation Order
```
Rules evaluated by PRIORITY (lowest number first):

Priority 0  → Evaluated first
Priority 1  → Evaluated second
Priority 2  → Evaluated third
...
Priority N  → Evaluated last
Default Action → Applied if no rule matches

FIRST MATCHING RULE WINS — evaluation stops
```

> ⚠️ **Critical exam point:** Rules are evaluated in **ascending priority order** (0 before 100). The **first rule that matches** terminates evaluation. No further rules are checked after a match.

#### Rule Actions
```
ALLOW:
├── Request passes through to application
├── Remaining rules NOT evaluated (match terminates)
└── Use for known-good IP allowlisting

BLOCK:
├── Request rejected with HTTP 403
├── Custom response body/status code configurable
├── Remaining rules NOT evaluated
└── Use for known-bad IPs, attack patterns

COUNT:
├── Request counted in metrics but NOT blocked
├── Evaluation CONTINUES to next rule
├── Use for: testing new rules before enforcing
│           monitoring without blocking
└── Does not terminate rule evaluation

CAPTCHA:
├── Presents CAPTCHA challenge to user
├── Valid CAPTCHA token = request allowed
├── Invalid/missing token = request blocked
└── Use for: suspected bot traffic, login pages

CHALLENGE:
├── Silent JavaScript challenge (no user interaction)
├── Detects bots that don't execute JavaScript
├── Valid challenge response = request allowed
└── Use for: automated bot detection
```

### B. WAF Rule Types (Full Detail)

#### Type 1: Managed Rule Groups
AWS provides pre-built rule groups maintained by AWS security teams:

```
AWS Managed Rule Groups (free with WAF):

Core Rule Set (AWSManagedRulesCommonRuleSet):
├── Protects against OWASP Top 10
├── SQL injection, XSS, path traversal
├── WCU: 700
└── Most commonly used rule group

Known Bad Inputs (AWSManagedRulesKnownBadInputsRuleSet):
├── Blocks requests with known malicious patterns
├── Log4Shell, SSRF patterns
└── WCU: 200

SQL Database (AWSManagedRulesSQLiRuleSet):
├── SQLi-specific rules
├── More comprehensive than Core Rule Set SQLi
└── WCU: 200

Linux OS (AWSManagedRulesLinuxRuleSet):
├── Linux-specific attack patterns
├── Command injection targeting Linux
└── WCU: 200

Windows OS (AWSManagedRulesWindowsRuleSet):
├── Windows-specific attacks
├── PowerShell injection patterns
└── WCU: 200

PHP Application (AWSManagedRulesPHPRuleSet):
├── PHP-specific vulnerabilities
└── WCU: 100

WordPress (AWSManagedRulesWordPressRuleSet):
├── WordPress-specific attack patterns
└── WCU: 100

Amazon IP Reputation List:
├── Blocks IPs associated with bots and threats
├── Updated continuously by AWS threat intel
└── WCU: 25

Anonymous IP List:
├── Blocks Tor exit nodes, VPNs, proxies
└── WCU: 50

Bot Control (AWSManagedRulesBotControlRuleSet):
├── Identifies and manages bot traffic
├── Common bots: allowed (Google, Bing)
├── Malicious bots: blocked
├── Targeted bot inspection available
└── WCU: 50 (Common) / 50+ (Targeted)

Account Takeover Prevention (ATP):
├── Protects login endpoints
├── Credential stuffing detection
├── Stolen credential checking
└── WCU: 50
```

> ⚠️ **Exam tip:** Bot Control and ATP (Account Takeover Prevention) are **additional cost** managed rules — not free like the basic managed rules. This distinction appears in cost-optimization scenarios.

#### Type 2: Rate-Based Rules
```
Rate-based rules automatically block IPs that exceed
a request threshold within a 5-minute window:

Configuration:
├── Threshold: minimum 100 requests per 5 minutes
├── Aggregation key:
│     ├── IP address (most common)
│     ├── Forwarded IP (behind proxy)
│     ├── HTTP header value
│     ├── Query argument value
│     └── URI path
├── Scope-down statement (optional):
│     └── Only count requests matching a condition
│           Example: only rate-limit /login endpoint
└── Action: BLOCK (auto-unblocked when rate drops)

Example use cases:
├── Login endpoint: 10 attempts per 5 minutes
├── API endpoint: 1000 requests per 5 minutes
├── Search endpoint: 100 searches per 5 minutes
└── Global: 2000 requests per 5 minutes per IP
```

#### Type 3: Custom Rules (Rule Statements)

**IP Set Match:**
```json
{
  "Name": "BlockBadIPs",
  "Priority": 1,
  "Statement": {
    "IPSetReferenceStatement": {
      "ARN": "arn:aws:wafv2:...:ipset/bad-ips/..."
    }
  },
  "Action": {"Block": {}},
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "BlockBadIPs"
  }
}
```

**Geo Match:**
```json
{
  "Name": "BlockCountries",
  "Statement": {
    "GeoMatchStatement": {
      "CountryCodes": ["KP", "IR", "CU"]
    }
  },
  "Action": {"Block": {}}
}
```

**String Match:**
```json
{
  "Name": "BlockSQLi",
  "Statement": {
    "ByteMatchStatement": {
      "SearchString": "UNION SELECT",
      "FieldToMatch": {"QueryString": {}},
      "TextTransformations": [
        {"Priority": 0, "Type": "URL_DECODE"},
        {"Priority": 1, "Type": "LOWERCASE"}
      ],
      "PositionalConstraint": "CONTAINS"
    }
  },
  "Action": {"Block": {}}
}
```

**Label Match (Rule Chaining):**
```
Rule 1: Managed rule adds label "awswaf:managed:aws:core-rule-set:CrossSiteScripting_Body"
Rule 2: Custom rule matches on that label → custom action

This allows building logic based on managed rule detections
without overriding the managed rule group behavior
```

#### Type 4: Rule Groups
```
Rule Groups = reusable collections of rules
├── AWS Managed Rule Groups (AWS maintains)
├── AWS Marketplace Rule Groups (third-party vendors)
│     ├── Fortinet, F5, Imperva, etc.
│     └── Additional subscription cost
└── Custom Rule Groups (you create)
      ├── Share across multiple Web ACLs
      └── Centralize rule management
```

```

├── Amazon S3 (via Kinesis Data Firehose)

└── Each rule has its own metric (if enabled)
```

### F. WAF Bot Control & Account Takeover Prevention

#### Bot Control
```
Two inspection levels:

Common Bot Control:
├── Detects and manages common bots
├── Verified bots (Google, Bing): ALLOW by default
├── Unverified bots: configurable action
├── Categories: scrapers, scanners, crawlers
└── WCU: 50

Targeted Bot Control (additional cost):
├── Detects sophisticated bots
├── Browser fingerprinting
├── Session behavior analysis
├── Detects bots that mimic human behavior
└── WCU: varies
```

#### Account Takeover Prevention (ATP)
```
Protects login endpoints from:
├── Credential stuffing attacks
│     (using leaked username/password lists)
├── Brute force attacks
├── Password spraying

How it works:
├── Monitors login endpoint specifically
├── Checks credentials against known
│     compromised credential database
├── Tracks failed login attempts
├── Applies CAPTCHA/block on suspicious activity
└── Detects anomalous login patterns

Configuration:
├── Specify login endpoint URI
├── Specify username and password fields
├── Configure threshold for failed attempts
└── Set action: BLOCK or CAPTCHA
```

## 2.1 Scenario-Based Q&A (20 Questions)

---

### Question 1
**A company has a WAF Web ACL with the following rules in order: Priority 1 — Block known bad IPs (IP Set), Priority 2 — AWS Core Rule Set (BLOCK), Priority 3 — Rate limit 1000 req/5min (BLOCK), Priority 10 — Allow corporate IPs (ALLOW). A request from a corporate IP that is also in the known bad IP set arrives. What happens?**

A) Request is allowed because corporate IPs have priority
B) Request is blocked because Priority 1 matches first
C) Both rules match — the more specific rule wins
D) Request is counted but not blocked

**Answer: B**

**Explanation:**
- WAF evaluates rules in ascending priority order — lowest number first
- Priority 1 (Block bad IPs) is evaluated before Priority 10 (Allow corporate)
- The bad IP rule matches first → request is BLOCKED
- Evaluation stops at first match — Priority 10 never evaluated
- To fix: move corporate IP allowlist to Priority 0 (lower number = evaluated first)
- This is the most common WAF rule ordering mistake in exam scenarios

---

### Question 2
**A security team wants to test new WAF rules against production traffic without blocking legitimate users. Which WAF action should they use initially?**

A) BLOCK with a custom response code of 200
B) ALLOW with logging enabled
C) COUNT
D) CHALLENGE

**Answer: C**

**Explanation:**
- COUNT action logs and counts matching requests but does NOT block them
- Traffic flows normally to application — no user impact
- Metrics accumulate in CloudWatch showing how many requests would have been blocked
- Team analyzes COUNT metrics to verify rule accuracy before switching to BLOCK
- After validation period → change action to BLOCK
- COUNT is the standard WAF testing methodology — critical exam concept
- CHALLENGE detects bots — not for rule testing

---

### Question 3
**A company deploys WAF to protect their CloudFront distribution. They create the WAF Web ACL in ap-south-1 (Mumbai) where their ALB origin is located. CloudFront traffic is not being filtered by WAF. What is wrong?**

A) CloudFront requires WAF to be attached at the ALB level not CloudFront

### Question 9
**A WAF Web ACL has a default action of ALLOW. The ACL has 5 rules — all with COUNT action. A malicious request matching all 5 rules arrives. What happens?**

A) Request is blocked after matching 5 COUNT rules
B) Request is allowed — COUNT never blocks
C) Request triggers CAPTCHA after 3 matches
D) WAF returns an error due to multiple rule matches

**Answer: B**

**Explanation:**
- COUNT action NEVER blocks requests — it only counts and logs
- Evaluation CONTINUES through all rules even after COUNT matches
- After all 5 COUNT rules, no BLOCK action has been applied
- Default action is ALLOW → request passes to application
- This is why COUNT-only configurations are dangerous in production
- All 5 COUNT rules execute and generate metrics — but traffic flows through
- Fix: change rules from COUNT to BLOCK when testing is complete

### Question 10
**A company needs to block all traffic from specific countries except for users from those countries who have a valid session cookie. Which WAF configuration achieves this?**

A) Geo match block rule — no exceptions possible
B) Priority 1: ALLOW rule matching valid session cookie, Priority 2: Geo match BLOCK rule
C) Priority 1: Geo match BLOCK rule, Priority 2: ALLOW rule for session cookie
D) Use CAPTCHA for geographic blocks

**Answer: B**

**Explanation:**
- Rule evaluation stops at first match — order is critical
- Priority 1 (ALLOW with session cookie) evaluated first
- If user has valid cookie → ALLOWED → evaluation stops (geo block never evaluated)
- If user has no valid cookie → Priority 1 doesn't match → Priority 2 geo block evaluated → BLOCKED
- Option C (geo block first) would block ALL users from those countries — even with valid cookies
- This is a classic WAF rule ordering pattern for exceptions to blocks

A) Multiple separate rules for each encoding type
B) Text transformations in WAF rules
C) Regular expression matching with encoding patterns
D) AWS managed SQL injection rule group only

- Single rule with multiple transformations is more efficient than multiple rules

## 2.2 Common Exam Traps & Distractors

### Trap 1: Higher Priority Number = Evaluated First
> ❌ **Wrong:** "Rule with Priority 100 is evaluated before Priority 1"
> ✅ **Right:** Lower number = higher priority = evaluated FIRST (Priority 0 before Priority 100)

### Trap 2: COUNT Blocks After Threshold
> ❌ **Wrong:** "COUNT action blocks request after matching 3 rules"
> ✅ **Right:** COUNT NEVER blocks — it only counts and logs, evaluation continues

### Trap 3: WAF for CloudFront Can Be in Any Region
> ❌ **Wrong:** "Create WAF in same region as CloudFront origin"
> ✅ **Right:** WAF for CloudFront MUST be in **us-east-1** with CLOUDFRONT scope

### Trap 4: Shield Standard Includes DDoS Response Team
> ❌ **Wrong:** "Contact the DDoS Response Team via Shield Standard"
> ✅ **Right:** DRT access requires **Shield Advanced** only

### Trap 5: Shield Advanced Can Be Cancelled Anytime
> ❌ **Wrong:** "Cancel Shield Advanced if attack stops"
> ✅ **Right:** Shield Advanced has a **1-year binding commitment**

### Trap 6: Rate-Based Rules Block Immediately
> ❌ **Wrong:** "Rate-based rule blocks after first request over threshold"
> ✅ **Right:** Rate is calculated over a **5-minute sliding window**

### Trap 7: Default Action Evaluated Before Rules
> ❌ **Wrong:** "Default BLOCK action prevents all unmatched traffic before rules run"
> ✅ **Right:** Default action is LAST resort — only applied when NO rules match

### Trap 8: WAF Web ACLs Shareable via RAM
> ❌ **Wrong:** "Share WAF Web ACL across accounts using AWS RAM"
> ✅ **Right:** WAF Web ACLs cannot be shared via RAM — use Firewall Manager for multi-account

### Trap 9: Shield Advanced Costs Extra for WAF
> ❌ **Wrong:** "Shield Advanced + WAF = $3,000/month + WAF charges"
> ✅ **Right:** WAF is **included at no extra charge** for Shield Advanced protected resources

### Trap 10: ALLOW Action Continues Rule Evaluation
> ❌ **Wrong:** "ALLOW action counts the request and continues to next rule"
> ✅ **Right:** ALLOW terminates rule evaluation — just like BLOCK. Only COUNT continues evaluation.

## 2.4 Elimination Strategies

### Strategy 1: CloudFront WAF = us-east-1
Any scenario with **CloudFront WAF** → eliminate other regions → must be **us-east-1 with CLOUDFRONT scope**

### Strategy 2: Testing Rules = COUNT Mode
Need to **test without impacting traffic** → eliminate BLOCK, ALLOW → **COUNT mode**

### Strategy 3: DDoS Response Team = Shield Advanced
Need **human DDoS response / SRT access** → eliminate Shield Standard → **Shield Advanced**

### Strategy 4: Multi-Account WAF = Firewall Manager
**Consistent WAF across multiple accounts** → eliminate manual deployment, RAM sharing → **AWS Firewall Manager**

### Strategy 5: Credential Stuffing = ATP
Protect **login endpoint from compromised credentials** → eliminate Core Rule Set, rate limiting → **Account Takeover Prevention (ATP)**

### Strategy 6: Rule Order = First Match Wins
**Exception to a block rule** → put ALLOW rule at **lower priority number** than BLOCK rule

### Strategy 7: Distributed Bots = Bot Control Targeted
Attack spread across **thousands of IPs** evading rate limits → eliminate rate-based rules → **Bot Control targeted inspection**

### Strategy 8: Cost Protection During Attack = Shield Advanced
**AWS bill increases during DDoS attack** → eliminate Shield Standard → **Shield Advanced cost protection**

### Strategy 9: COUNT Never Blocks
Any scenario asking if COUNT action blocks → answer is **never** — COUNT only logs/counts

### Strategy 10: WAF Bypass Prevention = Secret Header
Prevent attackers from **bypassing CloudFront WAF** by hitting ALB directly → **secret custom header from CloudFront + WAF verification on ALB**
