SCENARIO 1: SQL Injection Protection
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
A company's web application is experiencing SQL injection attempts.
The application runs on EC2 behind an Application Load Balancer.
What is the MOST cost-effective solution to block these attacks?

A) Deploy Network Firewall with Suricata IDS/IPS rules
B) Implement AWS WAF with SQL injection rule set
C) Create Security Group rules to block malicious IPs
D) Use NACLs to filter SQL patterns

Answer: B ✅

Explanation:
- WAF is Layer 7 (application layer) - perfect for SQL injection
- AWS Managed Rule Set for SQL injection is FREE
- Cost: ~$15/month (WAF + rules + requests)
- Network Firewall ($600/month) is overkill
- Security Groups can't inspect HTTP content
- NACLs can't detect SQL patterns (Layer 4 only)

Key Concept: Use WAF for application-layer attacks!

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 2: Block Social Media Access
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
A company needs to block employee access to social media sites
(facebook.com, twitter.com) from their VPC for compliance reasons.
Employees should still access AWS services and work-related sites.
What solution provides this capability?

A) Create NACL rules to block social media IP ranges
B) Use Security Groups to deny outbound traffic to social media
C) Deploy Route 53 Resolver DNS Firewall with domain blocklist
D) Implement AWS WAF with custom URL filtering rules

Answer: C ✅

Explanation:
- DNS Firewall blocks at DNS resolution level
- Blocks .facebook.com, .twitter.com (wildcard support)
- Works for HTTPS (doesn't need to decrypt)
- Cost: $90/VPC/month
- NACLs: Can't block domains, only IPs (which change)
- Security Groups: Outbound is allow-all by default (can't deny)
- WAF: Only protects resources it's attached to (not egress)

Alternative:
- Network Firewall domain lists ($600/month, if already deployed)

Key Concept: DNS Firewall for domain blocking!

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 3: DDoS Protection
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
An e-commerce website is experiencing a Layer 7 DDoS attack
with thousands of requests per second from different IPs.
The site uses CloudFront and ALB. What should you implement?

A) Shield Advanced for enhanced DDoS protection
B) WAF rate-based rule to limit requests per IP
C) Network Firewall to inspect and block traffic
D) Increase ALB capacity and EC2 Auto Scaling

Answer: B ✅

Explanation:
- Layer 7 attack = HTTP flood attack
- WAF rate-based rule: Block IPs exceeding threshold
- Example: 2000 requests per 5 minutes per IP
- Cost: ~$15/month (WAF + rules)
- Shield Standard (FREE) already protects Layer 3/4
- Shield Advanced ($3k/month) - not needed for most cases
- Network Firewall doesn't help with rate limiting
- Scaling helps but doesn't block attackers

Configuration:
Rate-based rule: 2000 requests/5min → BLOCK for 10 minutes

Key Concept: WAF for Layer 7 DDoS, Shield for Layer 3/4!

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 4: IDS/IPS Requirement
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
A healthcare company must comply with HIPAA, which requires
intrusion detection and prevention capabilities.
They have a multi-tier VPC with web, app, and database layers.
What AWS service meets this requirement?

A) AWS WAF with managed rule groups
B) GuardDuty with VPC Flow Logs
C) AWS Network Firewall with Suricata rules
D) Security Hub with AWS Config rules

Answer: C ✅

Explanation:
- HIPAA requires IDS/IPS for intrusion detection AND prevention
- Network Firewall provides both:
  - IDS mode: ALERT on suspicious traffic
  - IPS mode: DROP/REJECT malicious traffic
- Suricata rules for deep packet inspection
- Supports custom rules and AWS managed rules
- Cost: $600-1200/month (worth it for compliance)

Why others don't work:
- WAF: Only Layer 7, no IPS
- GuardDuty: Detection only, no prevention
- Security Hub: Aggregation, not IDS/IPS

Key Concept: Network Firewall = IDS/IPS for AWS!

SCENARIO 5: Multi-VPC Security
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
A company has 20 VPCs across development, staging, and production.
They want centralized security inspection for all egress traffic.
What architecture should they implement?

A) VPC Peering between all VPCs with NACLs
B) Transit Gateway with inspection VPC and Network Firewall
C) PrivateLink endpoints in each VPC
D) Security Groups allowing traffic between VPCs

Answer: B ✅

Explanation:
Architecture:
20 VPCs → Transit Gateway → Inspection VPC → Network Firewall → NAT → Internet

Benefits:
- Centralized: One firewall for all VPCs ($600/month)
- Scalable: Easy to add more VPCs
- Inspection: All traffic goes through firewall
- Cost-effective: vs 20 separate firewalls ($12k/month)

Routing:
VPC route tables: 0.0.0.0/0 → Transit Gateway
TGW route table: 0.0.0.0/0 → Inspection VPC
Inspection VPC: Traffic → Firewall → NAT → Internet

Cost:
- Transit Gateway: 20 × $36/month = $720/month
- Network Firewall: $600/month
- Total: $1,320/month ✅

Key Concept: TGW + Inspection VPC = Centralized security!

SCENARIO 6: Stateful vs Stateless
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
An application needs to allow inbound HTTP (port 80) but block
all other inbound traffic. Return traffic must be allowed.
Which combination provides this with LEAST administrative overhead?

A) Security Group: Allow inbound port 80
B) NACL: Allow inbound port 80 + outbound ephemeral ports
C) Both Security Group and NACL with matching rules
D) Network Firewall with stateful rules

Answer: A ✅

Explanation:
- Security Groups are STATEFUL
- Inbound rule: Port 80 → automatically allows return traffic
- No need to configure outbound rules for responses
- NACL is STATELESS: Must configure both directions
  - Inbound: Port 80
  - Outbound: Ephemeral ports (1024-65535)
- Network Firewall: Overkill for simple port allow

Rule comparison:
Security Group (1 rule):
- Inbound: TCP 80 from 0.0.0.0/0

NACL (2 rules):
- Inbound: TCP 80 from 0.0.0.0/0
- Outbound: TCP 1024-65535 to 0.0.0.0/0

Key Concept: Use Security Groups when possible (stateful = easier)!

SCENARIO 7: Private Service Connectivity
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Question:
A SaaS provider wants to offer their analytics API to 100 customers
without exposing their VPC infrastructure. Customers should access
via private connectivity without internet traversal.
What AWS service enables this?

A) VPC Peering with each customer VPC
B) Transit Gateway with shared routing
C) AWS PrivateLink with VPC Endpoint Service
D) Direct Connect to each customer

Answer: C ✅

Explanation:
PrivateLink architecture:
Provider: NLB → VPC Endpoint Service → Service Name
Customers: VPC Endpoint → Private IP in their VPC

Benefits:
- Scalable: Supports thousands of consumers
- Private: Traffic never leaves AWS network
- Secure: Provider approves each connection
- Hidden: Customers don't see provider VPC
- No IP conflicts: Each customer uses their own CIDR

Cost:
- Provider: $7/month (endpoint service)
- Each customer: $7/month (endpoint)
- Total for 100 customers: $707/month

Alternatives don't scale:
- VPC Peering: 100 peering connections (impossible to manage)
- Transit Gateway: Exposes entire VPC (not just service)
- Direct Connect: Expensive, physical connectivity

Key Concept: PrivateLink for SaaS/service exposure!
