## 1.1 Service Overview & Purpose

### What is AWS Secrets Manager?
AWS Secrets Manager is a **fully managed service** that helps you **store, retrieve, rotate, audit, and control access** to secrets such as database credentials, API keys, OAuth tokens, and other sensitive configuration data.

Think of it as a **secure, auditable vault** for your application secrets — one that can also **automatically rotate** those secrets without any application downtime.

### What is AWS Systems Manager Parameter Store?
Parameter Store is a **hierarchical key-value store** for configuration data and secrets. It is part of AWS Systems Manager and provides **secure, centralized storage** for configuration parameters ranging from plain-text configuration values to encrypted secrets.

Think of it as a **configuration database** — broader than just secrets, covering all application configuration.

### Why Do They Exist? (Problems They Solve)
```
Without secrets management:
├── Secrets hardcoded in application code
│     └── Committed to Git → exposed forever
├── Secrets in environment variables
│     └── Visible in process listings, logs
├── Secrets in config files
│     └── Copied to every server, hard to rotate
├── No audit trail
│     └── Who accessed what secret when?
├── Manual rotation
│     └── Forgot to rotate → security risk
└── No centralized control
      └── Secrets scattered across 50 microservices
```

```
With Secrets Manager + Parameter Store:
├── Secrets stored encrypted (KMS)
├── Centralized access via API
├── Full CloudTrail audit trail
├── Automatic rotation (Secrets Manager)
├── Fine-grained IAM access control
├── Cross-account access supported
└── Native integration with RDS, ECS, Lambda
```

### Exam Weight & Importance
- Appears in **Domain 2: Identity & Access Management** and **Domain 3: Infrastructure Security**
- Expect **3–5 questions** directly involving these services
- Commonly tested: rotation mechanics, Secrets Manager vs Parameter Store decision, cross-account patterns, RDS integration

## 1.3 Deep Dive — Every Sub-Topic

### A. Secrets Manager — Secret Types & Storage

#### Supported Secret Types
```
Built-in rotation support:
├── Amazon RDS credentials
│     ├── MySQL, PostgreSQL, Oracle, SQL Server, MariaDB
│     └── Aurora MySQL, Aurora PostgreSQL
├── Amazon Redshift credentials
├── Amazon DocumentDB credentials
└── Other (generic secret — custom rotation Lambda)

Custom secrets (manual or custom Lambda rotation):
├── API keys (Stripe, Twilio, etc.)
├── OAuth tokens
├── SSH keys
├── TLS certificates
└── Any JSON-formatted secret
```

#### Secret Value Format
```json
// RDS secret format (auto-managed)
{
  "username": "dbadmin",
  "password": "new-password-generated",
  "engine": "mysql",
  "host": "mydb.cluster-xxxx.ap-south-1.rds.amazonaws.com",
  "port": 3306,
  "dbname": "myappdb",
  "dbClusterIdentifier": "mydb-cluster"
}

// Custom API key secret
{
  "api_key": "sk-live-xxxxxxxxxxxx",
  "api_secret": "xxxxxxxxxxxxxxxxxxxx",
  "endpoint": "https://api.service.com/v1"
}
```

#### Secret Versioning
```
Secret versions are managed automatically:
│
├── AWSCURRENT  → Version apps should use
│                 GetSecretValue returns this by default
│
├── AWSPENDING  → New version created during rotation
│                 Exists temporarily during rotation
│                 Promoted to AWSCURRENT when rotation succeeds
│
└── AWSPREVIOUS → Last AWSCURRENT before rotation
                  Kept as fallback for in-flight requests
                  Automatically cleaned up after next rotation
```

#### Secret Encryption
- All secrets encrypted with **KMS** at rest
- Default: **AWS managed key** (`aws/secretsmanager`)
- Recommended: **Customer Managed Key (CMK)** for full control
- In transit: **TLS 1.2+**

### B. Automatic Secret Rotation (Exam Critical)

#### How Rotation Works
Rotation uses a **Lambda function** that follows a **4-step protocol**:

```
Step 1 — createSecret:
  ├── Lambda generates new credentials
  ├── Stores as NEW VERSION with label AWSPENDING
  └── AWSCURRENT still active (apps unaffected)

Step 2 — setSecret:
  ├── Lambda tests AWSPENDING credentials
  └── Verifies new credentials work before applying

Step 3 — setSecret (continued):
  ├── Lambda updates the actual resource (e.g., RDS)
  └── Changes password on the database

Step 4 — finishSecret:
  ├── Moves AWSPENDING → AWSCURRENT
  ├── Moves old AWSCURRENT → AWSPREVIOUS
  └── Apps now get new credentials on next GetSecretValue call
```

> ⚠️ **Exam critical:** During rotation, **two versions exist simultaneously** (AWSCURRENT and AWSPENDING). Applications using cached credentials continue working. Apps calling GetSecretValue get the new credentials only after finishSecret completes.

#### Rotation Schedule Options
```
Rotation schedule:
├── Fixed interval: every N days (e.g., every 30 days)
├── Cron expression: specific time/day
│     Example: cron(0 2 1 * ? *) = 2am on 1st of each month
└── Manual: triggered on-demand via console or API
```

#### Single User vs Multi User Rotation

**Single User Rotation (default):**
```
RDS has one user: dbadmin
├── Rotation changes dbadmin's password
├── Brief window where old and new passwords both valid
├── Apps using cached old password may get auth errors
└── Use when: simple apps, acceptable brief disruption
```

**Multi User Rotation (recommended for production):**
```
RDS has two users: dbadmin_a and dbadmin_b
├── Apps always use AWSCURRENT (e.g., dbadmin_a)
├── Rotation creates new password for AWSPENDING (dbadmin_b)
├── Switches AWSCURRENT to dbadmin_b
├── Zero downtime — apps always have valid credentials
└── Use when: production workloads requiring zero disruption
```

#### Rotation Lambda Requirements
```
Lambda must:
├── Be in same VPC as the database (for RDS)
├── Have outbound access to:
│     ├── Secrets Manager endpoint (port 443)
│     └── Database endpoint (port 3306/5432/etc.)
├── Have IAM permissions:
│     ├── secretsmanager:GetSecretValue
│     ├── secretsmanager:PutSecretValue
│     ├── secretsmanager:DescribeSecret
│     └── secretsmanager:UpdateSecretVersionStage
└── Have DB permissions to change passwords
```

> ⚠️ **Common exam trap:** If rotation Lambda is in a VPC and needs to reach Secrets Manager, it needs either a **VPC endpoint** for Secrets Manager or a **NAT Gateway**. Without this, rotation silently fails.

### C. Cross-Account Secret Sharing

#### Resource-Based Policy Approach
```
Account A (secret owner):
  Attach resource policy to secret:
  {
    "Principal": {"AWS": "arn:aws:iam::AccountB:role/AppRole"},
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "*"
  }

Account B (secret consumer):
  IAM policy on AppRole:
  {
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "arn:aws:secretsmanager:region:AccountA:secret:my-secret"
  }

  PLUS KMS key policy in Account A must allow Account B
  (secret is encrypted — Account B needs KMS access too)
```

> ⚠️ **Three-part requirement for cross-account secrets:**
> 1. Secret resource policy (Account A)
> 2. IAM policy (Account B)
> 3. KMS key policy (Account A — if using CMK)

### D. Parameter Store — Deep Dive

#### Parameter Tiers

| Feature | Standard | Advanced |
|---|---|---|
| **Parameter count** | 10,000 per account | 100,000 per account |
| **Value size** | 4KB max | 8KB max |
| **Cost** | Free | $0.05 per parameter/month |
| **Parameter policies** | ❌ No | ✅ Yes |
| **TTL/Expiry** | ❌ No | ✅ Yes |
| **Change notifications** | ❌ No | ✅ EventBridge |
| **Higher throughput** | Standard | Higher |

#### Parameter Policies (Advanced Tier Only)
```
Parameter policies allow:
├── Expiration policy
│     └── Parameter automatically expires after date
│           → Useful for enforcing rotation
├── ExpirationNotification
│     └── EventBridge event X days before expiry
└── NoChangeNotification
      └── Alert if parameter unchanged for N days
```

#### Parameter Store Hierarchy
```
Hierarchical naming best practice:
/
├── /App1/
│     ├── /Production/
│     │     ├── DB_HOST        (String)
│     │     ├── DB_PORT        (String)
│     │     └── DB_PASSWORD    (SecureString)
│     └── /Staging/
│           ├── DB_HOST        (String)
│           └── DB_PASSWORD    (SecureString)
└── /Shared/
      ├── /CertificateARN      (String)
      └── /KMSKeyARN           (String)
```

#### Getting Parameters by Path (Powerful Feature)
```bash
# Get ALL parameters under a path
aws ssm get-parameters-by-path \
  --path "/App1/Production/" \
  --recursive \
  --with-decryption

# Returns all parameters in one API call
# Much more efficient than getting each individually
```

#### SecureString Encryption
```
SecureString uses KMS:
├── Default: AWS managed key (aws/ssm)
├── Custom: Customer Managed Key (CMK)
└── Encryption transparent to caller with correct IAM

IAM required for SecureString:
├── ssm:GetParameter (or ssm:GetParameters)
└── kms:Decrypt (on the KMS key used)
```

### E. Secrets Manager vs Parameter Store (Exam Critical)

#### Feature Comparison (Full)

| Feature | Secrets Manager | Parameter Store |
|---|---|---|
| **Primary purpose** | Secrets with rotation | Config + secrets |
| **Automatic rotation** | ✅ Built-in | ❌ Manual/custom |
| **Cost** | $0.40/secret/month + API | Free (Standard) |
| **Value size** | 64KB | 4KB (Std), 8KB (Adv) |
| **Versioning** | ✅ Full versioning | ✅ Basic versioning |
| **Cross-account** | ✅ Resource policy | ✅ Via IAM + KMS |
| **Native RDS rotation** | ✅ Built-in Lambda | ❌ Custom solution |
| **Hierarchy/paths** | ❌ Flat names | ✅ Hierarchical |
| **Parameter policies** | N/A | ✅ Advanced tier |
| **CloudTrail** | ✅ Yes | ✅ Yes |
| **KMS encryption** | ✅ Always | ✅ SecureString only |
| **Resource policy** | ✅ Yes | ❌ No |
| **Plain text values** | ❌ Always encrypted | ✅ String type |
| **Config values** | ❌ Overkill | ✅ Natural fit |

#### Decision Framework (Exam Scenarios)

```
Use Secrets Manager when:
├── Need automatic rotation
├── Database credentials (RDS, Redshift, DocumentDB)
├── Need cross-account secret sharing
├── Audit trail of every access is required
├── $0.40/month per secret is acceptable
└── Secret has a defined lifecycle (create, rotate, expire)

Use Parameter Store when:
├── Plain configuration values (no encryption needed)
├── Large number of parameters (cost-sensitive)
├── Hierarchical config (by environment, service)
├── Need to fetch entire config path at once
├── Lambda environment variable replacement
├── No automatic rotation needed
└── Free tier is important (Standard)
```

### F. Integration Patterns

#### RDS Integration with Secrets Manager
```
Application code:
  import boto3, json

  def get_db_credentials():
      client = boto3.client('secretsmanager')
      response = client.get_secret_value(
          SecretId='prod/myapp/db-credentials'
      )
      return json.loads(response['SecretString'])

  # Never hardcode credentials
  # Always fetch from Secrets Manager at runtime
  # Cache with TTL to avoid throttling
```

#### Lambda Integration
```
Pattern 1: Environment variable (Parameter Store)
  Lambda env var: DB_HOST = {{resolve:ssm:/App/Prod/DB_HOST}}
  → CloudFormation resolves at deploy time

Pattern 2: Runtime fetch (Secrets Manager)
  Lambda code fetches secret at invocation
  → Always gets latest rotated credentials
  → Cache in Lambda global scope (persists across invocations)

Pattern 3: Lambda extension
  → AWS Parameters and Secrets Lambda Extension
  → Local HTTP endpoint (localhost:2773)
  → Caches parameters/secrets locally in Lambda
  → Reduces API calls and latency
```

#### ECS Integration
```
ECS Task Definition:
{
  "secrets": [
    {
      "name": "DB_PASSWORD",
      "valueFrom": "arn:aws:secretsmanager:region:account:secret:prod/db"
    },
    {
      "name": "API_KEY",
      "valueFrom": "arn:aws:ssm:region:account:parameter/app/api-key"
    }
  ]
}
→ ECS fetches secrets at task launch
→ Injects as environment variables in container
→ Task execution role needs Secrets Manager + KMS permissions
```

#### CloudFormation Dynamic References
```yaml
# Reference Parameter Store value
DBHost: '{{resolve:ssm:/App/Production/DB_HOST}}'

# Reference SecureString (encrypted)
DBPassword: '{{resolve:ssm-secure:/App/Production/DB_PASS}}'

# Reference Secrets Manager
DBCredentials: '{{resolve:secretsmanager:prod/db:SecretString:password}}'
```

### G. Secret Caching Best Practices

#### Why Cache?
```
Problem: Every Lambda invocation calls GetSecretValue
→ Latency: 10-50ms per API call
→ Cost: API calls charged
→ Throttling: 10,000 TPS limit for GetSecretValue

Solution: Cache with TTL
→ Fetch once, cache in Lambda global scope
→ Refresh every 5-60 minutes (before rotation window)
→ AWS provides SDK cache clients for this
```

#### AWS Secrets Manager Caching Client
```python
import boto3
from aws_secretsmanager_caching import SecretCache, \
    SecretCacheConfig

# Configure cache
cache_config = SecretCacheConfig(
    max_cache_size=1000,
    exception_retry_delay_base=1,
    exception_retry_growth_factor=2,
    exception_retry_delay_max=3600,
    default_version_stage='AWSCURRENT',
    secret_refresh_interval=3600,  # 1 hour TTL
    secret_version_stage_refresh_interval=3600
)

client = boto3.client('secretsmanager')
cache = SecretCache(config=cache_config, client=client)

# Use cached secret
secret = cache.get_secret_string('prod/myapp/db')
```

## 1.5 Security & Compliance Angles

### IAM Permissions

**Secrets Manager:**
```
secretsmanager:GetSecretValue     → Read secret (apps need this)
secretsmanager:CreateSecret       → Create new secret
secretsmanager:UpdateSecret       → Update secret value
secretsmanager:RotateSecret       → Trigger rotation
secretsmanager:DeleteSecret       → Delete secret
secretsmanager:DescribeSecret     → View metadata
secretsmanager:ListSecrets        → List all secrets
secretsmanager:PutResourcePolicy  → Set resource policy
```

**Parameter Store:**
```
ssm:GetParameter                  → Read single parameter
ssm:GetParameters                 → Read multiple parameters
ssm:GetParametersByPath           → Read by path hierarchy
ssm:PutParameter                  → Create/update parameter
ssm:DeleteParameter               → Delete parameter
ssm:DescribeParameters            → List parameters
```

### Common Misconfigurations

| Misconfiguration | Risk | Fix |
|---|---|---|
| Hardcoded secrets in code | Exposure via Git | Always use Secrets Manager/Parameter Store |
| No rotation enabled | Stale credentials | Enable automatic rotation |
| Rotation Lambda no VPC endpoint | Rotation silently fails | Add VPC endpoint or NAT Gateway |
| GetSecretValue in hot loop | Throttling + cost | Cache with TTL |
| No resource policy cross-account | Access denied | Add resource policy + KMS policy |
| Using plain String for passwords | Unencrypted at rest | Use SecureString for Parameter Store |
| Long secret deletion window | Delayed cleanup | Use force delete for non-critical secrets |
| No CloudTrail monitoring | Undetected access | Alert on GetSecretValue anomalies |

### Compliance Relevance

| Framework | Relevance |
|---|---|
| **PCI DSS** | Protect credentials, no hardcoding, rotate secrets |
| **HIPAA** | Access controls, audit trail for PHI credentials |
| **ISO 27001** | Cryptographic controls, access management |
| **SOC 2** | Change management, logical access controls |
| **CIS AWS** | Secrets rotation, no hardcoded credentials |

### Question 1
**A company stores RDS MySQL credentials in AWS Secrets Manager with automatic rotation enabled every 30 days. After a recent rotation, several Lambda functions report database authentication failures. What is the MOST likely cause?**

A) Secrets Manager deleted the old credentials immediately after rotation
B) The Lambda functions are caching the old credentials and not fetching the latest AWSCURRENT version
C) The rotation Lambda function failed to update the RDS password
D) IAM permissions for Lambda were revoked during rotation

**Answer: B**

**Explanation:**
- Lambda functions often cache secrets in global scope for performance
- After rotation, cached credentials become stale — auth fails against new RDS password
- Secrets Manager does NOT delete old credentials immediately — AWSPREVIOUS is retained
- Fix: implement cache TTL shorter than rotation interval, or use AWS Secrets Manager caching client
- Rotation Lambda failure would show in CloudTrail and rotation status — different symptom
- IAM permissions are not affected by rotation

---

### Question 2
**A company has a strict security policy requiring that database credentials must be automatically rotated every 24 hours with zero application downtime. Which rotation strategy should they implement?**

A) Single user rotation with 24-hour interval
B) Multi user rotation with 24-hour interval
C) Manual rotation triggered by EventBridge every 24 hours
D) Parameter Store with custom Lambda rotating credentials daily

**Answer: B**

**Explanation:**
- Multi user rotation maintains TWO database users (e.g., dbadmin_a and dbadmin_b)
- While one is AWSCURRENT, the other is being rotated as AWSPENDING
- Apps always have valid credentials — zero downtime
- Single user rotation has a brief window where old and new passwords may conflict
- Manual rotation introduces human error risk and is not automatic
- Parameter Store has no built-in rotation — requires custom solution with more complexity

---

### Question 3
**A security engineer wants to share a Secrets Manager secret from Account A with an application running in Account B. The secret is encrypted with a CMK in Account A. What combination of configurations is required?**

A) Secret resource policy in Account A only
B) Secret resource policy in Account A + IAM policy in Account B
C) Secret resource policy in Account A + IAM policy in Account B + KMS key policy in Account A
D) AWS RAM share of the secret to Account B

**Answer: C**

**Explanation:**
- Three components required for cross-account secret access:
- 1) Secret resource policy (Account A) — allows Account B principal to GetSecretValue
- 2) IAM policy (Account B) — allows the role to call secretsmanager:GetSecretValue on Account A's secret
- 3) KMS key policy (Account A) — allows Account B to use the CMK for decryption
- Without KMS access, Account B cannot decrypt the secret value even with Secrets Manager access
- AWS RAM does not support Secrets Manager secrets

---

### Question 4
**An application running in a private VPC subnet with no internet access needs to retrieve secrets from Secrets Manager at runtime. What is required?**

A) NAT Gateway to route traffic to Secrets Manager
B) VPC Endpoints for both Secrets Manager and KMS
C) Internet Gateway attached to the VPC
D) VPC Peering to the Secrets Manager VPC

**Answer: B**

**Explanation:**
- Private subnets with no NAT Gateway cannot reach Secrets Manager via internet
- VPC Endpoint for Secrets Manager routes API calls through AWS private network
- Secret values are encrypted — KMS VPC Endpoint also needed for decryption
- NAT Gateway works but routes traffic over public internet — less secure and higher cost
- Internet Gateway makes subnet public — violates private subnet requirement
- Secrets Manager is not in a customer VPC — VPC peering is not applicable

---

### Question 5
**A development team stores 500 application configuration values including feature flags, API endpoints, database hostnames, and 10 database passwords. They want the most cost-effective solution. Which approach is BEST?**

A) Store all 500 values in Secrets Manager
B) Store all 500 values in Parameter Store Standard tier
C) Store 490 non-sensitive values in Parameter Store Standard, 10 passwords in Secrets Manager
D) Store all values in S3 with SSE-KMS encryption

**Answer: C**

**Explanation:**
- Parameter Store Standard is FREE for non-sensitive config values
- Secrets Manager costs $0.40/secret/month → 500 secrets = $200/month
- Database passwords need rotation → Secrets Manager is appropriate
- Feature flags and endpoints are non-sensitive → Parameter Store String type (free)
- Hostnames and ports → Parameter Store String type (free)
- S3 is not designed for secrets management — no rotation, no versioning, no audit

---

### Question 6
**A rotation Lambda function for an RDS secret is consistently failing. CloudTrail shows the Lambda is invoked but the rotation status shows RotationFailed. The Lambda is deployed in a private VPC subnet. What is the MOST likely cause?**

A) The Lambda execution role lacks RDS permissions
B) The Lambda cannot reach the Secrets Manager endpoint to update secret versions
C) The RDS instance is in a different availability zone
D) The rotation schedule interval is too short

**Answer: B**

**Explanation:**
- Rotation Lambda in private VPC needs to call Secrets Manager API (steps 1-4)
- Without VPC endpoint for Secrets Manager or NAT Gateway, API calls fail
- Lambda can reach RDS (in same VPC) but cannot reach Secrets Manager endpoint
- This is the most common rotation failure pattern in exam scenarios
- RDS AZ placement doesn't affect rotation Lambda connectivity
- Rotation interval doesn't cause RotationFailed status

---

### Question 7
**An application calls GetSecretValue 1,000 times per second across multiple Lambda functions retrieving the same database credential. The team notices high Secrets Manager costs and occasional throttling. What is the BEST solution?**

A) Increase Secrets Manager TPS quota via Service Quotas
B) Store the secret in Parameter Store instead
C) Implement the AWS Secrets Manager caching client with appropriate TTL
D) Store credentials in Lambda environment variables

**Answer: C**

**Explanation:**
- AWS Secrets Manager caching client caches secrets in memory with configurable TTL
- Dramatically reduces API calls — one call per cache TTL period instead of per invocation
- TTL should be shorter than rotation interval to avoid stale credentials
- Quota increase doesn't reduce cost — still charged per API call
- Moving to Parameter Store loses automatic rotation capability
- Lambda environment variables are static — don't get updated after rotation

### Question 11
**A Lambda function retrieves a database secret from Secrets Manager. After a rotation, the Lambda function still connects successfully using old credentials for 45 minutes before failing. What explains this behavior?**

A) Secrets Manager keeps AWSPREVIOUS valid for 1 hour after rotation
B) The Lambda execution environment is reusing a cached secret from a previous invocation
C) RDS accepts both old and new passwords during a 1-hour grace period
D) The rotation Lambda has a 45-minute delay configured

**Answer: B**

**Explanation:**
- Lambda execution environments persist between invocations (warm starts)
- If secret is cached in Lambda global scope (outside handler), it persists in memory
- The cached old credential works until the execution environment is recycled
- After ~45 minutes the environment was recycled, forcing a fresh secret fetch
- AWSPREVIOUS exists but Secrets Manager doesn't automatically serve it to applications
- RDS does not have a grace period for old passwords after rotation
- This is exactly why cache TTL must be shorter than rotation interval

## 2.2 Common Exam Traps & Distractors

### Trap 1: GetSecretValue Always Returns Latest
> ❌ **Wrong:** "GetSecretValue always returns the most recently created version"
> ✅ **Right:** GetSecretValue returns AWSCURRENT by default — which is the active version, not necessarily the most recently created (AWSPENDING exists during rotation)

### Trap 2: Rotation Immediately Invalidates Old Credentials
> ❌ **Wrong:** "After rotation completes, old credentials are immediately invalid"
> ✅ **Right:** AWSPREVIOUS is retained — old credentials may still work briefly depending on database behavior

### Trap 3: Parameter Store SecureString Only Needs ssm Permission
> ❌ **Wrong:** "ssm:GetParameter is sufficient to retrieve a SecureString"
> ✅ **Right:** SecureString requires ssm:GetParameter AND kms:Decrypt on the encrypting key

### Trap 4: Secrets Manager Secret Deletion is Immediate
> ❌ **Wrong:** "Deleted secrets are immediately gone"
> ✅ **Right:** 7-30 day recovery window (use --force-delete-without-recovery to bypass)

### Trap 5: Cross-Account Secrets Only Need Resource Policy
> ❌ **Wrong:** "Add Account B to secret resource policy and they can access it"
> ✅ **Right:** Resource policy + IAM policy in Account B + KMS key policy = all three required

### Trap 6: Parameter Store Standard Supports Parameter Policies
> ❌ **Wrong:** "Set expiry policy on Standard tier parameter"
> ✅ **Right:** Parameter policies only available in Advanced tier

### Trap 7: Rotation Lambda Can Always Reach Secrets Manager
> ❌ **Wrong:** "Lambda in private VPC can always call Secrets Manager API"
> ✅ **Right:** Private VPC Lambda needs VPC endpoint or NAT Gateway to reach Secrets Manager

### Trap 8: Secrets Manager and Parameter Store Both Have Resource Policies
> ❌ **Wrong:** "Use Parameter Store resource policy for cross-account access"
> ✅ **Right:** Only Secrets Manager supports resource-based policies — Parameter Store does not

### Trap 9: All Secret Types Have Native Rotation
> ❌ **Wrong:** "Enable native rotation for Stripe API keys in Secrets Manager"
> ✅ **Right:** Only RDS, Redshift, DocumentDB have native rotation — everything else needs custom Lambda

### Trap 10: ECS Task Role Fetches Secrets at Startup
> ❌ **Wrong:** "ECS task role needs Secrets Manager permissions for secret injection"
> ✅ **Right:** Task EXECUTION role fetches secrets at launch — task role is for runtime API calls

## 2.4 Elimination Strategies

### Strategy 1: Auto Rotation = Secrets Manager
Any scenario requiring **automatic credential rotation** → eliminate Parameter Store → Secrets Manager

### Strategy 2: Cost Sensitive + No Rotation = Parameter Store
**Large number of config values, no rotation needed** → eliminate Secrets Manager ($0.40 each) → Parameter Store Standard (free)

### Strategy 3: Cross-Account = Three Requirements
Cross-account secret access → always need **all three**: resource policy + IAM policy + KMS key policy

### Strategy 4: ECS Secrets = Task Execution Role
ECS secret injection at startup → **task execution role** (not task role, not service role)

### Strategy 5: Private VPC + Secrets Manager = VPC Endpoint
Lambda/ECS in private VPC calling Secrets Manager → **VPC endpoint** (not NAT Gateway for best practice)

### Strategy 6: Parameter Expiry = Advanced Tier
Parameter policies, TTL, expiry → **Advanced tier only** → Standard tier eliminated

### Strategy 7: Large Values (>4KB) = Advanced Tier or Secrets Manager
Values exceeding 4KB → Advanced tier (up to 8KB) or Secrets Manager (up to 64KB)

### Strategy 8: Hierarchy + Path Fetch = Parameter Store
Hierarchical config, fetch entire path → **Parameter Store** (GetParametersByPath)

### Strategy 9: Rotation Failure in Private VPC = Connectivity
Rotation Lambda fails, private VPC → **VPC endpoint for Secrets Manager** missing

### Strategy 10: Config + Automation = Remediation
Detect non-compliant secrets + auto-fix → **AWS Config rule + SSM Automation** remediation
