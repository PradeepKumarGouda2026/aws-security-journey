## 1.1 Service Overview & Purpose

### What is AWS Directory Service?
AWS Directory Service is a **managed service** that provides multiple ways to use **Microsoft Active Directory (AD)** or other directory services with AWS. It eliminates the need to run and manage your own directory infrastructure on EC2 instances.

A **directory** is essentially a database of:
- Users and their credentials
- Groups and memberships
- Computers and devices
- Policies (Group Policy Objects)
- Trust relationships

### Why Does It Exist? (Problem It Solves)
Before AWS Directory Service, enterprises had two painful options:

```
Option 1: Run AD on EC2 (self-managed)
  ├── Deploy Windows Server EC2 instances
  ├── Install AD Domain Services manually
  ├── Configure replication manually
  ├── Patch OS and AD yourself
  ├── Manage backups yourself
  ├── Handle failover yourself
  └── Pay for Windows Server licenses

Option 2: Extend on-premises AD to AWS
  ├── Set up VPN or Direct Connect
  ├── High latency for auth requests
  ├── Single point of failure if link goes down
  └── Complex networking requirements
```

AWS Directory Service solves this by providing:
- **Fully managed** AD infrastructure
- **Multi-AZ** by default (high availability)
- **Automatic patching** and maintenance
- **Native AWS integration** (IAM Identity Center, RDS, WorkSpaces, etc.)
- **No licensing headaches** for Managed AD

### AWS Directory Service Options Overview
```
AWS Directory Service
├── AWS Managed Microsoft AD    → Full AD in AWS (enterprise)
├── AD Connector                → Proxy to on-premises AD
├── Simple AD                   → Lightweight Samba-based directory
└── Amazon Cloud Directory      → Cloud-native hierarchical directory
```

### When to Use Which
| Scenario | Recommended Option |
|-------------------------------------------|---------------------------|
| Full AD features in AWS, enterprise scale | AWS Managed Microsoft AD |
| Keep all data on-premises, just need AWS auth | AD Connector |
| Small org, basic LDAP needs, no AD features needed | Simple AD |
| Custom hierarchical data, not user auth | Amazon Cloud Directory |
| Existing on-prem AD + extend to AWS | Managed AD with trust |
| Data residency — nothing stored in AWS | AD Connector |

### Exam Weight & Importance
- Appears in **Domain 2: Identity & Access Management** (16%)
- Frequently paired with IAM Identity Center, EC2 domain join, RDS, WorkSpaces scenarios
- Expect **2–4 questions** directly or indirectly involving Directory Services
- Commonly tested: **which directory option fits the scenario**

## 1.3 Deep Dive — Every Sub-Topic

### A. AWS Managed Microsoft AD (Full Detail)

#### What It Is
AWS Managed Microsoft AD is a **genuine Microsoft Active Directory** (not a simulation) running on **AWS-managed infrastructure**. It gives you:
- Full AD DS (Active Directory Domain Services)
- LDAP support
- Kerberos authentication
- Group Policy Objects (GPOs)
- AD trusts (one-way and two-way)
- Schema extensions
- Fine-grained password policies

#### Editions

| Feature | Standard Edition | Enterprise Edition |
|---|---|---|
| **Objects supported** | 30,000 | 500,000 |
| **Use case** | Small/medium orgs | Large enterprises |
| **Multi-region replication** | ❌ | ✅ |
| **Price** | Lower | Higher |

#### Domain Controllers
- Always deployed as **at least 2 DCs** across 2 AZs
- AWS manages DC patching, replication, backups
- You **cannot RDP** into the domain controllers
- You interact via AD management tools on a domain-joined EC2

#### What AWS Manages vs What You Manage
```
AWS Manages:                    You Manage:
├── DC patching                 ├── Users and groups
├── DC replication              ├── Group Policy Objects
├── Backups (daily snapshots)   ├── AD trusts
├── Hardware failures           ├── OU structure
├── Multi-AZ failover           ├── Schema extensions
└── Software updates            └── RADIUS/MFA config
```

#### Organizational Units (OUs)
When Managed AD is created, AWS pre-creates:
```
Domain: corp.example.com
├── AWS Reserved (AWS-managed, you cannot modify)
│     ├── Domain Controllers
│     └── AWS Delegated Groups
└── <Your OU> (you manage everything here)
      ├── Users
      ├── Computers
      └── Groups
```

> ⚠️ **Exam gotcha:** You cannot modify the **AWS Reserved** OU. Any attempt to modify AWS-managed OUs will be blocked. Create your own OUs for all user/computer objects.

#### Trust Relationships
Managed AD supports **AD trust relationships** with:
- On-premises AD domains
- Other AWS Managed AD domains
- External forests

**Trust types:**
```
One-way trust (outgoing):
  On-prem AD trusts AWS AD
  → On-prem users can access AWS resources

One-way trust (incoming):
  AWS AD trusts on-prem AD
  → AWS users can access on-prem resources

Two-way trust (bidirectional):
  Both domains trust each other
  → Users in either domain can access resources in both

Forest trust:
  Extends trust across entire AD forests
  → All domains in both forests are trusted

External trust:
  Trust between specific domains only
  → More limited scope
```

#### Kerberos Authentication Flow with Managed AD
```
Step 1: EC2 instance joins domain
Step 2: User logs in with AD credentials
Step 3: EC2 contacts Managed AD DC for Kerberos TGT
Step 4: DC validates credentials, issues TGT
Step 5: User uses TGT to request service tickets
Step 6: User accesses resources using service tickets
```

#### Multi-Region Replication (Enterprise Edition)
```
Primary Region (ap-south-1)
├── DC-1 (AZ-A)
└── DC-2 (AZ-B)
        │
        │ AD Replication
        ▼
Secondary Region (us-east-1)
├── DC-3 (AZ-A)
└── DC-4 (AZ-B)
```
- Read/write in primary region
- Read-only in secondary regions (by default)
- Useful for global workloads, WorkSpaces in multiple regions

#### Integration Points
```
AWS Managed Microsoft AD integrates with:
├── IAM Identity Center          → SSO for AWS accounts
├── Amazon EC2                   → Domain join
├── Amazon RDS (SQL Server)      → Windows Authentication
├── Amazon RDS (MySQL/PostgreSQL)→ Kerberos auth
├── Amazon WorkSpaces            → Virtual desktops
├── Amazon WorkDocs              → Document collaboration
├── Amazon FSx for Windows       → Windows file shares
├── AWS Transfer Family          → SFTP with AD auth
└── Amazon QuickSight            → BI with AD groups
```

### B. AD Connector (Full Detail)

#### What It Is
AD Connector is a **directory gateway** (proxy) that redirects directory requests to your on-premises Active Directory. It is **not** a directory itself — it stores absolutely no directory data in AWS.

#### How It Works
```
AWS Service request (e.g., EC2 login)
        │
        ▼
AD Connector (in your VPC)
        │
        │ Forwards request via VPN/Direct Connect
        ▼
On-Premises Active Directory
        │
        │ Authenticates user, returns result
        ▼
AD Connector returns result to AWS service
```

#### Sizes

| Size | Use Case | Users/Connections |
|---|---|---|
| **Small** | Up to 500 users | Low traffic |
| **Large** | 500–5000 users | Higher traffic |

#### What AD Connector CAN Do
- Redirect authentication to on-premises AD
- Allow EC2 instances to domain-join on-prem AD
- Enable sign-in to AWS Management Console with AD credentials
- Integrate with IAM Identity Center
- Work with WorkSpaces using on-prem AD
- Support MFA via RADIUS server on-premises

#### What AD Connector CANNOT Do
```
AD Connector limitations:
├── ❌ Cannot be used as an identity source for Amazon Cognito
├── ❌ Does NOT support AD trusts
├── ❌ Does NOT support schema extensions
├── ❌ Does NOT support Group Policy Objects natively
├── ❌ Does NOT work if on-prem AD is unreachable (no failover)
├── ❌ Cannot be shared across multiple accounts natively
└── ❌ Does NOT support RADIUS-based MFA natively in all services
```

#### Network Requirements
```
AD Connector requires connectivity to on-prem AD:
├── VPN (Site-to-Site) OR AWS Direct Connect
├── TCP/UDP port 88  (Kerberos)
├── TCP/UDP port 389 (LDAP)
├── TCP port 636     (LDAPS)
├── TCP/UDP port 464 (Kerberos password change)
├── TCP port 445     (SMB)
└── TCP/UDP port 53  (DNS)
```

> ⚠️ **Critical exam point:** If VPN or Direct Connect goes down, **AD Connector stops working** entirely — there is no failover. AWS Managed AD with trust relationship is more resilient.

### C. Simple AD (Full Detail)

#### What It Is
Simple AD is a **Microsoft Active Directory–compatible** directory powered by **Samba 4**. It is NOT genuine Microsoft AD — it's an open-source implementation that supports a subset of AD features.

#### Sizes

| Size | Objects | Use Case |
|---|---|---|
| **Small** | Up to 500 | Very small orgs, dev/test |
| **Large** | Up to 5,000 | Small to medium orgs |

#### What Simple AD Supports
```
Simple AD supports:
├── ✅ Basic LDAP operations
├── ✅ Kerberos-based SSO
├── ✅ User accounts and groups
├── ✅ Basic Group Policy
├── ✅ EC2 domain join
├── ✅ IAM Identity Center (basic)
└── ✅ WorkSpaces (basic)
```

#### What Simple AD Does NOT Support
```
Simple AD does NOT support:
├── ❌ AD trusts (cannot connect to on-prem AD)
├── ❌ MFA
├── ❌ RADIUS
├── ❌ Schema extensions
├── ❌ Fine-grained password policies
├── ❌ Replication to other directories
├── ❌ PowerShell AD module
└── ❌ RDS SQL Server Windows Authentication
```

> ⚠️ **Exam trap:** Simple AD looks attractive for cost savings but has critical limitations. Any scenario requiring AD trusts, MFA, or SQL Server auth → eliminate Simple AD immediately.

### D. Amazon Cloud Directory (Full Detail)

#### What It Is
Amazon Cloud Directory is a **cloud-native, highly scalable hierarchical data store** — it is fundamentally different from the other three options. It is NOT an Active Directory service.

#### Use Cases
```
Cloud Directory is for:
├── Org charts (hierarchical employee data)
├── Device registries (IoT device management)
├── Network topology graphs
├── Course catalogs (e-learning)
└── Custom hierarchical data structures
```

#### Key Characteristics
- Supports **multiple hierarchies** simultaneously
- Scales to **hundreds of millions of objects**
- Flexible schema — define your own object types
- Accessed via **API** (not LDAP or Kerberos)
- Not a replacement for AD — completely different purpose

> ⚠️ **Exam tip:** If a question asks about user authentication, SSO, or domain join → Cloud Directory is NEVER the answer. It's for **custom hierarchical data**, not identity/authentication.

### E. EC2 Domain Join Patterns

#### Pattern 1: Join to AWS Managed Microsoft AD
```bash
# On EC2 (Windows) — PowerShell
Add-Computer -DomainName "corp.example.com" `
             -Credential (Get-Credential) `
             -Restart

# Using SSM Documents (recommended — no manual steps)
aws ssm create-association \
  --name "AWS-JoinDirectoryServiceDomain" \
  --targets "Key=instanceids,Values=i-1234567890abcdef0" \
  --parameters '{"directoryId":["d-1234567890"],
                 "directoryName":["corp.example.com"],
                 "dnsIpAddresses":["10.0.1.10","10.0.2.10"]}'
```

#### Pattern 2: Seamless Domain Join (Launch-Time)
```json
// EC2 Launch Template — automatically joins domain at launch
{
  "IamInstanceProfile": {
    "Name": "AmazonSSMDirectoryServiceAccess"
  },
  "TagSpecifications": [{
    "ResourceType": "instance",
    "Tags": [{"Key": "aws:directory:id", "Value": "d-1234567890"}]
  }]
}
```

#### Pattern 3: Linux Domain Join
```bash
# Linux EC2 joining AWS Managed AD
# Install required packages
sudo yum install -y sssd realmd krb5-workstation \
  samba-common-tools oddjob oddjob-mkhomedir adcli

# Join the domain
sudo realm join -U Admin corp.example.com

# Verify join
realm list

# Configure SSSD for AD authentication
sudo systemctl enable sssd
sudo systemctl start sssd
```

### F. RDS Integration with Directory Services

#### SQL Server Windows Authentication
```
User authenticates with AD credentials
        │
        ▼
RDS SQL Server instance
        │ Kerberos
        ▼
AWS Managed Microsoft AD
        │ (Optional trust)
        ▼
On-premises AD
```

Setup requirements:
- AWS Managed Microsoft AD (Simple AD and AD Connector NOT supported for RDS SQL Server)
- IAM role: `AmazonRDSDirectoryServiceAccess`
- VPC DNS must resolve directory domain

#### MySQL/PostgreSQL Kerberos Auth
```bash
# Create RDS instance with Kerberos auth
aws rds create-db-instance \
  --db-instance-identifier lab33-rds \
  --db-instance-class db.t3.micro \
  --engine mysql \
  --domain d-1234567890 \
  --domain-iam-role-name rds-directoryservice-access-role \
  --master-username admin \
  --master-user-password <password>
```

## 1.5 Security & Compliance Angles

### IAM Permissions for Directory Service

| Action | IAM Permission |
|---|---|
| Create directory | `ds:CreateDirectory` |
| Describe directories | `ds:DescribeDirectories` |
| Create trust | `ds:CreateTrust` |
| Create AD Connector | `ds:ConnectDirectory` |
| Enable IAM Identity Center | `ds:AuthorizeApplication` |
| Delete directory | `ds:DeleteDirectory` |

### Encryption

| Layer | Managed AD | AD Connector | Simple AD |
|---|---|---|---|
| **Data at rest** | AES-256 | N/A (no data) | AES-256 |
| **Data in transit** | TLS/Kerberos | TLS | TLS/Kerberos |
| **Snapshots** | Encrypted | N/A | Encrypted |
| **Customer KMS** | ❌ | ❌ | ❌ |

> ⚠️ None of the Directory Service options support **customer-managed KMS keys** — encryption uses AWS-managed keys only.

### Logging & Monitoring

**CloudTrail Events:**
```
ds:CreateDirectory         → New directory created
ds:DeleteDirectory         → Directory deleted
ds:CreateTrust             → Trust relationship established
ds:ConnectDirectory        → AD Connector created
ds:EnableSso               → SSO enabled for directory
ds:CreateAlias             → Alias created for directory
```

**CloudWatch Metrics (Managed AD):**
```
├── ExceptionCount         → Failed operations
├── ClientAuthenticationRequests → Auth request volume
└── DirectoryMonitoringData → DC health metrics
```

**AWS Security Hub:**
- Findings for exposed directories
- Compliance checks for directory configurations

### Common Misconfigurations

| Misconfiguration | Risk | Fix |
|---|---|---|
| AD Connector with unreliable VPN | Auth outages | Use Managed AD with trust for resilience |
| No RADIUS MFA on Managed AD | Weak authentication | Configure RADIUS MFA server |
| Modifying AWS Reserved OU | Breaks managed infrastructure | Only manage your own OUs |
| Simple AD for enterprise use | Missing critical features | Upgrade to Managed AD |
| Directory in single AZ | No HA | Always use multi-AZ (default for Managed AD) |
| No directory snapshots | Data loss risk | Enable automated snapshots |
| Overly permissive AD admin account | Lateral movement risk | Use least-privilege AD accounts |

## 2.1 Scenario-Based Q&A (20 Questions)

---

### Question 1
**A company has strict data residency requirements — no employee directory data can be stored outside their on-premises datacenter. They need AWS WorkSpaces for remote employees. Which Directory Service option should they use?**

A) AWS Managed Microsoft AD
B) Simple AD
C) AD Connector
D) Amazon Cloud Directory

**Answer: C**

**Explanation:**
- AD Connector is a pure proxy — stores absolutely NO data in AWS
- All authentication requests are forwarded to on-premises AD
- Managed AD and Simple AD both store directory data in AWS — violate data residency
- Cloud Directory is not an authentication service

---

### Question 2
**A company uses AWS Managed Microsoft AD. Their VPN connection to on-premises goes down. Which statement is TRUE?**

A) All AWS authentication fails because Managed AD depends on on-premises AD
B) AWS authentication continues normally — Managed AD operates independently
C) Only EC2 domain join fails, other services continue
D) Managed AD automatically fails over to on-premises AD

**Answer: B**

**Explanation:**
- AWS Managed Microsoft AD is a **fully independent** directory in AWS
- It does NOT depend on on-premises connectivity to function
- On-premises trust is optional — if configured, cross-domain auth may fail but AWS-side auth continues
- This is a key resilience advantage over AD Connector
- AD Connector WOULD fail if VPN goes down — Managed AD would NOT

---

### Question 3
**A company needs to authenticate users to Amazon RDS SQL Server using their Active Directory credentials. Which Directory Service option supports this?**

A) Simple AD
B) AD Connector
C) AWS Managed Microsoft AD
D) Amazon Cloud Directory

**Answer: C**

**Explanation:**
- RDS SQL Server Windows Authentication **only** works with AWS Managed Microsoft AD
- Simple AD does not support RDS SQL Server Windows Auth
- AD Connector does not support RDS SQL Server Windows Auth
- Cloud Directory is not an authentication service
- This is one of the most commonly tested limitations

---

### Question 4
**A startup has 200 employees, no on-premises infrastructure, no AD experience, and needs basic user authentication for EC2 and WorkSpaces in a single AWS region. They want the lowest cost option. What should they use?**

A) AWS Managed Microsoft AD Standard Edition
B) AD Connector
C) Simple AD Small
D) Amazon Cloud Directory

**Answer: C**

**Explanation:**
- Simple AD Small is the lowest cost option
- Supports up to 500 users — fits 200 employees

## 2.2 Common Exam Traps & Distractors

### Trap 1: Simple AD Supports Trusts
> ❌ **Wrong:** "Use Simple AD and establish a trust with on-premises AD"
> ✅ **Right:** Simple AD has ZERO trust support — Managed AD required for trusts

### Trap 2: AD Connector Stores Data in AWS
> ❌ **Wrong:** "AD Connector replicates user data to AWS for faster authentication"
> ✅ **Right:** AD Connector stores absolutely nothing — pure proxy

### Trap 3: AD Connector is Resilient to On-Premises Outages
> ❌ **Wrong:** "AD Connector fails over to cached credentials if VPN goes down"
> ✅ **Right:** AD Connector has zero resilience — VPN down = auth down

### Trap 4: Cloud Directory is an AD Replacement
> ❌ **Wrong:** "Use Cloud Directory for EC2 domain join"
> ✅ **Right:** Cloud Directory is for custom hierarchical data — not AD or auth

### Trap 5: RDS SQL Server Works with Simple AD or AD Connector
> ❌ **Wrong:** "Configure AD Connector for RDS SQL Server Windows Authentication"
> ✅ **Right:** RDS SQL Server Windows Auth = Managed AD ONLY

### Trap 6: Managed AD Depends on On-Premises
> ❌ **Wrong:** "If on-premises AD goes down, Managed AD stops working"
> ✅ **Right:** Managed AD is fully independent — on-prem outage doesn't affect it

### Trap 7: MFA is Native in Managed AD
> ❌ **Wrong:** "Enable native TOTP MFA directly in Managed AD console"
> ✅ **Right:** Managed AD MFA requires RADIUS server configuration

### Trap 8: Simple AD and Managed AD are Interchangeable
> ❌ **Wrong:** "Simple AD is a cost-effective version of Managed AD with same features"
> ✅ **Right:** Simple AD is Samba 4, NOT Microsoft AD — significant feature gaps

### Trap 9: AWS Reserved OU Can Be Modified with Admin Rights
> ❌ **Wrong:** "Use Directory Administrator credentials to modify AWS Reserved OU"
> ✅ **Right:** AWS Reserved OU is locked — create your own OUs

### Trap 10: Multi-Region Replication Available in Standard Edition
> ❌ **Wrong:** "Enable multi-region replication on Standard Edition Managed AD"
> ✅ **Right:** Multi-region replication = Enterprise Edition only

## 2.4 Elimination Strategies

### Strategy 1: Data Residency = AD Connector
Any mention of **no data in AWS** or **data sovereignty** → eliminate Managed AD and Simple AD → AD Connector

### Strategy 2: Trust Relationships = Managed AD Only
Any mention of **AD trust** with on-premises → eliminate Simple AD and AD Connector → Managed AD

### Strategy 3: RDS SQL Server Auth = Managed AD Only
**RDS SQL Server Windows Authentication** → always Managed AD — eliminate everything else

### Strategy 4: Custom Hierarchical Data = Cloud Directory
Not about users/auth but about **custom data structures** → Cloud Directory

### Strategy 5: On-Premises Goes Down = Managed AD Wins
Scenario about **resilience to on-premises outages** → Managed AD (independent) beats AD Connector (dependent)

### Strategy 6: Small Org, No On-Prem, Low Cost = Simple AD
**Startup, small team, no AD experience, lowest cost** → Simple AD (if no advanced features needed)

### Strategy 7: Multi-Region = Enterprise Edition
Any **multi-region** directory requirement → Managed AD Enterprise Edition

### Strategy 8: Eliminate Cloud Directory Quickly
In any scenario about **user auth, SSO, domain join, MFA** → eliminate Cloud Directory immediately
