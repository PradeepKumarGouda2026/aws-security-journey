## **Section 1: CloudTrail**

**Q1: B) AWS CloudTrail**
- CloudTrail logs every API call made in your AWS account
- Essential for compliance, security investigation, and audit trails
- Records who, what, when, where, and result of every API call

**Q2: C) Enable log file validation**
- Log file validation creates digest files that prove logs haven't been tampered with
- Uses cryptographic hashing to detect any modifications
- A and B are good security practices but don't specifically prevent tampering

**Q3: B) Data events (S3 GetObject, PutObject)**
- Management events (control plane): Logged by default ✅
- Data events (data plane like S3 GetObject): Must be explicitly enabled ❌
- Reason: Data events are very high volume and cost extra

**Q4: C) Use Amazon Athena to query logs**
- Athena allows SQL queries on S3 logs (fast and efficient)
- Event History only stores 90 days
- CloudWatch Logs has retention limits and costs
- Athena is the best long-term search solution

**Q5: B) CloudTrail → CloudWatch Logs → Metric Filter → Alarm → SNS**
- This is the correct real-time alerting architecture
- Metric filter converts log pattern to metric
- Alarm triggers when metric threshold is met
- EventBridge can work too, but this is the classic CloudWatch pattern

**Q6: C) 90 days**
- CloudTrail Event History retains events for 90 days automatically
- Free feature, no configuration needed
- For longer retention, logs must go to S3

**Q7: C) SSH sessions to EC2 instances**
- CloudTrail logs AWS API calls only
- SSH sessions happen at the OS level (not AWS API)
- Use CloudWatch Logs or third-party tools for OS-level logging

**Q8: B) Create a multi-region trail**
- Multi-region trail captures events from all regions in one trail
- Most efficient and cost-effective approach
- Logs go to a single S3 bucket

**Q9: B) Configure S3 bucket lifecycle policy**
- CloudTrail delivers to S3, but doesn't manage retention
- Use S3 lifecycle policies to manage retention and transitions
- Example: Keep 1 year in S3, then move to Glacier for 6 years

**Q10: B) Why an API call failed**
- errorCode shows the reason for failure (AccessDenied, InvalidParameter, etc.)
- errorMessage provides additional details
- If empty/null, the API call succeeded

## **Section 2: GuardDuty**

**Q11: B) Unsupervised learning and anomaly detection**
- GuardDuty uses ML to detect anomalies and patterns
- Learns normal behavior and flags deviations
- Also uses threat intelligence feeds

**Q12: A, C, D) CloudTrail event logs, VPC Flow Logs, DNS logs**

**Q13: B) EC2 instance is querying Bitcoin mining-related domains**

- "BitcoinTool.B!DNS" = DNS queries to Bitcoin domains
- Indicates potential crypto mining (or legitimate Bitcoin node)

**Q14: B) GuardDuty → EventBridge → Lambda → Change security group**
- EventBridge receives GuardDuty findings
- Lambda changes security group to isolation-sg (blocks all traffic)
- This is the standard automated response pattern
- You built this in Week 3! 🎯

**Q15: C) 0.1-8.9+**
- GuardDuty uses decimal severity scores
- Low: 0.1-3.9, Medium: 4.0-6.9, High: 7.0-8.9+
- Different from Inspector's CVSS (0-10)

**Q16: B) No, it's completely agentless**
- GuardDuty analyzes logs only (CloudTrail, VPC Flow, DNS)
- No software installation needed
- One of its key advantages

**Q17: B) Create a suppression rule for the finding type**
- Suppression rules filter out expected findings
- Can filter by IP, finding type, resource, etc.
- Finding is still recorded but not shown as active
- Don't disable GuardDuty - you'll miss real threats!

**Q18: D) 15-30 minutes, can generate findings immediately**
- GuardDuty starts analyzing immediately upon enabling
- Some findings can appear within minutes
- Complex behavioral patterns may take 15-30 minutes

**Q19: B) $4-10 per month + usage**
- Base: $4/month per account

- Typical small account: $4-15/month total

**Q20: B) API calls made using IAM credentials from Tor network**

## **Section 4: Inspector**

**Q31: A, C, D) CVEs, Network misconfigurations, Package vulnerabilities**
- Inspector scans for security vulnerabilities
- Package vulnerabilities = outdated software with known CVEs
- Network reachability = ports open to 0.0.0.0/0
- Does NOT scan code quality or business logic

**Q32: A) EC2, ECR, Lambda**
- Inspector scans compute resources
- EC2: OS packages + network
- ECR: Container image layers
- Lambda: Runtime + dependencies
- Does NOT scan S3, RDS, DynamoDB

**Q33: B) SSM Agent (pre-installed on Amazon Linux 2023)**
- SSM Agent allows Inspector to inventory packages
- Pre-installed on Amazon Linux 2, 2023, Ubuntu, Windows
- Not a separate "Inspector agent"
- Must have IAM role: AmazonSSMManagedInstanceCore

**Q34: B) CVSS (Common Vulnerability Scoring System)**
- CVSS v3.1 scoring (0.0-10.0)
- Industry standard for vulnerability severity
- Critical: 9.0-10.0, High: 7.0-8.9, Medium: 4.0-6.9, Low: 0.1-3.9

**Q35: B) Remediate immediately (same day)**
- Critical vulnerabilities (9.0-10.0) = immediate remediation
- High (7.0-8.9) = within 7 days
- Medium (4.0-6.9) = within 30 days
- Low (0.1-3.9) = when convenient
- You found and fixed critical CVEs in Week 3! 🎯

**Q36: B) On push + periodic re-scan**
- Inspector scans ECR images automatically on push
- Re-scans periodically (daily) for new CVEs
- Enhanced scanning with deeper analysis available
- Continuous vulnerability monitoring

**Q37: B) Network reachability issue**
- Inspector checks security group rules
- Flags overly permissive rules (0.0.0.0/0)
- Not a software vulnerability, but a configuration risk

**Q38: B) Inspector automatically rescans and closes the finding**
- Inspector continuously monitors resources
- After you patch (e.g., `yum update`), Inspector rescans within 24h
- Finding automatically marked CLOSED when vulnerability no longer exists
- No manual intervention needed!

**Q39: B) ~$12-15 per month**
- $1.25 per EC2 instance per month (first 100)
- 10 instances × $1.25 = $12.50/month
- Very affordable for continuous vulnerability scanning

**Q40: A) Inspector finds vulnerabilities, GuardDuty finds active threats**
- Inspector: Static analysis (CVEs, package versions, network config)
- GuardDuty: Runtime detection (active attacks, compromised instances)
- Both needed for complete security!
- Inspector = "what's broken?", GuardDuty = "who's attacking?"
